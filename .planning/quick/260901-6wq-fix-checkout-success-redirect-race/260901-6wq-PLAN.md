<objective>
After a shopper successfully places an order on ANY of the three channels — WhatsApp,
Manual Transfer (MTN/Orange Money), Cash on Delivery — they never see the order
confirmation. The browser lands on `/cart`, showing "Your cart is empty."

The fix is one deletion: `revalidatePath(\`/s/${slug}\`, "layout")` at
`src/server/checkout/actions.ts:442` is removed, along with its now-unused
`next/cache` import.

Purpose: this is Phase 3 core order-placement functionality. The confirmation screen
carries the order number, the D-12 tracking link (the shopper's ONLY route back to
their order — there is no account, and the plaintext token exists nowhere in the
database) and, on the manual-transfer path, the payment instructions. Losing it means
every shopper who buys anything is left believing the purchase failed, while the order
row, the stock hold and the audit trail all exist server-side. The order is placed
correctly; only the screen that tells anyone about it is lost.

Output: one call and one import deleted from `submitCheckout`, a rationale comment in
its place, one existing unit test rescoped, one new source-scanning contract test, and
one runtime assertion added to the isolation suite. No change to the checkout page's
guard, no change to `checkout-form.tsx`, no change to `src/server/cart/actions.ts`, no
new dependency.

**1. The failure, mechanically.**

`submitCheckout` (`src/server/checkout/actions.ts`) ends, after `placeOrder` succeeds,
with three statements in this order (lines 434-442):

    await idempotency.rememberOrderForKey(...);   // claim the key
    await cartCache.clearStoredCart(cartId);      // the basket is now empty
    revalidatePath(`/s/${slug}`, "layout");       // <- the bug

That `revalidatePath` makes Next re-render the CURRENTLY OPEN `/checkout` route as part
of finishing this same Server Action. `src/app/s/[slug]/checkout/page.tsx:91` then runs
again:

    if (payable.length === 0) redirect("/cart");

The cart is empty *because the order being placed just succeeded*, so the guard fires,
and the server-issued redirect wins over the client's `setOutcome(result)` at
`checkout-form.tsx:268` — the state update that would have rendered the confirmation
section (`checkout-form.tsx:286-398`).

Confirmed live in the dev server log: `POST /checkout` returns **200** (the action
succeeds, nothing throws) immediately followed by `GET /cart`. The order row exists.
The screen is what is lost. Unconditional in the code — not gated by channel — so all
three payment paths fail identically.

**3. THE DECISIVE FINDING: `revalidatePath` does not compare paths. Scoping it narrower
does NOT fix this.**

The obvious fix — "revalidate the storefront root, the PDP route and the cart page
instead of the whole layout, so the open `/checkout` route is not a target" — **does not
work**, and this is provable from the installed package rather than guessed:

`node_modules/next/dist/server/web/spec-extension/revalidate.js:86-106` —
`revalidatePath(path, type)` builds an implicit cache tag from the path and delegates
to the internal `revalidate(tags, expression)` with `profile === undefined`.

`node_modules/next/dist/server/web/spec-extension/revalidate.js:220-223` — the tail of
that function, verbatim:

    if (!profile || cacheLife?.expire === 0) {
        // TODO: only revalidate if the path matches
        store.pathWasRevalidated = ActionDidRevalidateStaticAndDynamic;
    }

The `// TODO: only revalidate if the path matches` is Next's own comment. Path matching
is **not implemented**. Any `revalidatePath` call, with any path and any type, sets the
flag.

`node_modules/next/dist/server/app-render/action-handler.js:963` and `:990` then decide
whether to re-render the current page purely from that flag — the requested path is
never consulted:

    skipPageRendering ||= workStore.pathWasRevalidated === undefined ||
                          workStore.pathWasRevalidated === ActionDidNotRevalidate;

So `skipPageRendering === false` for **every** revalidating action, and the currently
open route is re-rendered regardless of which path was named. `/checkout` re-renders,
the guard fires, the redirect wins. Targeting `/s/{slug}/cart` instead of
`/s/{slug}` changes nothing.

The bundled docs say the same thing in prose —
`node_modules/next/dist/docs/01-app/03-api-reference/04-functions/revalidatePath.md:19`:
*"**Server Functions**: Updates the UI immediately (if viewing the affected path)."*
Under a `"layout"` revalidation of `/s/{slug}`, `/checkout` **is** an affected path.
But the source is stronger than the doc: it shows the affected-path test does not exist
at all yet.

**Two further doors are closed by the same flag, so do not reach for them:**
- `refresh()` (new in Next 16) sets `pathWasRevalidated = ActionDidRevalidateDynamicOnly`
  (`revalidate.js:83`) — still not `ActionDidNotRevalidate`, so it still re-renders.
- Writing a cookie from the action sets the flag too
  (`node_modules/next/dist/server/web/spec-extension/adapters/request-cookies.js:130`),
  so a "just placed an order" cookie read by the page would itself force the re-render
  it was meant to survive.

**4. Why deleting the call does not leave the header bubble stale.** Four facts, all
verified:

a. **Every storefront page is dynamic.** `StoreHeader` awaits `getCurrentCart(slug)`
   (`src/server/cart/read.ts`), which awaits `cookies()`. None of these pages can enter
   the full route cache, so every server render reads the cart from Redis fresh. There
   is no server-side cache entry for the deleted call to invalidate.

b. **The client Router Cache does not hold them either.**
   `node_modules/next/dist/docs/01-app/03-api-reference/05-config/01-next-config-js/staleTimes.md:42`:
   *"`v15.0.0` | The `dynamic` `staleTimes` default changed from 30s to 0s."*
   `next.config.ts` sets no `experimental.staleTimes` (verified — the file contains only
   `images.remotePatterns` and `allowedDevOrigins`). A `<Link>` navigation to `/`,
   `/p/{slug}` or `/cart` therefore always refetches from the server.

c. **Prefetch cannot cache a stale count.** `src/app/s/[slug]/loading.tsx`,
   `cart/loading.tsx` and `checkout/loading.tsx` all exist, so auto-prefetch only ever
   caches the static shell above the loading boundary. The header streams from the
   server on every navigation.

d. **`clearStoredCart` really empties it** — `src/server/cart/cache.ts:238-249` deletes
   the Redis key (the cookie is left in place, which is fine: `getCurrentCart` returns
   `null` for a cookie whose key is gone).

**The one residual gap, stated honestly rather than hidden:** browser **back/forward**
navigation always restores from the Router Cache regardless of `staleTimes`. A shopper
who presses Back from the confirmation screen may briefly see the pre-order cart, and
the header on the confirmation screen itself keeps its pre-order count for as long as
the shopper stays there. Both self-heal on the next interaction (clicking through from
that stale cart re-renders `/checkout` server-side, finds an empty basket, and correctly
redirects to a freshly rendered empty `/cart`). This is a cosmetic, transient,
back-button-only artifact, and it is strictly better than losing the confirmation
screen on 100% of orders. Record it in the SUMMARY; do not try to fix it here — every
mechanism that would fix it is closed by fact 3.
