# Phase 05.3 — Validation Strategy

> Per-phase validation contract for feedback sampling during execution.

---

## Test Infrastructure

| Property | Value |
|----------|-------|
| **Framework** | Vitest 4.1.10, two projects (`unit`, `isolation`). `unit` runs on `environment: "node"` — no jsdom, no testing-library. Every "component" test in this repo is a source scan or a pure-logic test; no component in this phase can be behaviourally tested. This is exactly why `src/lib/editor/reducer.ts` exists as a separate, pure-logic-testable module. |
| **Config file** | `vitest.config.ts` |
| **Quick run command** | `npm run test:unit` (→ `vitest run tests/unit --reporter=dot`) |
| **Full suite command** | `npm run test:full` (→ `dotenv -e .env.test -- vitest run`, needs the dedicated Neon test branch) |
| **Additional gates** | `npm run lint` (`--max-warnings=0`), `npm run typecheck` (`tsc --noEmit`), `npm run build` (run **before** `typecheck` — routes must actually generate) |
| **Baseline** | 651 passing across 39 unit files as of quick task 260908-bv1 |

---

## Sampling Rate

- **Per task commit:** `npm run test:unit && npm run lint && npm run typecheck`
- **Per wave merge:** `npm run build` then `npm run test:unit`, plus the dead-route grep gate
- **Phase gate:** `npm run test:full` green (or `test:unit` + the two named isolation files if the test branch is unavailable), plus manual verification of the six things no automated test can see (Task 3's `checkpoint:human-verify`, listed below)
