> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## ⚠️ READ THIS FIRST — WHAT THIS PHASE CHANGES AND WHAT IT DOES NOT

This is a **route split**, not a redesign. One surface (Surface 3 — Blue/gold/slate, Outfit headings, `0.75rem` radius, per `04-UI-SPEC.md`) becomes two routes instead of one. **Every token, every field kind, every rail row, every publish-bar rule, every a11y contract in `04-UI-SPEC.md` § Storefront Editor carries over unchanged** unless this document explicitly says otherwise. Where this document is silent, `04-UI-SPEC.md` and `05.1-UI-SPEC.md` win.

**D-B is binding on this document too:** no Header/Template/Footer grouping, no add/remove sections, no undo/redo. Nothing in this contract introduces any of the three.

**This document supersedes, narrowly:**
- `04-UI-SPEC.md` § Storefront Editor → *Navigation* table (route is no longer `/dashboard/storefront-editor`; the sidebar item's `href` changes)
- `04-UI-SPEC.md` § Storefront Editor → *Layout* (the ≥`lg` two-pane / <`lg` toggle description now applies to the Editor page only, not to a single combined route)
- `04-UI-SPEC.md` § Storefront Editor → *The rail — two views* → *List view* → `Change template` row (no longer opens a third rail view; now a link to the Themes page)
- The `ChangeTemplatePanel` component's role: it stops being a rail-embedded panel and becomes the Themes page's own content, renamed `ThemesBrowser`

**Everything else in `04-UI-SPEC.md` § Storefront Editor is unchanged and still governs:** the rail's `Brand & logo` row and settings panel, all six field kinds, the preview canvas and its handshake/timeout/selection-sync behaviour, the Publish bar's copy and states, the view-only/Starter/trial rules, the accessibility floor, the responsive strategy (Edit/Preview toggle below `lg`).

## Resolved Decisions (the four flagged items)

These were explicitly flagged by `05.3-RESEARCH.md` as beyond research's authority. Resolved here, with reasons, so the planner does not re-open them.

### R-1 — What "full-screen Editor" means: **Option B, full-bleed within the dashboard shell**

**Decision:** The Editor page (`/dashboard/storefront/editor`) opts out of `(dashboard)/layout.tsx`'s content padding with a local negative-margin bleed. It does **not** move to a new route group. Sidebar, header band, `TrialBanner`, and `<Toaster/>` all remain mounted and visible exactly as they are on every other dashboard route.

**Mechanism, concretely:**

```tsx
// src/app/(dashboard)/dashboard/storefront/editor/page.tsx's root return,
// or a wrapper div at the top of editor-shell.tsx's render:
<div className="-mx-4 -my-8 flex min-h-[calc(100svh-3.5rem)] flex-col sm:-mx-8">
  <EditorShell ... />
</div>
```

| Detail | Contract |
|---|---|
| Horizontal bleed | `-mx-4 sm:-mx-8` — cancels `(dashboard)/layout.tsx`'s `px-4 py-8 sm:px-8` exactly, so the editor's own rail/preview panes reach the same edges the header band already reaches |
| Vertical bleed | `-my-8` — cancels the `py-8` top/bottom, so the editor region sits directly under whatever renders above it. When `TrialBanner` renders nothing (`state === "subscribed"`) that's the header band itself, with no gap; when a trial is active or expired the banner (plus the parent's `gap-6`) still sits between the header and the bleed block — "full-bleed" describes the editor's own edges, not a claim that the trial banner disappears. |
| Height | `min-h-[calc(100svh-3.5rem)]` — `3.5rem` (56px) is the header's `min-h-14`. This is what makes the editor read as "fills the screen" rather than "a tall block on a scrolling page," and is exact only in the no-banner state; with `TrialBanner` rendered, the visible editor region is shorter by the banner's own height plus `gap-6`, which is expected and correct (the banner is meant to stay visible, not be covered). `svh` not `vh`, same reasoning as the flagship hero (mobile browser chrome). |
| `TrialBanner` | Stays **above** this bleed block, inside the still-padded flow — i.e., the bleed div is a sibling of `<TrialBanner/>`, not a wrapper around it. D-11 ("above the content on every dashboard route") is satisfied unchanged. |
| Sidebar / header / `<Toaster/>` | Untouched — they live in the layout, outside anything this page controls. |
| What "full-screen" buys the merchant | The rail's 320px + the preview canvas now run edge-to-edge under the header, matching the Shopify reference's chrome-minimal feel, without losing auth, toasts, or the trial notice. |
| Themes page | Does **not** bleed. It is a normal padded dashboard page (`04-UI-SPEC.md`'s existing `px-4 py-8 sm:px-8` container), because it is a browsing/library surface, not the workbench — the Shopify "Online Store" list page is not full-bleed either. |

**Reason:** Research's own Pitfall 5 is decisive: Option C (a sibling route group) kills the publish toast, the D-11 trial banner, and sign-out with no compensating benefit — the merchant never actually said "I want to lose navigation," they said "put the editor on its own page," which D-A already delivers via the route split alone. Option A (status quo width) under-delivers on the user's explicit "full-screen" framing from the Shopify reference. Option B is the only one that satisfies both the literal request and every other locked contract (D-11, the publish toast, sign-out) simultaneously, and it is a one-file, reviewable change (a wrapper `div`), not an architectural fork.

The alternative (nesting under the old `storefront-editor` segment) makes the URL lie about what renders there, which this codebase's own comment-honesty convention (05.1-UI-SPEC's `template-thumbnail.tsx` precedent) already treats as a defect class. `/dashboard/storefront-editor` stops resolving; no redirect is added (see R-2a).

The key name is cosmetically stale; renaming it is an optional, single-consumer mechanical rename left to the planner's discretion, not a copy change.

### R-3 — Spotlight-card composition on the Themes page: **two-column row at ≥`md`, stacked below it; capped image width; new `sizes` value**

**Decision:** `<CurrentTemplateCard>` is not stretched full-width. On the Themes page it renders inside a **two-column row at `md`+ (image left, text+actions right)**, collapsing to a stacked single column below `md`. This is the layout the user's own Shopify "Online Store" screenshots show (current-theme row: thumbnail left, name/actions right) and it is what research's FLAG 3 named as the closer-to-reference option.

**Concrete markup shape (Themes page only — `CurrentTemplateCard` itself stays byte-identical, per R-3b):**

```tsx
// src/app/(dashboard)/dashboard/storefront/themes-browser.tsx
<div className="grid grid-cols-1 gap-6 md:grid-cols-[minmax(0,22rem)_1fr] md:items-center">
  <CurrentTemplateCard tile={spotlightTile} sizes="(min-width: 768px) 352px, 100vw" />
  <div className="flex flex-col gap-4">
    <div>
      <p className="text-sm leading-normal text-muted-foreground">{strings.editor.templateCurrentHeading}</p>
      <h2 className="font-heading text-2xl leading-tight font-semibold tracking-tight text-foreground">
        {spotlightTile.name}
      </h2>
    </div>
    <Button render={<Link href="/dashboard/storefront/editor" />} className="w-fit min-h-11">
      {strings.editor.customizeButton}
    </Button>
  </div>
</div>
```

| Detail | Contract |
|---|---|
| Grid | `grid-cols-1` (<`md`) → `md:grid-cols-[minmax(0,22rem)_1fr]` (≥`md`) — the image column is capped at `22rem` (352px), not `1fr`, so it never becomes the ~610px banner research flagged |
| `sizes` on `CurrentTemplateCard`'s image | `"(min-width: 768px) 352px, 100vw"` — replaces the rail's hardcoded `"320px"` for this one caller. Derived directly from the `22rem` cap above: at ≥768px the image is exactly as wide as its column; below 768px it's the stacked full-bleed column, capped by the page's own `max-w-5xl` container. |
| Image aspect | Unchanged — `aspect-[16/10]`, inherited from `CurrentTemplateCard`'s own markup (05.1-UI-SPEC card anatomy). At 352px wide that's a 220px-tall image — a card, not a hero. |
| Vertical alignment | `md:items-center` — the text/action column centers against the image column's height rather than top-aligning, matching the Shopify reference row |
| "Customize" button | Lives in the **Themes page's own component** (`themes-browser.tsx`), beside the card — **not inside `current-template-card.tsx`**. See R-3b. |
| Page container | `max-w-5xl` (1024px) — same width 05.1-UI-SPEC already established for the onboarding branding page and the value the grid-engine derivation table is built against |

**R-3b — `CurrentTemplateCard` gets one new optional prop, nothing else:**

```ts
// src/components/theming/current-template-card.tsx
export function CurrentTemplateCard({
  tile,
  sizes = "320px",   // NEW — optional, defaults to today's exact rail value
}: {
  readonly tile: TemplateTile;
  readonly sizes?: string;   // NEW
}): ReactElement
```

The `sizes` prop is threaded straight to the existing `<TemplateMedia>` call, replacing the hardcoded literal. **No other change to this file.** The Editor rail no longer renders this component at all (the panel moves wholesale to the Themes page — see § Layout below), so there is in fact only one active caller after this phase, but the prop stays optional/defaulted so the component's contract doesn't silently narrow.

**Reason for "beside the card, not inside it":** `current-template-card.tsx`'s own header states a **structural, grep-enforced** zero-interactive-element claim (T-05-35 mitigation from quick task 260908-bv1) — a scan bans `RadioGroupItem`/`onClick=`/`onChange=` in that file, comments included. A `<Link>` wouldn't literally trip that grep, but placing the Customize action inside the shared component breaks the *spirit* of "this card cannot fire an action," and the component is also used nowhere else that would need it. Keeping it external costs nothing and preserves the component's zero-interactive guarantee for any future caller.

### R-4 — Navigation-guard scope: **Editor→Themes link only, via `<Link onNavigate>`. Sidebar and browser-back are explicitly out of scope, logged as a follow-up.**

**Decision:** The dirty-draft guard covers exactly one transition: the rail's `Change template` row (now a `<Link href="/dashboard/storefront">`) leaving a dirty Editor. It does **not** extend to the sidebar's "Storefront" item, to any other sidebar link, or to the browser back/forward buttons.

**Mechanism — Next 16.3.1's own `<Link onNavigate>`, confirmed shipped, no custom solution:**

```tsx
// src/app/(dashboard)/dashboard/storefront/editor/section-list.tsx
// (or a small wrapping component, if the guard needs to own dialog state
//  that section-list.tsx should not — see prop-contract note below)
<Link
  href={changeTemplateHref}
  onNavigate={(e) => {
    if (!dirty) return;         // clean draft: let the navigation proceed
    e.preventDefault();         // dirty: hold, and ask
    setLeaveDialogOpen(true);
  }}
  className={/* same row-button classes the current onClick row uses */}
>
  <LayoutTemplate aria-hidden="true" className="size-4 shrink-0" />
  <span className="truncate">{strings.editor.railChangeTemplateEntry}</span>
</Link>
```

The confirm surface is the existing shadcn `AlertDialog` idiom (`publish-bar.tsx:315-339` is the template) — never `window.confirm`, which inlines prose CLAUDE.md forbids.

| Detail | Contract |
|---|---|
| `beforeunload` | Stays, unchanged (`editor-shell.tsx:413-420`). Covers real document unloads (tab close, hard reload, typed URL). |
| `onNavigate` | New. Covers this one client-side `<Link>` transition. The two guards are complementary, not redundant — neither substitutes for the other. |
| Scope boundary | Sidebar "Storefront" item, any other sidebar link, and browser back/forward remain **unguarded** — identical to today's behavior (today, clicking "Products" with a dirty editor already loses the draft silently; this phase does not fix or worsen that pre-existing gap). |
| Modifier-click / new tab | `onNavigate` fires only on same-origin client-side navigation; `Ctrl`/`Cmd`+click and external URLs skip it correctly, with no extra code needed. |
| Dialog copy | New `strings.editor` keys — see § Copywriting Contract |
| Cancel action | Closes the dialog, draft untouched, merchant stays on the Editor |
| Confirm action | Closes the dialog and completes the navigation (`router.push` to `changeTemplateHref`, or re-dispatch of the intercepted navigation) |

**Reason:** Guarding only the one transition this phase's own route split *creates* is D-B's "relocate, don't add" principle applied to risk mitigation itself — it closes the exact regression the split introduces (Pitfall 3: a round-trip that is lossless today becoming lossy) without touching `app-sidebar.tsx`, a file governed by three separate contract-test assertions in `tests/unit/dashboard-nav.test.ts`. Extending the guard to every sidebar link would fix a real but *pre-existing* bug — worth doing, but it is a scope expansion into a file this phase has no other reason to touch, and is logged below as a follow-up rather than silently rolled in.

**Follow-up (not this phase, record and move on):** a global `NavigationBlockerContext` guarding every link out of a dirty editor, including the sidebar. Out of scope per D-B and per the reasoning above.

## Page Data Contract

What each page fetches, independently — no shared client state, no context provider, no URL state (confirmed per research Focus 1(b): the "shared" fact, current template key, is a database column one server action owns; `revalidatePath` + a fresh RSC read is the entire mechanism).

### Themes page RSC

```tsx
export default async function StorefrontThemesPage() {
  const ctx = await requireMerchantContext();       // every page authorizes itself — non-negotiable
  await ensureStorefrontSeeded({});                  // NEW HERE — first-touch entry point for legacy tenants
  const editor = await getEditorStorefront(ctx.tenantId);  // only templateKey is read from this

  return (
    <ThemesBrowser
      tiles={editorTemplateTiles(ctx.plan.tier, editor.templateKey)}  // moved verbatim from the old page.tsx
      currentTemplateKey={editor.templateKey}
      canEditStorefront={ctx.canEditStorefront}       // READ gate only, never the control

  );
}
```

Does **not** fetch: `getPaymentSettings`, `activeProductCount`, `SECTION_TYPE_DATA`, `EDITABLE_THEME_FIELDS`, `THEME_MAXIMA`, `variantsForTemplate`, `env.R2_PUBLIC_BASE_URL`, or the `storefrontUrl`/`previewUrl`/`previewOrigin` triple — none of it is needed without a preview iframe.

Unchanged shape from the current `storefront-editor/page.tsx`, minus one prop:

```tsx
<EditorShell
```

### The `EditorState` hard constraint (do not violate)

`state.templateKey` has no reader after this split (its only consumer, `<ChangeTemplatePanel currentTemplateKey={state.templateKey}>`, no longer exists on this page) — **but it must stay in the reducer state.** `tests/unit/editor-reducer.test.ts:474-481` asserts the exact key set `["dirty","document","selectedSectionId","templateKey","tokens","variants"]`. The Editor page still passes `currentTemplateKey={editor.templateKey}` into `EditorShellProps` for this reason alone. Do not remove the field, the prop, or narrow the type.

### `switchTemplate`'s dual revalidation

The Themes page fires `switchTemplate`; the result must be visible on both pages:

```ts
// src/server/theming/actions.ts, switchTemplate
revalidatePath("/dashboard/storefront");         // the Current badge, on the page the merchant is on
revalidatePath("/dashboard/storefront/editor");  // fresh document/tokens/variants for when they navigate there
```

`saveDraft`, `publishStorefront`, `discardDraft` only ever fire from the Editor; each needs only `revalidatePath("/dashboard/storefront/editor")`.

## PublishBar / Save / Discard / Publish — the mapping onto two pages

**Confirmed explicitly, per research Focus 3: the Themes page gets no `PublishBar`, no Save button, no Publish button, no status pill, and needs no second commit flow.**

| Action | Lives on | Mechanism |
|---|---|---|
| `saveDraft` | Editor only | Unchanged `PublishBar` |
| `publishStorefront` | Editor only | Unchanged `PublishBar` |
| `discardDraft` | Editor only | Unchanged `PublishBar` |
| `switchTemplate` | Themes only | The existing destructive `<AlertDialog>` inside the relocated panel (now `ThemesBrowser`). **This is already the commit flow — `switchTemplate` is a self-contained, fully-committed server action** (`merchantAction({ mode: "write" })`, one transaction, explicitly leaves `published`/`publishedTokens`/`publishedTemplateKey` byte-identical). Nothing new is built for it. |

**The information regression this split creates, and how it's closed:** today, confirming a switch shows the `PublishBar`'s `Saved · not published yet` state on the *same screen*, immediately. After the split, the merchant confirms on a page with no publish bar at all. **Fix: a `sonner` success toast on the Themes page, with an action that navigates to the Editor.**

```tsx
// themes-browser.tsx, on a successful switchTemplate
toast.success(strings.editor.templateSwitchedToast, {
  action: {
    label: strings.editor.customizeButton,
    onClick: () => router.push("/dashboard/storefront/editor"),
  },
});
```

This is free — `<Toaster/>` is already mounted once in `(dashboard)/layout.tsx`, and `publish-bar.tsx`'s existing `toast.success(copy, { action })` call is the exact idiom to copy. `04-UI-SPEC.md` § "The four states" already sanctions this pattern ("a stay-on-page action gets a toast").

**`handleTemplateSwitched`'s `savedAgainstPublishedAt = publishedAt` compensation is deleted, not ported.** After the split, the switch happens on Themes and the merchant then *navigates* to a fresh Editor RSC render, where the server's own `draftUpdatedAt > publishedAt` comparison is true by construction (`switchTemplate` writes `draftUpdatedAt` and never touches `publishedAt`). The hack becomes unnecessary; porting it would be dead, misleading code.
