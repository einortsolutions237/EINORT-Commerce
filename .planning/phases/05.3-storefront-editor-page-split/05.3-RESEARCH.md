## Summary

This phase is almost entirely a **move**, not a rewrite. The load-bearing discovery is that the existing code is already partitioned along exactly the seam this phase needs to cut. `change-template-panel.tsx` has **zero relative imports** — every import is a `@/`-absolute path — so it can be dropped into a new directory with no import edits at all. `switchTemplate` is already a fully-committed persisted server write (`merchantAction({ mode: "write" })`, one transaction, its own `revalidatePath`) that shares nothing with `saveDraft`/`publishStorefront`/`discardDraft` except the entitlement gate. And `<TemplatePicker>`'s grid is already **container-query driven** (`@container` + `@lg:grid-cols-2 @4xl:grid-cols-3`, shipped by Phase 5.1 specifically because viewport breakpoints were wrong inside a 320px rail) — meaning it re-flows from 1 column to 3 in a wide page context **with no CSS change whatsoever**. The `w-80` rail width lives in `editor-shell.tsx:682`, not in the panel.

The two genuinely new things this phase must build are (1) **navigation between the pages**, and (2) a **dirty-draft guard on that navigation**. The second is the phase's one real regression risk and is not optional. Today, going from "edit sections" to "change template" is a rail push/pop — a `useState` toggle, zero navigation, draft fully preserved. After the split it becomes a client-side route change, and `beforeunload` (the existing leave guard, `editor-shell.tsx:413-420`) **does not fire on Next.js client-side navigation**. A merchant with unsaved reorders who clicks through to Themes loses them silently. Next 16.3.1 ships the exact framework-native fix: `<Link onNavigate={(e) => e.preventDefault()}>` (added in v15.3.0), documented in the bundled docs under "Blocking navigation."

Everything else falls out cleanly. The Themes page needs **three** of the Editor's current seventeen props (`templates`, `currentTemplateKey`, `canEditStorefront`) and no live-preview iframe at all — the template cards already carry real generated `.webp` previews from plan 05.1-08. The Editor page keeps everything else and **loses one prop** (`templates`). The `savedAgainstPublishedAt = publishedAt` hack in `handleTemplateSwitched` becomes unnecessary and should be deleted rather than ported: after a switch, the merchant arrives at a fresh Editor RSC render where the server's own `draftUpdatedAt > publishedAt` comparison is naturally true, because `switchTemplate` writes `draftUpdatedAt` and never touches `publishedAt`.

**Primary recommendation:** `git mv` the five editor files into `src/app/(dashboard)/dashboard/storefront/editor/` and `change-template-panel.tsx` into `src/app/(dashboard)/dashboard/storefront/`, sidebar item repoints to `/dashboard/storefront` (Themes), one `<Link onNavigate>` dirty-guard in each direction, and update the five hardcoded route strings (1 sidebar href, 3 `revalidatePath`, 1 `REQUIRED_HREFS` entry) in the same commit.

### (a) What is duplicated / fetched independently per page

Only three RSC-resolved values, and they are cheap:

| Value | Themes page | Editor page | Source |
|-------|-------------|-------------|--------|
| `ctx` (`requireMerchantContext()`) | ✓ | ✓ | Already duplicated across every dashboard page by design; `React.cache()` collapses it to one `getSession` per render pass (`(dashboard)/layout.tsx:33-38`). |
| `ensureStorefrontSeeded({})` | ✓ **must be added** | ✓ (already there) | **Easy to miss.** Today only the editor page calls it. If Themes becomes the landing destination for the "Storefront" nav item, a pre-Phase-4 organization can reach the switch button *before* ever opening the Editor — and `switchTemplate` throws `StorefrontNotSeededError` (`actions.ts:482`) on an unseeded row. The call is an idempotent `upsert` with an empty `update` on both halves; adding it to the Themes page costs one round trip and closes the hole. |
| `getEditorStorefront(ctx.tenantId)` | ✓ (for `templateKey` only) | ✓ (for everything) | Reusing the existing, tested query on the Themes page is preferable to writing a narrower one: a new query is a new untested surface. It over-reads two JSON columns; that is the correct trade. |

The Themes page additionally calls `editorTemplateTiles(ctx.plan.tier, editor.templateKey)` — the function **moves** from the Editor page's module to the Themes page's module unchanged (`page.tsx:178-217`). The Editor page no longer calls it. It has no other caller. `[VERIFIED: grep — `editorTemplateTiles` appears only in `storefront-editor/page.tsx`]`

The Themes page does **not** need: `getPaymentSettings`, `activeProductCount`, `SECTION_TYPE_DATA`, `EDITABLE_THEME_FIELDS`, `THEME_MAXIMA`, `variantsForTemplate`, `env.R2_PUBLIC_BASE_URL`, or the `storefrontUrl`/`previewUrl`/`previewOrigin` triple.

### (b) What is genuinely shared and needs a different mechanism

**Answer: nothing needs a shared client mechanism. No context provider, no URL state, no store.**

The one thing that *looks* shared is "which template is current," and it is already handled server-side. `switchTemplate` is a committed persisted write followed by `revalidatePath`, and the Next 16 docs are explicit: *"Server Functions: Updates the UI immediately (if viewing the affected path)."* `[CITED: node_modules/next/dist/docs/01-app/03-api-reference/04-functions/revalidatePath.md]` So the `Current` badge moves to the new template on the Themes page the merchant is standing on, and the Editor page — when navigated to — re-renders from the server with the new `templateKey`, `document`, `tokens`, and `variants`. Zero client plumbing.

**Does the Themes page need the live-preview iframe? No.** Definitively:

- The whole point of the iframe is *this merchant's unsaved draft* — the postMessage payload is `{document, tokens, variants}` from the reducer (`editor-shell.tsx:370-388`). The Themes page has no reducer and no draft.
- The template cards already carry **real generated preview imagery**: `previewUrl: TEMPLATE_PREVIEWS[key] ? publicUrlFor(\`${templatePreviewPrefixFor(key)}/card.webp\`) : null` (`page.tsx:201-203`), produced by `npm run templates:previews` (plan 05.1-08), rendered through `<TemplateMedia>` with the `<TemplateThumbnail>` wireframe as the D-05 fallback.
- 05.1-UI-SPEC § "No per-card secondary button" already ruled that a per-card preview affordance "would require a lightbox or a new route, both out of this phase's boundary." That ruling still holds and this phase must not reverse it.

Carrying the iframe to the Themes page would also drag `previewUrl`, `previewOrigin`, the handshake, the 10s deadline, and the origin check onto a page that has nothing to post. Don't.

### The `savedAgainstPublishedAt` simplification (worth its own paragraph)

`handleTemplateSwitched` currently calls `setSavedAgainstPublishedAt(publishedAt)`, and `editor-shell.tsx:530-541` spends a paragraph explaining why: `switchTemplate` had just persisted a new draft write *while the merchant stayed on the page*, so the RSC's `draftUpdatedAt` prop was stale and `draftUpdatedAt > publishedAt` could under-report "unpublished" as false.

**After the split, that staleness window closes.** The switch happens on the Themes page; the merchant then *navigates* to the Editor, which is a fresh RSC render reading `getEditorStorefront` after `switchTemplate` wrote `draftUpdatedAt` (`actions.ts:513`) and deliberately left `publishedAt` byte-identical (`actions.ts:503-510`). The server comparison `draftUpdatedAt > publishedAt` is therefore true **by construction**. The hack becomes not just unnecessary but misleading, and the correct action is to delete it along with its caller — provided `switchTemplate` revalidates the Editor path (Focus 3).

`savedAgainstPublishedAt` itself stays, because `onSaved`/`onDiscarded` in `PublishBar` still use it (`editor-shell.tsx:665-672`).

## Focus 2 — Route Structure (RESOLVED)

### Recommendation

| Page | URL | File |
|------|-----|------|
| **Themes** | `/dashboard/storefront` | `src/app/(dashboard)/dashboard/storefront/page.tsx` |
| **Editor** | `/dashboard/storefront/editor` | `src/app/(dashboard)/dashboard/storefront/editor/page.tsx` |

**Both get new paths; `src/app/(dashboard)/dashboard/storefront-editor/` is removed.**

### Why this, and not the zero-edit alternative

The tempting alternative is to keep the existing directory and nest: `/dashboard/storefront-editor` becomes Themes, `/dashboard/storefront-editor/editor` becomes the Editor. That requires **no** sidebar edit, **no** `REQUIRED_HREFS` edit, and only reroutes the `revalidatePath` strings. It was seriously considered and rejected for two reasons:

1. **It makes the route name lie.** A URL segment called `storefront-editor` that renders a theme *library* is the same class of defect this codebase's comment convention exists to prevent — and this repo has a demonstrated intolerance for it (05.1-UI-SPEC forced an update to `template-thumbnail.tsx`'s header rather than leave a comment contradicting shipped behaviour).
2. **`/dashboard/storefront-editor/editor` is not a URL anyone would defend in review.**

The proposed structure is a direct parallel to Shopify's own `Online Store` → `Themes` → `Customize`, which is the reference the user supplied.

### App Router conventions confirmed against this codebase

- **Route group:** both pages stay inside the existing `(dashboard)` group. It adds no URL segment `[CITED: node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/route-groups.md]`, and — critically — `(dashboard)/layout.tsx` is **not** a root layout (`src/app/layout.tsx` is), so this is a normal nested layout. The docs' "full page load between route groups" caveat applies **only** to multiple root layouts and does not apply here.
- **kebab-case segments:** `storefront`, `editor` — both clean, matching `settings/payment`, `storefront-editor`, `s/[slug]/order/[token]`.
- **Colocated client components:** the existing directory already colocates non-route `.tsx` files beside `page.tsx` (`editor-shell.tsx`, `section-list.tsx`, …). App Router permits this; `page.tsx` / `layout.tsx` / `loading.tsx` are the only reserved names. Preserve the pattern.
- **`loading.tsx`:** the existing one (`storefront-editor/loading.tsx`, 51 lines) moves with the Editor. The Themes page needs its own — a skeleton shaped like the spotlight card + grid, per 04-UI-SPEC § "The four states" ("Server-rendered routes get a `loading.tsx` `skeleton` matching the final shape… No full-page spinners anywhere.").

### Proposed directory layout

```
src/app/(dashboard)/dashboard/storefront/
├── page.tsx                    # Themes — RSC. requireMerchantContext, ensureStorefrontSeeded,
│                               #   getEditorStorefront, editorTemplateTiles (moved verbatim)
├── loading.tsx                 # NEW — spotlight-card + grid skeleton
├── themes-browser.tsx          # ← git mv change-template-panel.tsx, adapted (Focus 6)

    ├── page.tsx                # ← git mv storefront-editor/page.tsx, minus editorTemplateTiles
    ├── loading.tsx             # ← git mv storefront-editor/loading.tsx (unchanged)
    ├── editor-shell.tsx        # ← git mv, minus the changeTemplate branch
    ├── section-list.tsx        # ← git mv, changeTemplate row becomes a link
    ├── settings-panel.tsx      # ← git mv, byte-identical
    ├── field-renderer.tsx      # ← git mv, byte-identical

```

**Should there be a `storefront/layout.tsx`?** **No.** The two pages share no chrome that isn't already in `(dashboard)/layout.tsx`, and adding one would only create a second place a future reader has to check for the auth boundary — which `(dashboard)/layout.tsx`'s header explicitly warns against (lines 22-44: a Next 16 layout "does not control whether its child segments render… a session check placed here is a check that sometimes does not happen"). Every page authorizes itself; keep it that way.

## Focus 3 — Publish / Save / Discard Placement (RESOLVED)

### `switchTemplate` is definitively a separate, self-committing action

Read from source, not assumed:

| Property | Evidence |
|----------|----------|
| Separate server action | `export const switchTemplate = merchantAction<…>({ mode: "write", schema: switchTemplateSchema, … })` — `src/server/theming/actions.ts:444-537`. Distinct from `saveDraft` (:128), `publishStorefront` (:209), `discardDraft` (:317). |
| **Commits immediately** | `db.$transaction` writing `storefrontPage.update({ data: { draft, draftUpdatedAt } })` and `storefrontTheme.update({ data: { draftTokens, draftTemplateKey } })` — `actions.ts:466-521`. There is no staging step. |
| **Does not publish** | `actions.ts:503-510`, in all-caps: *"`published`, `publishedTokens` AND `publishedTemplateKey` ARE LEFT BYTE-IDENTICAL. Writing `publishedTemplateKey` here would be a SILENT PUBLISH, and it is the single most important thing this action must not do."* |
| Its own tier gate | `assertCanEditStorefront` then `assertTemplateAccess(ctx, templateKey, …)` — `actions.ts:452,460`, both before any DB touch. |
| Its own confirm step already exists | `ChangeTemplatePanel`'s destructive `AlertDialog` (`change-template-panel.tsx:268-305`). |

### Answer: the Themes page gets **no** PublishBar, and needs no second commit flow

`change-template-panel.tsx:56-66` already states the rule in its own header, and it survives the split intact:

> *"THIS PANEL ADDS NO SAVE BUTTON, NO PUBLISH BUTTON AND NO STATUS PILL. `switchTemplate` is a completed persisted write… there is nothing left here to save. Rendering this panel's own 'changes not yet saved' status pill for something already saved would be the misleading draft/live signal the editor's whole design exists to prevent."*

The existing destructive `AlertDialog` **is** the confirm flow. It moves with the component. Nothing new is built.

### ⚠️ But the split destroys a real signal — and this must be replaced

Today, when a merchant confirms a switch, the `PublishBar` is **on the same screen**, and it immediately flips to `Saved · not published yet` (that is precisely what `handleTemplateSwitched`'s `setSavedAgainstPublishedAt(publishedAt)` forces). The merchant learns, without being told, that a further Publish is required.

After the split the merchant confirms a switch on a page with **no publish bar at all**, and the store is now in a saved-but-unpublished state with nothing on screen saying so. That is an information regression, not a layout change, and D-B ("preserve exactly, just relocate") requires it be addressed.

**Recommendation (minimal, no new capability):** on a successful switch, the Themes page shows a `sonner` success toast whose action navigates to the Editor page to publish. This is free: `<Toaster />` is already mounted once in `(dashboard)/layout.tsx:156` for the whole dashboard shell, and `publish-bar.tsx:184-191` already establishes the exact idiom (`toast.success(copy, { action: { label, onClick } })`). Copy goes in `strings.editor`. 04-UI-SPEC § "The four states" sanctions this: *"A stay-on-page action gets a toast (publish)."*

An inline non-destructive `<Alert>` on the Themes page is the alternative if the UI-SPEC prefers persistence over transience. **Flagged for the UI-SPEC to choose; either is in scope, silence is not.**

### `revalidatePath` after the split — the one non-obvious edit

`switchTemplate` currently revalidates one path. After the split it fires from Themes and its result must be visible on **both** pages:

```ts
// switchTemplate
revalidatePath("/dashboard/storefront");         // the Current badge, on the page the merchant is on
revalidatePath("/dashboard/storefront/editor");  // the new document/tokens/variants, for when they navigate
```

`saveDraft`, `publishStorefront` and `discardDraft` only ever fire from the Editor and only need `revalidatePath("/dashboard/storefront/editor")`.

A `revalidatePath("/dashboard/storefront", "layout")` would cover both in one call `[CITED: revalidatePath.md — "Layouts: Invalidates the layout… all nested layouts beneath it, and all pages beneath them"]`, but since this phase deliberately adds no `layout.tsx` at that segment (Focus 2), two explicit literal calls are the honest spelling. Prefer them.

### `switchTemplate`'s return payload becomes unused — leave it alone

`SwitchTemplateData` returns `{document, tokens, variants, templateKey, draftUpdatedAt}` specifically so the *open editor* could repaint without a reload (`actions.ts:429-434`). On the Themes page there is no editor to repaint, so the Themes client will call `switchTemplate` and use only `result.ok`.

**Do not delete the payload or narrow the type.** `tests/isolation/template-switch.test.ts` asserts on it, and a future phase may put a preview back on this surface. Note the now-unused fields in the calling component's comment instead of amputating a tested server contract.

### ⚠️⚠️ THE CRITICAL ONE: `beforeunload` does not fire on client-side navigation

This is the single biggest correctness risk in the phase and it is **not optional to address**.

`editor-shell.tsx:413-420` installs a `beforeunload` guard while `state.dirty` is true. `beforeunload` fires on real document unloads: closing the tab, a hard reload, typing a new URL. It **does not fire** when Next.js performs a client-side transition via `<Link>` or `router.push()`.

Today this is a latent, low-frequency bug (clicking "Products" in the sidebar with a dirty editor already loses the draft silently). After the split it becomes a **routine, high-frequency data-loss path**: Editor → Themes is now a real navigation, and it is a round trip a merchant makes constantly. Today that exact interaction is a `useState` push/pop that preserves the draft perfectly. Shipping the split without a guard is a straight regression against D-B's "preserve exactly."

**The fix is framework-native and shipped in this exact Next version.** `<Link onNavigate>` was added in Next v15.3.0; this project runs **16.3.1**. The handler receives an event with `preventDefault()`, and the bundled docs carry a "Blocking navigation" section demonstrating precisely the unsaved-changes case. `[VERIFIED: node_modules/next/dist/docs/01-app/03-api-reference/02-components/link.md:453-503, 1090-1260; version confirmed via \`require('next/package.json').version\` → 16.3.1]`

```tsx
<Link
  href="/dashboard/storefront"
  onNavigate={(e) => {
    if (!dirty) return;
    e.preventDefault();
    setLeaveDialogOpen(true);   // shadcn AlertDialog — NOT window.confirm
  }}
>
```

**Do not copy the docs' `window.confirm(...)` example.** It inlines user-facing prose, which CLAUDE.md forbids and which the codebase's contract tests are built to catch. Use the `AlertDialog` pattern already established at `publish-bar.tsx:315-339`, with copy in `strings.editor`.

Behavioural notes worth putting in the plan:
- `onNavigate` fires **only** on same-origin client-side navigation. `Ctrl`/`Cmd`+click (new tab) and external URLs deliberately skip it — correct, since neither unloads the current document. `[CITED: link.md:499-503]`
- The `beforeunload` guard stays. The two are complementary, not redundant.
- **Scope decision for the UI-SPEC:** guard only the Editor→Themes link (minimal, in-scope), or guard *every* link out of a dirty editor including the sidebar (the docs' React-Context `NavigationBlockerContext` pattern)? The latter fixes a pre-existing bug but touches `app-sidebar.tsx`, a file governed by three contract-test assertions. **Recommend the minimal scope for this phase**, and log the sidebar case as a follow-up. Flagged below.

### Pattern 1: Server-driven cross-page consistency, not client state lifting

**What:** When two routes need to agree on a fact that a server action owns, let the server action own it. `revalidatePath` + a fresh RSC read replaces any shared store.
**When to use:** Whenever the "shared" value is a persisted column (here: `draftTemplateKey`, `draftUpdatedAt`).
**Why it matters here:** it removes the entire temptation to build a `TemplateContext` provider in `(dashboard)/layout.tsx`, which would put per-tenant client state above every unrelated dashboard route.

```ts
// Source: src/server/theming/actions.ts:523-526 (existing pattern, path strings updated)
// "Same reason publishStorefront/discardDraft revalidate: the publish bar and
//  the editor's own preview state must not go stale until a hard reload."
revalidatePath("/dashboard/storefront");
revalidatePath("/dashboard/storefront/editor");
```

### Pattern 2: `onNavigate` as the SPA half of a two-part leave guard

**What:** `beforeunload` covers document unloads; `onNavigate` covers client-side transitions. Neither substitutes for the other.
**When to use:** Any route holding unsaved client state that a `<Link>` can leave.

```tsx
// Source: node_modules/next/dist/docs/01-app/03-api-reference/02-components/link.md
//         §"Blocking navigation" — adapted to this repo's AlertDialog + strings rules
<Link
  href={changeTemplateHref}
  onNavigate={(e) => {
    if (!dirty) return;
    e.preventDefault();
    setLeaveDialogOpen(true);
  }}
>
```

### Pattern 3: Container queries survive relocation; viewport breakpoints do not

**What:** A component sized with `@container`/`@lg:`/`@4xl:` is portable across container widths by construction.
**Why it matters:** it is the reason `<TemplatePicker>` needs no work in this phase, and the reason `tests/unit/template-picker-contract.test.ts` bans the viewport spelling.

### Anti-patterns to avoid

- **Lifting editor state into a shared provider or into the URL.** `editor-shell.tsx:44-54` states the rule the codebase enforces: *"There is one `useReducer`, no second reducer, no `patch()` updater and no inline setter that touches the document."* Nothing about splitting a route changes that.
- **Recreating the "Change template" panel on the Themes page instead of moving it.** Two hand-copied trees is exactly what quick task 260908-bv1 extracted `TemplateMedia` to prevent.
- **Adding a viewport breakpoint to `template-picker.tsx` to "widen" the grid.** Build failure, by design.
- **Adding a `layout.tsx` at `storefront/` "for shared chrome."** There is no shared chrome, and it invites a future reader to put the auth check there.
- **`window.confirm` for the unsaved-changes dialog**, even though the Next docs show it. Inlined prose; CLAUDE.md forbids it.
- **Removing `templateKey` from `EditorState` because it has no reader.** Breaks `editor-reducer.test.ts:474-481`.
- **Deleting or narrowing `SwitchTemplateData`.** Covered by `tests/isolation/template-switch.test.ts`.

## Common Pitfalls

### Pitfall 1: The dead `revalidatePath` (highest probability of shipping)
**What goes wrong:** One or more of the three `revalidatePath("/dashboard/storefront-editor")` calls in `src/server/theming/actions.ts` (lines 286, 406, 526) is left pointing at a route that no longer exists.
**Why it happens:** Next does not warn on revalidating a nonexistent path, no test asserts the argument, and the action still returns `{ ok: true }`. The failure is a stale status pill, not an exception.
**How to avoid:** Grep gate in the plan's verification block: `grep -rn "storefront-editor" src/ tests/` must return **zero** functional hits after the move.
**Warning signs:** Publish succeeds but the pill still reads "Saved · not published yet"; a template switch appears not to take effect after navigating to the Editor.

### Pitfall 2: `switchTemplate` revalidating only one path
**What goes wrong:** It fires from Themes and revalidates only `/dashboard/storefront`; the Editor keeps serving a cached RSC payload of the previous template.
**Why it happens:** The mechanical rename maps one old string to one new string. This action needs **two**.
**How to avoid:** Explicit dual `revalidatePath` (Focus 3). Verify manually: switch on Themes → Customize → the Editor's section list must show the new template's sections.
**Warning signs:** The rail shows the old template's five sections after a switch.

### Pitfall 3: Silent draft loss on Editor → Themes navigation
**What goes wrong:** `beforeunload` doesn't fire on SPA transitions; a dirty draft is discarded with no prompt.
**Why it happens:** The existing guard was written for a single-route surface where this transition was a `useState` toggle.
**How to avoid:** `<Link onNavigate>` guard (Focus 4). **Treat as required, not nice-to-have.**
**Warning signs:** Reorder a section, click "Change template," come back — the order is reset.

### Pitfall 4: `ensureStorefrontSeeded` missing from the new landing page
**What goes wrong:** A pre-Phase-4 organization reaches the Themes page first and `switchTemplate` throws `StorefrontNotSeededError` — uncaught, because `merchantAction` only converts `ReadOnlyError`/`EntitlementError`.
**Why it happens:** The seed call currently lives on the only editor route; the split creates a second entry point.
**How to avoid:** Call it on **both** pages. Ignore the result on both, for the reason `storefront-editor/page.tsx:63-66` gives.
**Warning signs:** Only reproducible against a legacy tenant — invisible in a fresh seed.

### Pitfall 5: Moving the Editor out of `(dashboard)` to get "true full-screen"
**What goes wrong:** `<Toaster />` is mounted exactly once, in `(dashboard)/layout.tsx:156`. Outside that subtree, `publish-bar.tsx`'s `toast.success(strings.editor.publishedToast, { action: … })` renders nothing. The merchant publishes and receives **zero** confirmation. `TrialBanner` (D-11: "Above the content on every dashboard route") and sign-out also disappear.
**Why it happens:** The Shopify reference *is* chrome-free, so "full-screen" reads as "outside the shell."
**How to avoid:** Keep both pages inside `(dashboard)`. See the flag below for the acceptable full-bleed options.
**Warning signs:** Nothing fails; the toast simply never appears.

### Pitfall 6: Adding a viewport breakpoint to the picker grid
**What goes wrong:** `tests/unit/template-picker-contract.test.ts` (`VIEWPORT_GRID_BREAKPOINT`, :106) fails the build.
**Why it happens:** "The grid needs to be wider on the new page" is a natural but wrong instinct.
**How to avoid:** Change nothing in `template-picker.tsx`. Container queries already do it.

### Pitfall 7: A blurry spotlight card
**What goes wrong:** `sizes="320px"` (`current-template-card.tsx:47`) is inherited into a much wider layout; `next/image` picks an undersized source.
**Why it happens:** It is a hardcoded literal in a shared component, invisible from the calling page.
**How to avoid:** Optional `sizes` prop defaulting to today's value (Focus 6).
**Warning signs:** The one card the merchant looks at hardest is the softest image on the page.

### Pitfall 8: Header comments that describe a rail that no longer exists
**What goes wrong:** `editor-shell.tsx`'s and `section-list.tsx`'s headers still describe the `changeTemplate` push/pop; `queries.ts:179` and `strings/index.ts:1556` still name the dead route.
**Why it happens:** Comments aren't compiled.
**How to avoid:** Treat them as part of the diff. In this codebase a comment contradicting shipped behaviour is a defect — 05.1-UI-SPEC forced exactly this fix on `template-thumbnail.tsx`.

### Pitfall 9: Stale `.next/types` after renaming route folders
**What goes wrong:** `npm run typecheck` reports `Cannot find name 'PageProps'/'LayoutProps'` against files that are fine.
**Why it happens:** Next generates those type unions from the route tree at build time; they are gitignored.
**How to avoid:** Run `npm run build` before trusting `npm run typecheck`. Documented from experience in quick task 260908-bv1's SUMMARY.

### Pitfall 10: `--max-warnings=0` on a leftover import
**What goes wrong:** `npm run lint` fails on the unused `ChangeTemplatePanel` / `TemplateSwitchedState` / `TemplateTile` imports in `editor-shell.tsx` after the branch is removed.
**How to avoid:** Remove imports in the same edit as the JSX. Note `TemplateTile` (`editor-shell.tsx:17`) is imported only for the `templates` prop type and must go with it.

## ⚠️ Flagged for the UI-SPEC / User — beyond research's authority

Four items are genuinely consequential and are **not** silently decided here.

### FLAG 1 — What "full-screen Editor page" actually means

CONTEXT.md D-A says "full-screen Editor page," and the Shopify reference is genuinely chrome-free. But `(dashboard)/layout.tsx:121` wraps every page's children in `<div className="flex flex-1 flex-col gap-6 px-4 py-8 sm:px-8">`, with a `TrialBanner` above and a `min-h-14` header band above that. The editor today is **not** full-screen; 04-UI-SPEC § Layout only promises "full editor width (not `max-w-5xl`)."

Three options, in ascending risk:

| Option | What it means | Risk |
|--------|---------------|------|
| **A. Status quo width** (recommended default) | Editor fills the dashboard inset, keeps the layout's padding | Zero. Matches 04-UI-SPEC exactly. |
| **B. Full-bleed within the shell** | Editor page opts out of the layout padding with a local negative-margin bleed (`-mx-4 -my-8 sm:-mx-8`) | Low, contained to one file. Sidebar, header, banner, Toaster all retained. |
| **C. Genuinely chrome-free** | Editor moves to a sibling route group (e.g. `(editor)/`) with its own minimal layout, dropping the sidebar/header/banner | **High.** Kills the publish toast (Pitfall 5), removes D-11's per-route trial banner, removes sign-out and all navigation. Would need a custom exit control and a re-mounted `<Toaster/>`. Materially changes what the merchant can do from the page — arguably outside D-B. |

**Research recommends B.** **C requires user confirmation** — it removes shipped, spec'd chrome (D-11 trial banner) and is a bigger change than "layout/structure only" plainly implies.

### FLAG 2 — Losing the old URL

`/dashboard/storefront-editor` stops resolving. There are no external inbound links (dashboard is session-gated, apex-only, and `robots`-irrelevant), and the product is pre-launch, so the practical cost is a pilot merchant's bookmark. The alternative — keeping the old segment as the Themes page — buys bookmark compatibility at the cost of a lying route name (Focus 2). **Recommend accepting the break; confirm.** A `redirects()` entry in `next.config.ts` is available if the user wants belt-and-braces.

### FLAG 3 — Spotlight-card layout on a full-width page

`<CurrentTemplateCard>` was designed for a 320px rail. Unconstrained on a ~976px page it becomes a ~610px-tall banner. Whether it becomes (a) a width-capped card, (b) a two-column row with the Customize button and metadata beside the image, or (c) something else is a **visual composition decision for the UI-SPEC**, informed by the user's Shopify "Online Store" screenshots (which show a wide current-theme row with the preview thumbnail on the left and actions on the right). Research will not pick one.

### FLAG 4 — Scope of the navigation guard

Guarding only the Editor→Themes link is the minimal, in-scope fix and closes the regression this phase creates. Guarding *every* link out of a dirty editor (including the sidebar, via the `NavigationBlockerContext` pattern in the Next docs) additionally fixes a **pre-existing** silent-data-loss bug — but touches `src/components/app-sidebar.tsx`, a file governed by three contract-test assertions in `tests/unit/dashboard-nav.test.ts`, and is arguably a new capability rather than a relocation. **Recommend minimal scope now, log the sidebar case as a follow-up todo.** Confirm.

| Pattern | STRIDE | Mitigation, already in place |
|---------|--------|------------------------------|
