## Read This First — Why This PATTERNS.md Looks Different

Per RESEARCH.md's own summary: *"This phase is almost entirely a move, not a rewrite."* Every file below except the two new ones (`storefront/page.tsx` Themes RSC, `storefront/loading.tsx`) already exists in the codebase in near-final form; the work is `git mv` plus a bounded, named edit. Where that is true, the "analog" is the pre-move file itself and the pattern excerpt is the delta, not a foreign template. I have also identified secondary analogs elsewhere in the codebase for the two genuinely new files and for anyone who wants a second reference point.

**No direct precedent exists in this codebase for "split one single-route CRUD-ish surface into a list/browse page + a dedicated full-screen workbench page that share zero client state and communicate only through `revalidatePath`."** The closest structural precedents are `products/page.tsx` → `products/[id]/page.tsx` and `orders/page.tsx` → `orders/[id]/page.tsx` (list page + dynamic detail page, RSC-per-route, no shared client state) — but those are list+detail with a dynamic `[id]` segment, not two static sibling routes over one resource. This is flagged explicitly below rather than papered over.

## Shared Patterns

### 1. Every page authorizes itself — `requireMerchantContext()` as first statement
**Source:** `src/app/(dashboard)/dashboard/storefront-editor/page.tsx:220`, `src/app/(dashboard)/dashboard/settings/payment/page.tsx:65`
**Apply to:** Both new `page.tsx` files (Themes and Editor). Never inherited from `(dashboard)/layout.tsx` — that layout's own header states it is not the authorization boundary.
```tsx
const ctx = await requireMerchantContext();
```

### 2. `AlertDialog` for every destructive/blocking confirm — never `window.confirm`
**Source:** `src/app/(dashboard)/dashboard/storefront-editor/publish-bar.tsx:315-339` (discard), already-moving `change-template-panel.tsx:268-305` (switch template)
**Apply to:** The new leave-editor dialog (`section-list.tsx`/`editor-shell.tsx`, R-4). CLAUDE.md forbids inline user-facing prose; `window.confirm` (the pattern Next's own docs demonstrate for `onNavigate`) is explicitly banned by RESEARCH.md's Anti-patterns section for this exact reason.

### 3. `toast.success(copy, { action: { label, onClick } })` for a stay-on-page confirmation
**Source:** `src/app/(dashboard)/dashboard/storefront-editor/publish-bar.tsx:184-191`
**Apply to:** `themes-browser.tsx`'s post-switch toast. `<Toaster/>` is already mounted once in `(dashboard)/layout.tsx:156` — do not remount it, do not build a new status-bar component (UI-SPEC § U-6 explicitly rejects a new PublishBar-like surface on Themes).

### 4. `refusalMessage(error, fallback)` helper — prefer the server's own sentence
**Source:** `src/app/(dashboard)/dashboard/storefront-editor/publish-bar.tsx:130-138` (and its accepted duplicate in `change-template-panel.tsx:126-134`)
**Apply to:** No new copy needed — `themes-browser.tsx` keeps its existing copy of this helper unchanged. Flagged here only so the planner does not "clean up" the duplication as unrequested scope.

### 5. `<Link onNavigate={(e) => e.preventDefault()}>` for SPA-transition dirty guards
**Source:** Not yet in this codebase — new for this phase, sourced from `node_modules/next/dist/docs/01-app/03-api-reference/02-components/link.md` §"Blocking navigation", adapted per UI-SPEC § R-4's exact code block.
**Apply to:** The `Change template` row in `section-list.tsx` only (guard scope is deliberately minimal — sidebar/back-button stay unguarded, logged as a follow-up per U-4).

### 6. Server-owned cross-page consistency via `revalidatePath` — never client state lifting
**Source:** `src/server/theming/actions.ts:283-286` (existing single-path precedent), extended to dual-path per UI-SPEC § "`switchTemplate`'s dual revalidation"
**Apply to:** `switchTemplate` only needs the new dual call; `saveDraft`/`publishStorefront`/`discardDraft` each need one updated path. No React Context, no `?template=` param, no `sessionStorage` — the "shared" fact is a database column one server action owns.

### 7. Header-comment convention — all-caps lead-ins citing decision IDs
**Source:** Every file in `src/app/(dashboard)/dashboard/storefront-editor/**` (e.g. `editor-shell.tsx:40-61`, `page.tsx:33-94`, `section-list.tsx:20-71`)
**Apply to:** Every moved/new file's header must be **rewritten to match new shipped behavior**, not carried verbatim. A comment describing behavior that no longer exists (e.g. the `changeTemplate` rail push/pop) is treated as a defect in this codebase (Pitfall 8, the `template-thumbnail.tsx` precedent cited throughout RESEARCH.md).
