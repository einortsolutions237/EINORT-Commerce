## Phase Goal

ROADMAP `**Goal:**` for Phase 6, verbatim: *A merchant can run their business day-to-day from a dashboard that surfaces what needs attention, and the platform owner can operate and support the pilot fleet of stores from a pilot-scoped Super Admin surface — including a direct messaging channel to every merchant and the ability to verify their subscription payments through it.*

**This plan's vertical slice:** the owner can take a store offline and put it back, with the merchant told why in the channel they already read. ADM-01 complete.

<objective>
Build the first and only writer of `Organization.status`, its source-scanning guard, and the symmetric suspend/restore UI mounted at both entry points.

Purpose: `Organization.status` has been NOT NULL with a default since Phase 1 and its schema comment says "suspension is a Phase 6 admin-only write". This is that write. Three things make it more than a column flip: the Redis hostname cache must be invalidated or a suspended storefront keeps serving until TTL (06-PATTERNS.md R-3, verified); the reason has nowhere durable to live except the merchant's thread, which is why D-15's system message **is** the audit record; and without a source-scanning guard the second writer arrives in Phase 7 and nothing notices.
Output: the writer, the guard, the isolation test, the dialog, and both mount points.
</objective>

**`invalidateTenantHost` is confirmed**, not assumed: `src/server/tenant/cache.ts` exports `invalidateTenantHost(...slugs: string[]): Promise<void>`. It must be called in the same code path as the status flip, **after** the transaction commits. `src/server/tenant/resolve.ts` caches slug→tenant resolution in Redis and fails closed on anything non-active, but a stale **positive** entry keeps a just-suspended storefront online until the TTL expires.

**D-16 — no read-only dashboard mode.** `src/server/merchant/context.ts` already redirects to `/suspended` when the organization's status is not `active`, and `src/app/suspended/page.tsx` already exists. Both are unchanged by this plan. The isolation test asserts the existing behaviour rather than building new behaviour.

**D-17 — symmetric by construction.** One function, one target status parameter, so "suspend" and "un-suspend" cannot drift into two half-matching code paths. One dialog component, mounted twice (R-2: once in the merchants-list row `dropdown-menu`, once on the detail page's `Store status` card), calling one action.

**R-2 / § Copywriting Contract — the two dialogs differ in register, not in mechanism.** Suspend requires a reason of **10–280 characters** with a live counter and a **destructive** confirm. Restore takes an **optional** note of ≤280 characters and a **primary** confirm — restoring is a safe action and colouring it red teaches the wrong reflex.

**No `AdminAuditEvent` model.** `Organization` has no audit table and ADM-04 keeps the scope pilot-sized. The `SYSTEM` message in the merchant's thread is the audit record — a genuine benefit of D-15 rather than a side effect, and worth stating in the module header (06-RESEARCH.md Pattern 5, Assumption A6).

**Copy** comes from `strings.admin.suspend`, `strings.admin.restore`, `strings.support.system` (plan 06-02). This plan authors none.
