## Phase Goal

ROADMAP `**Goal:**` for Phase 6, verbatim: *A merchant can run their business day-to-day from a dashboard that surfaces what needs attention, and the platform owner can operate and support the pilot fleet of stores from a pilot-scoped Super Admin surface — including a direct messaging channel to every merchant and the ability to verify their subscription payments through it.*

**This plan's vertical slice:** a merchant can pay their subscription by manual transfer and send the proof. Plan 06-16 gives the owner the decision surface.

<!-- Resolved decisions this plan executes against. -->

**R-3 — the form lives on `/dashboard/plan`, and the thread carries the receipt.** SUB-03 says the claim runs *through* the thread, and it does: the submission, the decision, and the audit trail all land there as `SYSTEM` messages carrying `subscriptionClaimId`, and the thread renders the claim inline. What this design does **not** do is put a payment form inside a chat transcript, where a half-typed reference competes with a conversation and the merchant has no plan or price context. `/dashboard/plan` is where a merchant already goes to think about paying.

**There is no second submit form inside the thread.** Plan 06-09 already renders one inline secondary link in the composer area when the subscription is unpaid or the trial has expired, pointing here.

**Global reference uniqueness (plan 06-03, Assumption A1).** `SubscriptionPaymentClaim.referenceNormalized` is `@unique` across all tenants, because the payee is one platform account, so the same reference twice is the same payment twice whoever sent it. A cross-tenant duplicate surfaces as a Prisma `P2002`, which is technically an existence oracle. **Refuse it with one generic message that never names the other tenant** — the same posture `src/server/claims/actions.ts` takes for cross-tenant claim ids. The message is the Phase 3 string reused verbatim: `This reference has already been used. Check your confirmation SMS and enter the exact reference.`

**Reuse, do not rewrite:** `normalizeReference()` from `src/server/claims/reference.ts` (pure, unit-tested, no tenant coupling), `ClaimStatus` and `PaymentOperator` from `src/server/db/enums.ts`, `formatXaf` from `src/server/payments/whatsapp.ts`, and the receipt upload door plan 06-11 built (`requestThreadAttachmentUpload` with kind `"subscriptions"`, then `thread-finalize`).

**`coversThrough` is not set at submit.** Plan 06-16's confirm computes and writes it. The card renders `—` while unreviewed.

**Copy** comes from `strings.plan.subscriptionClaim` and `strings.support.system` (plan 06-02). This plan authors none.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → `submitSubscriptionPayment` | A public endpoint that mints a financial claim row |
| client-supplied amount → what the platform believes was paid | Money must never be trusted from the client |
| a globally-unique reference → an existence oracle | A specific refusal reveals that another tenant used the reference |
| an expired-trial merchant → the ability to pay | An over-tight write gate would lock a paying customer out of paying |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-75 | Tampering | a client-supplied subscription amount | mitigate | The Zod schema has no amount field; the server resolves the price from the plan registry for the snapshotted tier, the same posture `placeOrder` takes for cart prices |
| T-06-76 | Information Disclosure | the `P2002` refusal on a cross-tenant duplicate reference | mitigate | One generic refusal message, byte-identical between the same-tenant and cross-tenant cases, asserted by deep equality in `tests/isolation/subscription-claims.test.ts` |
| T-06-77 | Tampering | replaying a reference to extend a subscription twice | mitigate | `referenceNormalized` is globally `@unique` at the database level, and `normalizeReference()` collapses case and whitespace variants before the insert |
| T-06-78 | Denial of Service | an expired-trial merchant unable to submit payment | mitigate | The `merchantAction` mode is chosen deliberately and documented; a `"write"` gate would refuse exactly the merchant who needs to pay |
| T-06-79 | Tampering | a client-supplied `receiptUploadKey` pointing at another tenant's object | mitigate | The key is validated server-side against the derivative-prefix shape for the caller's own tenant before it is persisted |
| T-06-80 | Repudiation | a claim with no trace in the channel of record | mitigate | The claim row and the `SYSTEM` receipt message carrying `subscriptionClaimId` are written in one transaction; neither can exist without the other |
| T-06-SC | Tampering | npm installs | mitigate | Zero packages, zero shadcn components added |
</threat_model>
