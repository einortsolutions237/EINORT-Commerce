## Phase Goal

ROADMAP `**Goal:**` for Phase 6, verbatim: *A merchant can run their business day-to-day from a dashboard that surfaces what needs attention, and the platform owner can operate and support the pilot fleet of stores from a pilot-scoped Super Admin surface — including a direct messaging channel to every merchant and the ability to verify their subscription payments through it.*

**This plan's vertical slice:** a merchant can send a screenshot. D-10's "attachments on any message" becomes real for images; plan 06-13 adds the PDF path D-22 requires.

<objective>
Extend the existing presign→PUT→finalize upload triad to support-thread image attachments, with two narrow doors, and render them in the transcript.

Purpose: 06-RESEARCH.md § Discretion Q5 — every step of the existing triad is a security control, and each was verified empirically against the real bucket. `presignUpload` signs `content-type` **and** `content-length` into `signableHeaders`; without that, a grant minted for `image/jpeg` accepted a `text/html` body with 200 OK. A reimplementation omits that and fails open. This plan adds registry rows and two doors — it invents no mechanism.
Output: two registry rows, a new upload kind for subscription receipts, one mint module with two doors, one finalize route, attachment persistence, and the grid.
</objective>

**Scope of this plan: images only.** `image/jpeg`, `image/png`, `image/webp` — the three formats `ALLOWED_UPLOAD_CONTENT_TYPES` already permits. **D-22's PDF support is NOT dropped**; it is built in plan 06-13 as a genuinely separate, non-re-encoding path with its own content-disposition and origin-isolation story, because a PDF cannot be re-encoded by Sharp and serving the uploaded bytes from the public asset origin is the exact outcome `publicUrlFor`'s `/original` refusal exists to prevent. This plan's composer copy and `accept` attribute therefore say JPG/PNG/WebP, and plan 06-13 widens both.

**Two narrow doors, one credential each** (Pattern 4, argued twice in shipped code at `src/server/images/claim-upload.ts` and `src/app/api/upload/claim-finalize/route.ts`): the merchant's mint is a `merchantAction`, the platform owner's is an `adminAction`. Never one route with an "or" — widening one route's authorization to accept a second credential is what makes a trust boundary unreadable.

**`MAX_UPLOAD_BYTES` is 10 MB**, declared per-upload-path in `src/server/images/claim-upload.ts`, not globally. 06-UI-SPEC.md Open Item #2 asks the planner to confirm which constant governs the thread preset: **declare a thread-specific constant in `thread-upload.ts` mirroring the claim path's 10 MB**, and have the size-error copy interpolate that constant so the message always reads a real value rather than a hardcoded number.

**Attachment cap is 4 per message** (§ S), enforced in **both** the composer (the attach button disables at four) and the action's Zod schema. The client cap is convenience; the schema is the boundary.

**Two new `UploadKind` values, added together:** `"threads"` for message attachments and `"subscriptions"` for plan 06-15's SUB-03 receipt. Both use the same new `thread` image preset. Adding both now means plan 06-15 calls an existing door instead of editing this file in a later wave.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → presigned PUT grant | A five-minute capability to write one object to the bucket |
| uploaded bytes → publicly served bytes | The re-encode is what stands between them |
| client-supplied storage key → an attachment row | The finalize response is client-held before it returns to the server |
| merchant credential vs owner credential | Two upload paths, deliberately not one |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-47 | Tampering | presigned-URL abuse (writing arbitrary content to the bucket) | mitigate | `presignUpload` signs `content-type` and `content-length` into `signableHeaders`, verified empirically against the real bucket; five-minute expiry; key composed server-side from a server-minted UUID; allowlist checked before signing |
| T-06-48 | Tampering | serving attacker-authored bytes from the platform's asset origin | mitigate | Every image is Sharp-re-encoded to webp and only the derivative prefix is returned; `publicUrlFor` throws on any key ending `/original` |
| T-06-49 | Tampering | a client submitting an arbitrary `storageKey` on the message action | mitigate | The action validates the descriptor's key against the derivative-prefix shape for the caller's own tenant before persisting; the key is never trusted as opaque |
| T-06-50 | Elevation of Privilege | one upload route accepting "a merchant session OR an admin session" | mitigate | Two mint doors with one credential each, and a re-authorizing finalize handler; the `kind` union selects a namespace, not a credential, and the header says so |
| T-06-51 | Denial of Service | an oversized upload or an unbounded attachment count | mitigate | 10 MB per object signed into `content-length` so R2 enforces it, and a server-side cap of 4 attachments per message in the Zod schema; the client caps are convenience only |
| T-06-52 | Information Disclosure | a publicly readable attachment containing a receipt with a phone number | accept | Capability URL with a v4 UUID, established precedent for claim screenshots. **Recorded as an explicit acceptance**: R2 derivatives are served from `R2_PUBLIC_BASE_URL` with no authentication, so anyone holding the URL can read the image |
| T-06-53 | Denial of Service | Sharp running on an Edge runtime | mitigate | No `runtime` export in the finalize route, `maxDuration = 30`, and the comment stating that the failure mode is adding the line |
| T-06-SC | Tampering | npm installs | mitigate | Zero packages; `sharp` and the AWS SDK are already in use |
</threat_model>
