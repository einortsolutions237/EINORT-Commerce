# Phase 6 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## ⚠️ READ THIS FIRST — THIS PHASE ADDS A SURFACE, NOT A PALETTE

This phase builds two things: a **support thread + attention band** on the existing merchant dashboard, and a **from-scratch Platform Super Admin** at `/admin`.

**The Super Admin is not a third design system.** It inherits Surface A's tokens — blue brand / gold accent / slate surface, Outfit headings, Plus Jakarta Sans body, `0.75rem` radius — **whole and unchanged**. D-02's "visually distinct from the merchant dashboard" is delivered by *chrome and composition* (a persistent gold banner, a different rail, a different wordmark, no trial banner, no store switcher, no Cmd/K search), **not** by a different palette. Anyone who reaches for a new colour token in this phase has misread D-02.

| Label | Route tree | Governing reference |
|---|---|---|
| **Surface A** — merchant platform | `src/app/(dashboard)/**` | `.planning/design-references/EINORT-COMMERCE-FRONT-END-MERCHANT-PLATFORM.md` + `03-UI-SPEC.md § SURFACE A` |
| **Surface C** — platform admin *(new this phase)* | `src/app/admin/**` | Same reference, same tokens. This document's § C sections. |
| Surface B — storefront | `src/app/s/[slug]/**` | Untouched by this phase. `tests/unit/surface-token-isolation.test.ts` still governs. |

**Nothing in this phase touches `src/app/s/[slug]/**`.** No storefront file may be edited. Surface C lives on the apex, inherits `:root`, and declares no `data-surface` attribute.

**Inherited verbatim from `03-UI-SPEC.md`, restated only where this phase changes something:** the 4-point spacing scale, the 4-size / 2-weight type scale, the accessibility floor, the four-states rule, the responsive strategy, the order-state chip map, the destructive-action register's shape, and the "colour is never the only signal" rule.

| sm | 8px | Attention-tile inner gap; message-bubble inner vertical padding; table cell vertical padding |
| md | 16px | Gap between message rows; card inner padding below `sm`; composer inner padding; gap between attention tiles on mobile |

**Exceptions (dimensions, not spacing tokens):**

## Typography

Inherited verbatim. **Exactly 4 sizes, exactly 2 weights (400, 600).** No 300, no 500, no 700, no italics.

| Role | Size | Weight | Line Height | Face |
|---|---|---|---|---|
| Body | 16px | 400 | 1.5 | `font-sans` (Plus Jakarta Sans) |
| Label | 14px | 600 | 1.4 | `font-sans` |
| Heading | 24px | 600 | 1.2 | **`font-heading`** (Outfit) |
| Display | 36px | 600 | 1.1 | **`font-heading`** (Outfit) |

Role assignment for this phase:

| Role | Where it appears |
|---|---|
| Display | **Unused.** Reserved for the wordmark. |
| Heading | Page headings (`Support`, `Merchants`, `Payment claims`, `Subscription payments`, `Inbox`); `CardTitle` on every card; the attention-tile counts; the claimed amount on a subscription-claim card |
| Label | The admin banner text; table column headers; nav items; author names in the thread; status chips; timestamps; the `Needs your attention` band heading; the domain string; unread count badges |
| Body | Message bodies; empty-state bodies; helper text; dialog bodies; last-message previews in the inbox |

**Numerals:** every XAF amount, every stock count, every claim count and every ledger amount renders `tabular-nums`. Transaction references and the `{slug}.einort.com` domain string render `font-mono`.

**Message bodies preserve author line breaks** (`whitespace-pre-wrap`) and wrap long unbroken strings (`break-words`). A pasted transaction reference must not blow out the bubble.

### Accent (`--primary`, blue) reserved for exactly

1. The single primary CTA fill per page (`Send`, `Submit payment`, `Suspend`-dialog's confirm is **destructive** not primary — see the register)
2. The active nav item indicator in either rail
3. Focus ring (`--ring` = brand-500, one step lighter — do not "tidy" it to brand-600)
4. Inline text links
5. **NEW this phase — narrow amendment:** the **unread-message count badge** (`Badge variant="default"`) on the merchant `Support` rail item, on the admin `Support` rail item, and the per-thread unread dot in the admin inbox list.

> **Why unread is blue and pending-claims is gold.** Gold's whole meaning in this product is *unreviewed money*. An unread message is informational, not financial. Giving both the same colour would inflate gold into a generic "notification" hue and destroy the signal the claims badge depends on. Two count badges in one rail with two hues is deliberate, and each one carries a text label beside it, so hue is never the only signal.

**Accent is NOT for:** message bubbles, status chips, table headers, icons, hover fills, card borders, the admin banner, or "all interactive elements."

**Mandatory test amendment, in the same commit that spends the gold:** `tests/unit/dashboard-nav.test.ts`'s gold-budget assertion must be extended into an explicit allow-table naming these five files and their expected count of 1 each, plus a total-count assertion of 5.

## Resolved Decisions

`06-CONTEXT.md § Claude's Discretion` and `06-RESEARCH.md § Open Questions` explicitly deferred these to UI-SPEC. Resolved here, with reasons, so the planner does not re-open them.

### R-1 — D-02's gold chrome: a full-width persistent banner strip, not a badge

**Decision.** `src/components/admin/admin-banner.tsx` renders a **full-width, `min-h-8`, `sticky top-0 z-30`** strip as the very first child of `src/app/admin/layout.tsx`, above the header band and spanning the rail as well as the content.

| Detail | Contract |
|---|---|
| Fill | `bg-gold-accent/15` — the same 15% tint the `gold` badge variant already uses, so gold's existing meaning extends coherently instead of becoming a second brand colour |
| Text | `text-gold-accent-foreground`, **Label** role (14px / 600) |
| Content | `shield-alert` (lucide, `size-4`) + `strings.admin.banner` — one line, left-aligned, `px-4 sm:px-8` |
| Copy | `EINORT Platform Admin — you are acting across every merchant store.` |
| Interactivity | **None.** No dismiss, no link, no button. It is a state indicator, so the 44px floor does not apply. |
| Below `sm` | Text truncates to `EINORT Platform Admin` via a `hidden sm:inline` span on the second clause. Never wraps to two lines. |
| Accessibility | `role="note"` on the strip. It is static, so no `aria-live`. |

**Reason.** D-02 justifies the treatment by *consequence* ("suspend, moderate"). A badge tucked beside a page header scrolls away exactly when a long merchant list is being scanned — the moment the reminder matters most. A full gold fill was rejected: it would put gold across ~5% of every admin viewport, which is not a 10%-accent, and it would make the gold *chips* inside the page invisible against their own chrome. The 15% tint reads as a warning band while leaving the page field slate-50 and the 60/30/10 split intact.

**A second, cheaper distinctness signal, no colour cost:** the admin rail's header shows the wordmark followed by `Platform Admin` in Label/`--muted-foreground`, and the admin surface has **no** trial banner, **no** Cmd/K search modal, and **no** store name in the header. Those four absences do more per pixel than any hue would.

### R-2 — Suspend lives in **both** places, with different affordances

**Decision.** The suspend/restore toggle (D-17, symmetric) appears:

- **On the merchants list (`/admin`)** as an item inside a per-row `dropdown-menu` (`ellipsis` icon-button trigger, `min-h-11`), labelled `Suspend store` or `Restore store` depending on `Organization.status`. Never a bare button in the row.
- **On the merchant detail page (`/admin/merchants/[id]`)** as a dedicated `Store status` card with the same symmetric button and the current status chip beside it.

Both entry points open the **same** dialog component and call the **same** server action. There is exactly one suspend UI, mounted twice.

**Reason.** The pilot has a handful of stores and the list is where the owner works; forcing a page load to act is friction with no safety payoff, because the real safety gate is D-14's required reason, not the number of clicks. Putting it *only* on the list, however, would leave the detail page — the one screen that shows the store's full context and its thread — unable to act on what it shows. The dropdown wrapper is what keeps a mis-click from being possible: a destructive action is never one stray tap away in a dense table row.

### R-3 — SUB-03's submit form lives on `/dashboard/plan`; the thread carries the receipt

**Decision.** The merchant submits a subscription payment from **`/dashboard/plan`**, via a `dialog` opened by a `Submit payment` primary button. On success the action posts a `SYSTEM`-authored message into that merchant's support thread carrying `subscriptionClaimId`, and the thread renders the claim **inline** as a `SubscriptionClaimCard`. The platform owner reviews and decides from `/admin/subscriptions` (D-20); each decision posts a further `SYSTEM` message into the same thread.

**There is no second submit form inside the thread.** When the merchant's subscription is unpaid or the trial has expired, the thread's composer area shows one inline secondary link — `Submit your subscription payment` — that navigates to `/dashboard/plan`.

**Reason.** SUB-03 says the claim runs *through* the thread; the thread is the channel of record for the submission, the decision, and the audit trail — and this design puts all three there. What it does not do is put a payment form inside a chat transcript, where a half-typed reference competes with a conversation and where the merchant has no plan/price context. `/dashboard/plan` is where a merchant already goes to think about paying, and `260831-vd2` deliberately left its expired-trial branch with the payment step "deferred to Phase 6." This is that step.

### R-4 — The merchant `Support` rail item goes in the **General** group

**Decision.** `Support` (`/dashboard/support`, lucide `messages-square`) is inserted into `NAV_GROUPS`' **General** group, directly beneath `Overview`. `REQUIRED_HREFS` in `tests/unit/dashboard-nav.test.ts` gains `"/dashboard/support"` in the matching position (second, after `"/dashboard"`), **in the same commit**.

**Reason.** D-07 requires "same visual weight as Orders/Products" — which the grouped rail already gives every item equally. Group choice is therefore about meaning: a conversation with the platform is neither Commerce nor Configuration. Top-of-rail placement also makes the unread badge visible without scrolling on a short mobile sheet.

**Label:** `Support` (not `Messages`, not `Help`). It is the word the merchant will search for, and the thread's purpose includes payment proof, not just chat.

### R-5 — "Low stock" is one exported constant, displayed but not configurable

**Decision.** `LOW_STOCK_THRESHOLD = 5`, a module-level `SCREAMING_SNAKE_CASE` constant in the registry-as-data style of `STARTER_PRODUCT_CAP`. No schema column, no merchant setting, no per-product override. The attention tile's copy states the number so the merchant is never guessing what "low" means.

**Reason.** Research Open Question 2's recommendation, accepted. It satisfies DASH-02 at pilot scale for one query, and it is exactly the shape Phase 9 (Inventory) replaces with a real store-wide setting. Adding a column now means migrating it in three phases' time for zero pilot benefit.

### R-6 — The Overview metric row grows to five cards; attention gets its own band

**Decision.** `/dashboard` gains **two** new regions, and rebuilds nothing:

1. A **`Needs your attention` band**, placed between the page header and the metric row.
2. A **fifth metric card**, `Products live`, appended to the existing four. The grid becomes `grid-cols-1 sm:grid-cols-2 lg:grid-cols-3 xl:grid-cols-5`.

**Reason.** DASH-01's "products/inventory" clause and DASH-02's "what needs attention" clause are different questions and must not share a card. A count of live products is a *performance* figure and belongs beside Revenue; pending claims, low stock and disputed orders are *work* and belong above everything, where the eye lands first. The existing four cards, the 7-bar chart and the recent-orders list are **not** touched — Q3's gap analysis is explicit that Overview must be extended, not rebuilt.

## Interaction & State Contract

### Every surface declares four states

| State | Requirement |
|---|---|
| Loading | `loading.tsx` skeletons matching the final layout's shape — attention band (3 tiles), 5-card metric row, thread bubbles, ledger table rows, inbox rows. Buttons swap to a `…` label, `disabled`, width retained. **No full-page spinners anywhere.** |
| Empty | Every list surface has an authored empty state, specified per page above. The attention band's all-zero line counts as its empty state. A blank region is a contract violation. |
| Error | Blocking errors render as a `destructive` `alert` above the form **and** mark the offending field `aria-invalid`. **Never a toast alone for a blocking error.** A failed send never loses typed text. |
| Success | A navigation is the success signal. A stay-on-page action gets a `sonner` toast. Remember the admin tree needs its own `<Toaster/>` (§ C0). |

### Optimistic updates

| Action | Optimistic? | Why |
|---|---|---|
| Send a support message | **Yes** | Cheap, append-only, and the pending bubble is honest about its state |
| Confirm an order-payment claim (admin ledger) | **Yes** | Matches the merchant-side one-tap pattern D-19 explicitly reuses |
| Reject an order-payment claim | **Yes** (row leaves the awaiting filter) | Same |
| Mark thread read | **Yes** (badge clears on navigation) | Derived count; a stale badge for one render is harmless |
| **Suspend / restore a store** | **No** | It takes a merchant's business offline and writes to their thread. Show the submitting state and wait for the server. |
| **Confirm / reject a subscription payment** | **No** | It changes entitlement. Same reasoning. |
| **Submit a subscription payment** | **No** | It mints a claim row and uploads an image |

### Accessibility floor (inherited, non-negotiable)

- Every input has a visible `<label>`. Placeholder-as-label is a contract violation.
- Visible focus ring on every interactive element (`--ring`, ≥2px, 3:1). The whole-row `Link` patterns (attention tiles, inbox rows) show the ring on the card, not on the text.
- 44px minimum touch target on every control. The admin banner is exempt: it contains none.
- `aria-live="polite"` + `role="log"` on the thread container; `role="status"` on copy-confirmation and unread-count regions.
- `aria-current="page"` on the active item in **both** rails — colour alone is never the active-state signal.
- Full keyboard path through the composer, the attachment grid, the lightbox, the suspend dialog and both reject dialogs. Dialog focus is trapped and returns to the trigger on close.
- Every icon-only button has an `aria-label` read from `strings`.
- Every route sets a meaningful `<title>` through the root layout's `%s · EINORT` template. Admin titles do **not** say "Admin" in a way that would appear in a shared screenshot's tab strip beyond what the banner already says — `Merchants · EINORT` is correct.
- Colour is never the only signal — every chip has an icon and a label; every unread row has a weight change as well as a badge.

### Responsive strategy

Mobile-first, **designed at 360px first**. Tables collapse to stacked cards below `md`, never to horizontal scroll — this applies to C1, C3 and C4 without exception. Both rails collapse to an off-canvas sheet below `lg`. The thread composer is `sticky bottom-0` at every width. No carousels, no drawers.

## Copywriting Contract

**Voice:** direct, second person, no exclamation marks, no "Oops"/"Whoops", no emoji, no ALL-CAPS. Errors state what happened and what to do next.

**Two audiences, never mixed.** Merchant-facing copy says `your store`, `we`, `the EINORT team`. Admin-facing copy is the owner's own console: it says `{store name}`, `the merchant`, and never `your`. A string used on both surfaces is a bug.

**Never write:** an internal name (`scopedDb`, `platformRole`, `PAYMENT_CLAIMED`, `tenantId`, `SupportMessage`) · `Delete` for anything in this phase · `Verified` for a payment · `Payment received` before the owner confirms · a promise about custom domains, real-time chat, or read receipts · "Are you sure?" as the whole of a confirmation.

## Open Items Flagged for the Planner

These are **not** blocking this contract. Each has a stated default that the planner may execute against; only #1 needs a user answer before its task is written.

1. **PDF attachments (Assumption A2).** This contract restricts thread attachments to JPG/PNG/WebP, narrowing D-10's literal "file/image attachments". Every accepted format is a decoder Sharp must be trusted with, and a PDF cannot be re-encoded — supporting it means a second, non-re-encoding storage path with its own content-disposition and origin-isolation story. **Confirm with the owner whether they expect PDF receipts.** If yes, that is a separate phase, not a task.
2. **Attachment size cap.** The copy interpolates `{max}` from the existing upload constant rather than hardcoding a number. The planner must confirm which constant governs the thread preset and that the message reads a real value.
3. **`subscriptionCurrentPeriodEnd` display vs. enforcement (Research OQ-1).** This contract *displays* the period end (§ C2, § C4's `Covers through`, § S's confirmation message). It does **not** specify that `resolveEntitlements` enforces a lapse. If the owner wants enforcement, that is a `canWrite` semantics change touching every gated action and is out of this contract's scope.
4. **The gold-budget test amendment is a task, not a side effect.** § Color specifies the exact allow-table. It must land in the same commit as the first gold spend or the build breaks mid-wave.
5. **`REQUIRED_HREFS` + `NAV_GROUPS` + `strings.dashboard.nav.support` must land together** (Pitfall 2). Either half alone fails the build.
6. **Admin-account bootstrap (Pitfall 6) has no UI.** This contract deliberately specifies no "promote a user" screen — `platformRole` is `input: false` on purpose. The bootstrap is a `scripts/` task, and the phase is not verifiable without it.
