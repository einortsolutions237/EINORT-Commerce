## Phase Goal

ROADMAP `**Goal:**` for Phase 6, verbatim: *A merchant can run their business day-to-day from a dashboard that surfaces what needs attention, and the platform owner can operate and support the pilot fleet of stores from a pilot-scoped Super Admin surface — including a direct messaging channel to every merchant and the ability to verify their subscription payments through it.*

**This plan's vertical slice:** the owner reviews a subscription payment and the merchant's plan is extended. SUB-03 complete, and with it the last requirement in the phase.

<objective>
Build SUB-03's platform half: the only writer of `SubscriptionPaymentClaim.status`, the separate review page D-20 requires, and the inline read-only claim cards in both threads.

Purpose: D-20 is explicit that customer→merchant order claims and merchant→platform subscription claims get **two separate views**. Different actors, different consequences — confirming one releases an order, confirming the other extends a subscription. One combined table with a type discriminator would put two unrelated state machines behind one column, which is the same argument 06-RESEARCH.md § Discretion Q1 used to reject a shared table.
Output: the writer, its extended isolation coverage, the review page and row island, the last rail badge, and the two inline card wirings.
</objective>

**What "extending the subscription" writes, resolved (06-RESEARCH.md Open Question 1, 06-UI-SPEC.md Open Item #3).** On confirm:
- set `Organization.subscriptionStatus` to `"active"`,
- set `Organization.subscriptionCurrentPeriodEnd` to `max(now, existing period end) + 1 month` — so a merchant paying early is extended rather than reset,
- set the claim's `coversThrough` to that same value, so the ledger can show what the confirmation bought.

**`resolveEntitlements` is deliberately NOT taught to expire on `subscriptionCurrentPeriodEnd` in this phase.** Enforcement changes `canWrite` semantics for every entitlement-gated action in the codebase and touches the well-covered `tests/unit/entitlements.test.ts`; STATE.md tracks it as `KD-V2-02`, the milestone's single largest hidden cost. **Store and display only.** Record the deferral in the module header and in the plan summary as an explicit, considered deviation — not an omission. Do not edit `src/server/entitlements/**` in this plan; the acceptance criteria assert it is unchanged.

**Confirm is NOT optimistic** (§ Interaction & State Contract) — it changes what the merchant is entitled to. An `alert-dialog` first, then the submitting state, then a toast. Reject is a `dialog` with a **required free-text** reason of at least 10 characters (≤140, live counter) — **no canned reasons here**, because the failure modes are platform-specific and the owner is writing to one merchant, not triaging a queue.

**Neither row action is `variant="default"`** — the same one-primary-per-page rule as the order ledger. `Confirm` is `outline`, `Reject` is `destructive`.

**Inline claim cards are read-only on both threads**, with a link to `/admin/subscriptions` on the platform side. Confirm and reject never happen from inside a transcript — D-20 gives that decision exactly one surface.

**Copy** comes from `strings.admin.subscriptions` and `strings.support.system` (plan 06-02). This plan authors none.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| admin decision → a merchant's entitlement | Confirming changes what a tenant is allowed to do |
| `adminDb` → `Organization` and `SubscriptionPaymentClaim` | Unscoped writes across two tables in one transaction |
| the date the owner reads → the date the server writes | A confirmation dialog that quotes a different value than it writes is a lie |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-81 | Tampering | double-confirm across two admin tabs extending a subscription twice | mitigate | The status guard inside the transaction throws `AlreadyReviewedError`; the isolation test asserts one write and one system message |
| T-06-82 | Tampering | a second writer of `SubscriptionPaymentClaim.status` or the period-end column | mitigate | One module, stated ALL-CAPS in its header; plan 06-15's writer creates rows only and never touches status |
| T-06-83 | Elevation of Privilege | a merchant setting their own period end | mitigate | `subscriptionCurrentPeriodEnd` is `input: false` in the organization plugin (plan 06-03), so no request body can reach it; the only writer is behind `adminAction` |
| T-06-84 | Repudiation | a confirmation the merchant never learns about | mitigate | Every decision posts a `SYSTEM` message into the claim's own tenant's thread inside the same transaction |
| T-06-85 | Information Disclosure | cross-tenant write through an unpredicated `adminDb` call | mitigate | Every `where` names the `tenantId` read from the claim row; grep-asserted, and the isolation test asserts tenant B is untouched |
| T-06-86 | Tampering | client-side recomputation of the resulting period end | mitigate | The date is computed server-side and passed to the dialog as a formatted string; grep-asserted that no month arithmetic exists in the client island |
| T-06-87 | Tampering | silently wiring `resolveEntitlements` to enforce the lapse | mitigate | A structural assertion in the isolation suite reads `src/server/entitlements/resolve.ts` and fails if the period-end column appears in its logic, so the KD-V2-02 deferral must be revisited deliberately |
