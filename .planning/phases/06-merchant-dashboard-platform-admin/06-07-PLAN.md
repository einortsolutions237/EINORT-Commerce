## Phase Goal

ROADMAP `**Goal:**` for Phase 6, verbatim: *A merchant can run their business day-to-day from a dashboard that surfaces what needs attention, and the platform owner can operate and support the pilot fleet of stores from a pilot-scoped Super Admin surface — including a direct messaging channel to every merchant and the ability to verify their subscription payments through it.*

**This plan's vertical slice:** the platform owner can act on any merchant's payment claim at the server layer, with exactly the same consequences the merchant's own one-tap action has. Plan 06-10 puts the ledger table on top of it.

<objective>
Resolve this phase's single highest-risk integration — 06-PATTERNS.md § Risks R-1 — and build the admin-side order-claim writer on the resolution.

Purpose: 06-RESEARCH.md Assumption A4 assumed `transitionOrder` accepts any transaction client. 06-PATTERNS.md verified it does **not**: `transitionOrder(tx: ScopedTx, …)`, and `releaseStock`/`holdStockForLines`/`markStockHeld` are `ScopedTx`-typed too. The admin zone cannot construct a `ScopedTx` and, under the ESLint fence, cannot even name the type. Duplicating the writer is forbidden — it breaks `tests/unit/single-order-state-writer.test.ts`, which is the structural half of ORD-02. This plan takes the cheapest correct option: widen the parameter to the structural minimum those functions actually use, declared in a neutral module both zones may import.
Output: one new type module, two widened signatures, the admin claims module, and both contract tests still green.
</objective>

<!-- The verified constraint this plan works against. -->

`src/server/orders/transition.ts` currently declares `export async function transitionOrder(tx: ScopedTx, args: TransitionOrderArgs): Promise<void>`.
`src/server/db/tenant-scoped.ts` declares `export type ScopedTx = Omit<ScopedDb, runtime.ITXClientDenyList>`.
`src/server/orders/stock.ts` declares `releaseStock`, `holdStockForLines` and `markStockHeld`, all `ScopedTx`-typed.
`eslint.config.mjs` forbids `src/server/admin/**` from importing `src/server/db/tenant-scoped`, and forbids anything outside `src/server/admin/**` from importing `src/server/db/admin`. **Do not widen either fence** — STATE.md flags fence-widening as the v2.0 milestone's #1 risk.

**Three options, ranked in 06-PATTERNS.md R-1. This plan executes option 1.**
1. Widen the parameter to the structural minimum the functions actually use, in a module carrying no `tenant-scoped` import. One writer, no new test violation.
2. A bridge in `src/server/orders/**` that constructs the scoped client for the target tenant. Legal, but it re-introduces a tenant-id-to-client hop on the admin path for no benefit once option 1 works.
3. Duplicate the writer. **Forbidden.**

`src/server/claims/actions.ts` is the merchant-side writer and **must not be reused** (Pitfall 3): it resolves the tenant from `requireMerchantContext()`, and the platform owner has no organization (D-04), so calling it from the admin path redirects the owner into store creation.
