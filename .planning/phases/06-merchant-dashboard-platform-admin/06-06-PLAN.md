## Phase Goal

ROADMAP `**Goal:**` for Phase 6, verbatim: *A merchant can run their business day-to-day from a dashboard that surfaces what needs attention, and the platform owner can operate and support the pilot fleet of stores from a pilot-scoped Super Admin surface — including a direct messaging channel to every merchant and the ability to verify their subscription payments through it.*

**This plan's vertical slice:** the merchant half of the messaging channel exists end to end at the server layer — a message can be written, read back, counted as unread, and it nudges the platform owner by email. Plan 06-09 puts a screen on it.

<objective>
Build `src/server/support/**`: the merchant-side thread domain, the reusable "post a system message" primitive every later v2.0 phase depends on, and the second consumer of this codebase's Resend integration.

Purpose: ROADMAP's v2.0 reconciliation note makes this thread the only real notification channel Phases 7–15 can rely on. Its write primitive has to be generic enough for D-15's suspension notice and for later phases' automated notices from day one, or each of them invents its own.
Output: five server modules and the degradation unit test.
</objective>

**The zone split (06-RESEARCH.md § Recommended Project Structure, "One structural tension the planner must resolve explicitly"):**
`src/server/support/**` is the **merchant side only** and uses `scopedDb`. The admin side lives in `src/server/admin/support.ts` (plan 06-12) and uses `adminDb`. They share only `src/server/support/shared.ts`, which imports **no** DB client at all. `src/server/admin/**` must never import `src/server/support/queries.ts` or `messages.ts` — ESLint forbids the admin zone from importing `tenant-scoped.ts`, and a transitive import would defeat TEN-05's spirit even where the rule does not catch it. State this in both module headers.

**Correction to CONTEXT.md D-09's parenthetical:** Resend is **already wired**. `src/server/claims/notify.ts` is a complete production integration called from `after()` at `src/server/claims/submit.ts`. This is its **second** consumer, not its first. Copy the pattern; do not invent one. CLAUDE.md, ROADMAP.md and CONTEXT.md all still say otherwise and are corrected in plan 06-17.

**Schema (plan 06-03):** `SupportMessage { id, tenantId, author: SupportAuthor, authorUserId, body, readByMerchantAt, readByPlatformAt, subscriptionClaimId, createdAt, attachments }`. Attachments are **not** written by this plan — plan 06-11 adds the attachment write path and extends `postMerchantMessage`'s input.

**Copy** comes from `strings.support.*` (plan 06-02). This plan authors none.

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-21 | Tampering | `src/server/support/actions.ts` | mitigate | Built with `merchantAction({mode:"write"})`, so identity and the write gate resolve before the payload is parsed; the Zod schema is the trust boundary and bounds the body at 4000 characters with `.trim()` first |

| T-06-SC | Tampering | npm installs | mitigate | Zero packages; `resend` is already a declared, in-use dependency |
