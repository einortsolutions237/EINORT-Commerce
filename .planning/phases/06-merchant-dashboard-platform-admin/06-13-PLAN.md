<!-- The resolved design. Read this whole block before writing anything. -->

**The origin-isolation story, resolved.** A PDF is a script-carrying document. It is never re-encoded, so the served bytes are the uploaded bytes. Therefore:

1. **The document object is stored at the `/original` key**, exactly like an image's upload. `publicUrlFor` **throws** on any key ending `/original`, so the document is **structurally unreachable** from `R2_PUBLIC_BASE_URL` by any code path in this repository. That refusal is not a coincidence being worked around — it is the control being reused deliberately, and the header must say so.
2. **The only way to read it is an authorized Next Route Handler** that re-derives identity, checks the attachment belongs to the caller's tenant (merchant door) or that the caller is the platform owner (admin door), reads the object with `getObjectBuffer`, and returns it with:
   - `Content-Type: application/pdf`
   - `Content-Disposition: attachment; filename="receipt.pdf"` — a **server-generated** filename; the uploaded one was discarded at mint and is never echoed
   - `X-Content-Type-Options: nosniff`
   - `Content-Security-Policy: default-src 'none'; sandbox`
   - `Cache-Control: private, no-store`
   Forcing a download rather than inline rendering means the document never executes in a document context on the app's own origin.
3. **Two doors, one credential each** (Pattern 4). A merchant route under `/api/support/attachment/[attachmentId]` and an admin route under `/api/admin/support/attachment/[attachmentId]`. Never one route with an "or".

**The image allowlist is not widened.** `ALLOWED_UPLOAD_CONTENT_TYPES` stays exactly `image/jpeg`, `image/png`, `image/webp`, and `isAllowedContentType` keeps its exact-match, no-normalization behaviour. A **separate** `ALLOWED_DOCUMENT_CONTENT_TYPES = ["application/pdf"]` and `isAllowedDocumentContentType` are added beside it, so a reader can see at the constant which contract applies.

**Magic bytes are verified at finalize, not trusted from the header.** The signed `content-type` proves what the browser *declared*, not what it *sent*. Since nothing re-encodes the bytes, finalize must read them back and assert a real PDF header (`%PDF-`) before any row can reference the object. A failed check returns an error code and writes no row; the orphaned object is cheap.

**Size cap:** reuse `MAX_THREAD_UPLOAD_BYTES` (10 MB) from plan 06-11, signed into `content-length` so R2 enforces it.

**Copy widening.** 06-UI-SPEC.md § S and plan 06-02's `strings.support.attachments` currently say `JPG, PNG or WebP.` — they were written against 06-UI-SPEC.md's Assumption A2, which narrowed D-10 to images. **D-22 supersedes A2.** This plan widens those two strings to include PDF and updates the `accept` attribute. Record this in the summary as a deliberate deviation from 06-UI-SPEC.md § S's attachment-types row, resolved in favour of the locked CONTEXT decision.

**Attachment cap stays 4 per message**, counting images and documents together.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| uploaded PDF bytes → served bytes | Nothing re-encodes them; they are served as uploaded |
| document object → the public R2 asset origin | The one boundary this whole plan exists to hold |
| merchant credential vs owner credential on download | Two doors, one credential each |
| declared `content-type` vs actual bytes | The signature proves the declaration, not the content |
