## Phase Goal

ROADMAP `**Goal:**` for Phase 6, verbatim: *A merchant can run their business day-to-day from a dashboard that surfaces what needs attention, and the platform owner can operate and support the pilot fleet of stores from a pilot-scoped Super Admin surface — including a direct messaging channel to every merchant and the ability to verify their subscription payments through it.*

**This plan's vertical slice:** the channel becomes two-way. A merchant writes; the owner sees it in an inbox, opens it, replies; the merchant's badge lights up. ADM-05's core loop and ADM-03's support-contact clause are complete after this plan.

<objective>
Build the platform side of the thread: a flat unread-first inbox, one merchant's conversation, and the admin-side message writer — reusing the transcript components mirrored by a prop rather than forking them.

Purpose: D-08 makes the inbox a flat list because no urgency taxonomy exists or is needed at pilot scale. D-11 makes the total badge and the per-thread indicator derive from the same unread query, so building one gets the other nearly free. Both facts shape the queries, not just the UI.
Output: the admin support server module, its action module, two pages with skeletons, the rail badge, and the two deferred entry points from plan 06-08.
</objective>

**Zone rule (06-RESEARCH.md § Recommended Project Structure).** `src/server/admin/support.ts` uses `adminDb` and may import **only** `src/server/support/shared.ts` from the support domain — never `queries.ts` or `messages.ts`, which use `scopedDb`. The two writers are deliberate siblings; do not "deduplicate" them across the fence. `eslint.config.mjs` must not change.

**Because `adminDb` is unscoped, every operation in this module names `tenantId` explicitly.** On the merchant path the predicate is injected by the Prisma extension; here it is the author's job, and forgetting it is a cross-tenant write.

**No raw SQL.** `$queryRaw`/`$executeRaw` are banned repository-wide. The inbox's "every merchant, with their latest message and unread count, unread-first" is **three parallel reads merged in JS** (06-RESEARCH.md Pattern 6): `adminDb.organization.findMany` for the fleet, `adminDb.supportMessage.groupBy({ by: ["tenantId"], _max: { createdAt: true } })` for the latest timestamp, and `adminDb.supportMessage.groupBy({ by: ["tenantId"], where: { author: "MERCHANT", readByPlatformAt: null }, _count: { _all: true } })` for unread. Then merge and sort in JS. State the pilot-scale row cap honestly in a comment rather than pretending it scales.

**§ C5 ordering:** unread first (most recent unread at the top), then read threads by most recent message, then merchants with **no messages at all**, alphabetically. Merchants with no messages are still listed so the owner can open a conversation.

**§ C5 layout:** a single-column list of rows with `--border` dividers, up to `max-w-4xl`. **Not a table** — a last-message preview is prose and does not belong in a cell. **No filters** (D-08 is explicit).

**§ C6:** the thread is the identical component to `/dashboard/support`, with `viewer="PLATFORM"` so `PLATFORM` messages render as "own" and `MERCHANT` as "other". A `SYSTEM` message carrying `subscriptionClaimId` renders the claim card inline **read-only with a link to `/admin/subscriptions`** — confirm/reject never happens from inside the transcript, because D-20 gives that decision exactly one surface. The card component arrives in plan 06-15; until then render the system message normally and leave a comment naming 06-15, rather than a placeholder.

**Copy** comes from `strings.admin.inbox` (plan 06-02). This plan authors none.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| URL `[tenantId]` → an unscoped write | The only client-supplied tenant identifier on the admin surface |
| `adminDb` → tenant-scoped tables | No predicate is injected; the author supplies it |
| platform-authored text → the merchant's dashboard | Content crosses from the highest-privilege account into a merchant's surface |

| Threat ID | Category | Component | Disposition | Mitigation Plan |

| T-06-54 | Tampering | `sendPlatformMessage`'s `tenantId` | mitigate | Validated against a real organization row before any write; the action is `adminAction`-wrapped so identity resolves before the payload is parsed, and the author id comes from `ctx.userId` |
| T-06-55 | Information Disclosure | cross-tenant write through an unpredicated `adminDb` call | mitigate | Every `where` in `src/server/admin/support.ts` names `tenantId`; grep-asserted count and an ALL-CAPS header statement |
