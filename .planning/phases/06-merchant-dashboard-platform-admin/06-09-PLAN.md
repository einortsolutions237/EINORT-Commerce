## Phase Goal

ROADMAP `**Goal:**` for Phase 6, verbatim: *A merchant can run their business day-to-day from a dashboard that surfaces what needs attention, and the platform owner can operate and support the pilot fleet of stores from a pilot-scoped Super Admin surface — including a direct messaging channel to every merchant and the ability to verify their subscription payments through it.*

**This plan's vertical slice:** a merchant can open Support from the rail, read the thread, and send a message that reaches the platform owner's inbox and nudges them by email. This is the first end-to-end use of the channel.

<objective>
Build the merchant side of the support thread: three reusable components, the page, and D-07's persistent nav item — with `REQUIRED_HREFS` extended in the same commit.

Purpose: 06-PATTERNS.md § No Analog Found lists the transcript components as the only genuinely new interaction code in this phase — no conversation UI, no bubble, no day separator, and no `useOptimistic` usage exists anywhere in this codebase. They are built once here against 06-UI-SPEC.md § S and reused unchanged by the platform side in plan 06-12, mirrored by a single `viewer` prop.
Output: `src/components/support/**`, the merchant page and its skeleton, the rail item, the unread badge wiring, and the extended nav contract test.
</objective>

**§ S — one component, two surfaces, mirrored by a single `viewer` prop.** Never fork per surface. Own side (`MERCHANT` on this page, `PLATFORM` on plan 06-12's page): right-aligned, `bg-secondary`, no border, author label `You`. Other side: left-aligned, `bg-card`, `--border` hairline, author label `EINORT` here and the store name there. `SYSTEM`: full width, centered, **no bubble**, a `bg-muted` inset row with `rounded-lg`, an `info` icon and a Label. Own-side bubbles are slate-100, **not blue** — a column of `--primary` fills would be the largest accent spend in the product and would leave nothing for the composer's `Send`.

**§ S — read receipts are not shown to either party.** The schema stores `readByMerchantAt`/`readByPlatformAt` because unread counts need them; surfacing "seen" turns an async, check-in-when-you-can channel into an obligation. Plan 06-06's `threadForMerchant` deliberately does not select those columns.

**Unread badge colour:** `variant="default"` (blue), per § Color's narrow accent amendment. Gold means unreviewed money; an unread message is informational. Spending gold here would also fail plan 06-04's five-file allow-table.

**Attachments are NOT in this plan.** The `paperclip` affordance and the attachment grid arrive in plan 06-11. Do not render a disabled paperclip button and do not build a dead code path — the composer ships text-only, and 06-11 adds the affordance. Say so in a comment.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| merchant-authored text → rendered HTML | Message bodies are arbitrary merchant input |
| optimistic client state → what the merchant believes was sent | A pending bubble that persists on failure is a lie |
| session → the tenant's own thread | The page reads and marks read for one tenant |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-36 | Tampering | rendering merchant text as markup | mitigate | Bodies render as text with `whitespace-pre-wrap break-words`; links are deliberately **not** auto-linkified and the omission is stated in a comment so it is not added casually |
| T-06-37 | Repudiation | an optimistic bubble surviving a failed send | mitigate | On failure the optimistic row is removed and the body is restored to the composer with an inline destructive Alert; never a toast alone |
| T-06-38 | Information Disclosure | read receipts leaking attention state | mitigate | `threadForMerchant` does not select the read columns and no component references them; grep-asserted |
| T-06-39 | Information Disclosure | cross-tenant thread read | mitigate | The page derives the tenant from `requireMerchantContext()` with no parameter, and every read goes through `scopedDb` |
| T-06-40 | Denial of Service | an unbounded message body | mitigate | The action's Zod schema bounds the body (plan 06-06); the composer's textarea caps input and the server refuses independently — the client cap is convenience, the schema is the boundary |
| T-06-SC | Tampering | npm installs | mitigate | Zero packages; `useOptimistic` ships with React 19, already installed |
</threat_model>
