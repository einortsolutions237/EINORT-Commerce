| — | **Internal-only: the distinctiveness contact sheet** | not a merchant route — a build/dev artifact | N/A (not merchant-facing) | § Distinctiveness Gate Contact Sheet |

**The rule this phase must not violate (D-02, restated as a checkable fact):** a variant is a structural/layout change — which sections render, in what arrangement, at what proportions. It is never a palette change. Every one of the 7 new variants below stays inside the zinc-monochrome storefront token set defined in `04-UI-SPEC.md` § Color, and reuses the **same four accent-reserved-for uses** — it introduces zero new ones. If a task under this phase reaches for a new colour, a new font weight, a new spacing value, or a new accent use, it is out of contract; stop and revise, don't add.

**Second rule (Finding 3 / Pitfall 4, restated as a design brief):** every new variant must be designed and reviewed with `backgroundImageKey` / `imageKey` set to `null` **first**. All 50 templates ship with no stock imagery (§ Image Policy). A variant that only looks finished with a photograph behind it is not shippable — it is the single most likely quality failure in this phase, because the null-image state is the *default* state for nearly every merchant on day one.

## Spacing Scale

Inherited verbatim from `04-UI-SPEC.md` — the seven-step scale, closed, unchanged. Phase 5 adds **zero new tokens**.

| Token | Value |
|-------|-------|
| xs | 4px |
| sm | 8px |
| md | 16px |
| lg | 24px |
| xl | 32px |
| 2xl | 48px |
| 3xl | 64px |

**Exceptions this phase adds (dimensions/layout constants, not scale tokens — same category as `04-UI-SPEC.md`'s hero height and editor rail width):**

| Exception | Value | Why |
|---|---|---|
| `trust-bar:strip` band padding | `py-6` (24px) < `md`, `py-8` (32px) ≥ `md` | Deliberately shallower than `band`'s 48/64px — "thin strip" is the distinctiveness signal; using the same padding as `band` would make the two variants read identically at a glance |
| `hero:split` minimum height | `md:min-h-[70svh]` | Shorter than `full-bleed`'s 85svh — a two-column layout carries visual weight without needing the same vertical dominance as a single full-bleed photo |
| `hero:stack` minimum height | `min-h-[70svh]`, `max-h-[900px]` | Same family as the other two hero variants, kept modest since there is no image to fill the frame |
| Template thumbnail (picker card) | `aspect-[3/4]`, min width `140px` | Small enough that a 25-card grid stays a few kilobytes of DOM at any tier (`05-RESEARCH.md` Pattern 7 payload note), large enough that the 12 possible block arrangements stay legible |
| `product-grid:showcase` grid gap | `gap-8` (32px), `gap-12` (48px) ≥ `md` | These ARE scale tokens (`xl`/`2xl`) reused, not new values — listed here only so the "generous gap" claim in `05-RESEARCH.md`'s variant table has a concrete number |

Any value outside these two tables plus `04-UI-SPEC.md`'s own exceptions table is a contract violation. Product tile aspect stays `aspect-[4/5]` site-wide, unchanged — `showcase` does not get a new aspect ratio, only more surrounding space.

`product-grid:dense`'s grid gap is `gap-2` (8px) at every breakpoint — a genuine spacing-scale token (`sm`), not a one-off constant, so it does not appear in the exceptions table above. It stays tighter than `grid`'s 16/24px at every breakpoint, which is the "dense" distinctiveness signal (§ New Variant Contracts).

## Color

Unchanged from `04-UI-SPEC.md` § Color, both surfaces. Phase 5 adds **zero new colour tokens** and **zero new accent uses**.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--background` (white, surface 1) / `--surface-*` slate scale (surfaces 2/3) | Page field |
| Secondary (30%) | `--muted`/`--secondary` zinc-100 (surface 1) / slate-100/200 (surfaces 2/3) | Washes, cards, image placeholders |
| Accent (10%) | `--brand-accent` (surface 1, merchant's own colour) / `--primary` brand-blue (surfaces 2/3) | See reserved-for lists below — **unchanged from Phase 4, no additions** |
| Destructive | `--destructive` | Form errors; the template-switch confirm dialog's confirm button |

**Accent reserved for, surface 1 (verbatim from `04-UI-SPEC.md`, no additions) — this list governs every one of the 7 new variants identically:**
1. The hero section's primary CTA fill (every hero variant: `full-bleed`, `split`, `stack`)
2. The contact band's primary CTA fill (every contact variant: `band`, `card`)
3. The product-grid "View all" link (every product-grid variant: `grid`, `dense`, `showcase`)
4. The selected state of a category filter chip (every product-grid variant)
5. (Derived, non-discretionary) the focus ring

**Accent is NOT for**, restated because it is the rule most at risk from a new variant: `trust-bar` icons (any variant, including `strip`), the `editorial-split` CTA on the ink band (any variant, including `banner` — that CTA is `bg-background text-foreground`, never the accent, per `04-UI-SPEC.md`'s locked "ink-on-ink collision" rule), any thumbnail decoration outside the one CTA block (§ Template Thumbnail), any tier-lock badge, any "Current template" badge, any selected-picker-card ring (that's `--primary`, the dashboard blue, not the merchant's storefront accent — surface 2/3 tokens never leak the merchant's own accent, per the still-binding D-12 document boundary).

**`--brand-accent-secondary` reserved for exactly two things, unchanged:** the announcement-bar fill and the `trust-bar:band` wash. `trust-bar:strip` does **not** get a wash (§ New Variant Contracts) — this is deliberate, not an oversight; see that section.

**Surfaces 2/3 gold-accent budget: still fully spent** (pending-claims badge, "Payment claimed" chip — `04-UI-SPEC.md` § Color). No template-picker element uses gold. Tier-locked cards and "Current template" badges use neutral/`--primary` treatments only (§ Onboarding Template Picker, § Editor "Change Template" Action) — this is a deliberate extension of the same budget discipline, not a new decision needing re-litigation.

## New Section-Type Variant Contracts (D-02, TMPL-03)

Seven new variant components across five section types. Each inherits its section type's existing settings shape, schema caps, motion tokens, and accessibility floor from `04-UI-SPEC.md` unchanged — only the layout differs. **Every variant below is designed and specified for the `null`-image case first**, per Finding 3.

### Background-treatment classification (extends the anti-flatness rule to variants)

`04-UI-SPEC.md`'s rule — "no two adjacent sections may share a background treatment" — now needs a per-*variant* classification, since two different variants of different section types can still collide. This table is the checkable reference a template author (and the Layer-1 distinctiveness test) uses:

| Section:Variant | Background treatment |
|---|---|
| `hero:full-bleed` | Photo + ink scrim (or flat zinc-100 when no image) |
| `hero:split` | Two-tone — white text column beside a zinc-100 image/monogram column |
| `hero:stack` | Flat zinc-100 |
| `trust-bar:band` | `--brand-accent-secondary` 8% wash |
| `trust-bar:strip` | White + top/bottom hairline rules (no wash) |
| `product-grid:grid` / `:dense` / `:showcase` | White (all three — differ only in density, not tone) |
| `editorial-split:split` | Ink (inverted `bg-foreground`) |
| `editorial-split:banner` | Ink (inverted `bg-foreground`) |
| `contact:band` | White |
| `contact:card` | Zinc-100 wash with a floated white card |

A template's default order must alternate treatments the same way the flagship does. `trust-bar:strip`'s hairline-only treatment is accepted as sufficiently distinct from an adjacent white section (its bordered strip reads as a rule, not a flat continuation) — recorded here so it is not re-litigated at review time.

## Image Policy (D-04, settles the phase's own open question)

**All 50 templates ship with `backgroundImageKey: null` and `imageKey: null` in their default documents.** No stock photography is sourced, licensed, or referenced. This is not a placeholder state — see Finding 3 in `05-RESEARCH.md`: `storageKeySchema`'s tenant-prefixed regex makes a shared stock asset structurally unreferenceable without weakening a documented security control, and Phase 4 already recorded the product judgement that a generic hero image is worse than none.

Consequence for this UI-SPEC: `hero:stack` and `editorial-split:banner` have **no image slot at all** by construction (§ New Variant Contracts) — they cannot fail the no-image case because there is no image case to fail. `hero:split`'s no-image monogram panel and `hero:full-bleed`'s existing zinc-100 no-scrim mode are the two remaining hero treatments, both already specified above / in `04-UI-SPEC.md`.

**A merchant can still upload a real image later through the existing image field** (unchanged pipeline, presign → PUT → finalize). Nothing here removes that capability — it only means no template *default* depends on one.

## Onboarding Template Picker (D-07, D-06, D-05)

**Surface 2. Blue/gold/slate, Outfit headings, 0.75rem radius. No storefront token — no `--brand-accent`, no zinc palette, no `font-sans`-only heading — appears anywhere on this card.**

**Focal point:** the template grid is the card's primary focal point — it is the largest, most visually dense element on Card 3 and the reason the card exists. The selected-card ring (`border-primary ring-2 ring-primary`) is the secondary cue, confirming which card the merchant has committed to once a pick is made; nothing else on the card competes for attention.

**Grid vs. list, evaluated against the Shopify theme-editor reference (informs, does not dictate):** the reference's left rail organizes a single theme's *sections* as a collapsible, grouped text-and-chevron list — an apt pattern there because the decision being made is *where, within one design*, and a section's name is the whole signal needed to make it. This card's decision is the opposite: *which one of up to 50 distinct visual designs*, where the design's geometry — not a label — is the thing being compared. Reducing that comparison to a text-tree of names and segment tags would strip out the one signal (§ Template Thumbnail Component's proportional block layout) that lets a merchant tell two templates apart at a glance, which is a regression, not a neutral alternative. **Recommendation: grid stays correct; no list-view toggle is added this phase.** The `grid-cols-2 sm:grid-cols-3` layout specified below (§ Grid and card) is unchanged by this evaluation.

### Placement

Inserted as a **new Card 3** inside `<BrandingForm>`, immediately below the existing industry-selection card. The existing Card 3 (Logo) and Card 4 (Brand colours) renumber to Card 4 and Card 5. Nothing else in `04-UI-SPEC.md`'s onboarding contract changes — same page chrome, same `max-w-2xl`, same card shape (`rounded-lg border border-border bg-muted`), same submit button, same redirect-ladder gating.

### Behaviour: soft filter, not a hard restriction (Finding 5, D-05)

| State | What renders |
|---|---|
| Before the merchant picks an industry tile (Card 2) | The grid shows the merchant's full tier-accessible set (10/25/50), unsorted by segment, so the card is never empty while they are still deciding |
| After the merchant picks an industry tile | The grid **re-sorts** — that segment's templates float to the front, still within the same tier-accessible set — with a brief `<Reveal>`-style transition (`transition-all duration-[var(--motion-quick)]`, reusing the storefront's own quick-transition timing is **not** correct here since this is surface 2; use a plain `transition-opacity duration-200` local to this component instead — no cross-surface token borrowing) |
| "Show all templates" | A `Label`/`text-primary underline` link beneath the grid's first row. Toggles between "recommended for {segment}" (sorted, same set) and the full tier-accessible set unsorted by segment. **Never removes any card** — this is a sort order toggle, not a filter that hides templates, per D-05's permanent prohibition on industry mechanically determining the reachable set |
| Toggle label | `Show all {N} templates` when collapsed → `Show recommended only` when expanded (`{N}` is the merchant's tier count: 10, 25, or 50) |

| Difference | Contract |
|---|---|
| No industry-based sort/toggle | The editor already knows the merchant's segment context less usefully than onboarding does (they are here to *change* template, not pick a first one) — grid renders unsorted, tier-accessible set only, no "show all" toggle needed since there is nothing to filter |
| No tier-locked upsell cards | Editor's picker shows **only** the merchant's current-tier accessible set as normal selectable cards — the onboarding upsell moment does not repeat here. A single text link beneath the grid, `Body text-muted-foreground`: *"Want more templates? [See plans]"* → `/dashboard/plan`, covers discovery without cluttering a working surface with locked cards |
| The current-template card (Finding 6 corollary) | The template matching `draftTemplateKey` always renders in the grid, even if the merchant has since downgraded below its `minTier` — this is the one case the accessible-set filter does not apply to. It shows `border-primary ring-2 ring-primary` (the normal "selected" treatment) **plus** a small pill badge top-left of its thumbnail, `bg-primary text-primary-foreground`, reading `Current`. If it sits above the merchant's tier, a caption renders beneath the card, Body `text-muted-foreground`: *"Your current template · kept from a previous plan."* Clicking the current-template card is a no-op — it is already selected, and re-selecting it must never open the destructive-confirm dialog |

### Relationship to the existing PublishBar — no new chrome, no new status language

The Shopify reference's top toolbar (a Draft status pill, a clearly primary Publish button set against a secondary/muted Save button, undo/redo, an overflow menu) is the part of that screenshot that transfers to this panel — not its section tree (see § Grid vs. list above for why the tree itself does not transfer). The transfer is architectural, not decorative: this panel sits *inside* the same rail/`PublishBar` shell `04-UI-SPEC.md` already defines for `Brand & logo` and the section list (`src/app/(dashboard)/dashboard/storefront-editor/publish-bar.tsx`), and it must never grow a save/publish button, a status pill, or draft/live copy of its own.

| Question | Answer | Why |
|---|---|---|
| Does switching require a separate "Save" step afterward? | **No.** `switchTemplate` is a `merchantAction({ mode: "write" })` that writes `draftTemplateKey` and re-seeds the draft document directly, in the same transaction, at the same trust tier as `saveDraft` (`05-RESEARCH.md` Finding 4 / Architecture Diagram: "`switchTemplate` … re-seed DRAFT ONLY"). It is a persisted server write, not a client-side staging edit — there is nothing left to save |
| Does the confirm dialog commit, or just stage the change? | **The dialog's confirm button *is* the commit.** Clicking `Change template` in the `alert-dialog` calls `switchTemplate` directly; there is no follow-up "now save this" step and no second persistence action anywhere in this flow |
| What does the existing PublishBar show immediately afterward? | `hasUnpublishedChanges: true`, `dirty: false` — the **same branch `PublishBar` already renders for any other saved-but-unpublished draft edit** (`publish-bar.tsx`'s `status` derivation: `dirty ? statusUnsaved : hasUnpublishedChanges ? statusSaved : statusPublished`). It is **not** the `dirty`/`statusUnsaved` branch — a template switch is a completed, persisted write, and showing "Unsaved changes" for something already saved would be exactly the kind of misleading draft/live signal `04-UI-SPEC.md` and the Shopify reference's own clear-status-pill language both exist to prevent |
| How does the editor shell learn a switch happened, so it can update the bar? | A new `onTemplateSwitched` callback on the editor shell, parallel to `PublishBarProps.onSaved` / `onDiscarded` and matching the existing `DiscardedState` shape: new `document`, new `tokens`, plus the new `SectionVariantMap`. This is the same callback contract `publish-bar.tsx` already establishes for `onDiscarded` — not a new state-management pattern introduced for this panel |
| Does the merchant still need to click Publish to make the switch visible to customers? | **Yes, exactly once, through the existing bar's existing single primary button.** The switch panel adds no second "make it live" control anywhere in the editor — the Shopify reference's one-clear-primary-action toolbar language is honored by *routing through* the bar that already draws that distinction, not by drawing a second one inside this panel |

### Selecting a *different* template — the destructive confirm

Selecting any card other than the current one immediately opens an `alert-dialog` (does **not** wait for a separate "confirm your pick" step inside the panel — the dialog *is* the confirm step):

| Element | Contract |
|---|---|
| Title | `Change to {templateName}?` |
| Body | `Switching replaces your sections and their content with {templateName}'s defaults. Your logo and brand colors carry over — your announcement text and footer message reset to the new template's defaults. This won't change what customers see until you publish.` |
| Confirm | `Change template` — **destructive** variant (same register as the existing Discard dialog: it discards work, even though nothing is deleted from the database) |
| Cancel | `Keep current template` |
| On confirm | Calls `switchTemplate({ templateKey })`. On success: rail returns to the list view, the newly-active template's card shows the `Current` badge, and the preview iframe repaints via the existing postMessage handshake (draft document + tokens + the new `SectionVariantMap`) — **no page reload**. Publish-bar status updates per § Relationship to the existing PublishBar, above — **not** `Unsaved changes` (that status is reserved for un-persisted local edits, which a completed template switch is not). |
| On refusal (`TemplateLockedError`, e.g. a stale client posting an out-of-tier key) | Non-destructive `alert` inside the panel, same register as the publish bar's save-failure alert: *"This template needs a higher plan. [See plans]"* → `/dashboard/plan` |

**Why the dialog states the accent/logo-vs-copy split explicitly (D-11):** this is the one moment a merchant could reasonably fear "did I just lose my branding," and the honest answer is asymmetric — two things survive, two things reset. Burying that in a generic "this will reset your storefront" warning would either overstate the loss (accents/logo are safe) or understate it (announcement/footer text is not). State both, plainly, in the dialog body — not in a tooltip, not in a linked help article.

## Template Thumbnail Component (Pattern 6)

`src/components/theming/template-thumbnail.tsx`. One component, used by both the onboarding picker and the editor's picker panel — it must never drift between the two, and it must never drift from the skeleton it represents, because it renders geometrically *from* the template's `{type, variant}[]` section list rather than from a stored image.

| Property | Contract |
|---|---|
| Frame | `aspect-[3/4] rounded-md border border-border bg-background overflow-hidden`, minimum width 140px |
| Content | A vertically-stacked miniature of the template's section list, each section rendered as one flat block sized proportionally to that section's real relative height (hero tallest, trust-bar/contact shortest) |
| Per-variant block shape | `hero:full-bleed` → one tall filled block · `hero:split` → two side-by-side half-width blocks · `hero:stack` → a short centred text-only mark (2-3 thin bars, no fill block) · `trust-bar:band` → one wide washed block with 3-4 small ticks · `trust-bar:strip` → one thin bordered line with small dots · `product-grid:grid` → 4 small squares in a row · `product-grid:dense` → 5-6 tighter squares · `product-grid:showcase` → 2 larger rectangles · `editorial-split:split` → one dark block beside a lighter block · `editorial-split:banner` → one full-width dark bar · `contact:band` → one thin centred bar · `contact:card` → a small bordered box, centred, on a light field |
| Colour | Every block is `bg-muted` / `bg-border` (neutral dashboard greys) **except exactly one** — the block representing the template's primary CTA (the hero block, or the contact block if hero is somehow absent) — which is filled via `style={{ backgroundColor: primaryAccent }}`, `primaryAccent` being validated Zod state from the template's own default tokens, **never a literal** (ban #1). This single coloured block is the thumbnail's only nod to the merchant's actual palette and mirrors the real page's own "accent used once, for the CTA" restraint. |
| Text | **None rendered inside the thumbnail.** Purely geometric — avoids needing legible micro-copy at 140px width across 50 templates, and keeps the component render-cheap for a 25-card grid |
| Below the thumbnail | Template display name (Label) and segment tag (Body, muted) — outside the thumbnail frame, part of the card, not the component itself |

**Zero image bytes, zero R2 dependency, zero regeneration obligation** — it cannot drift from the skeleton because it renders from the skeleton's own data, exactly as `05-RESEARCH.md` Pattern 6 specifies.
