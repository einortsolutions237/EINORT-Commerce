## Phase Goal

Merchants outside the fashion segment get their own structurally distinct storefront, and the template library reaches 50 visually distinct variations (10 Starter / 15 Business / 25 Professional) that a stranger would not mistake for one another.

> Planner note: the ROADMAP `**Goal:**` line for Phase 5 is not in `As a … I want to … so that …` form. It is reproduced verbatim rather than invented. Run `/gsd mvp-phase 5` if the user-story framing is wanted.

<objective>
Add `switchTemplate` and make the three existing write paths template-aware, so a template is a draft choice a merchant previews and publishes rather than an instant redesign of their live store.

Purpose: D-08 and D-09 require a real switch capability with an explicit warning and a full re-seed. `05-RESEARCH.md` Finding 4 establishes that the switch must write draft columns ONLY, because `actions.ts` lines 156-168 already state that adding a published column to a draft write "would silently turn every keystroke into a deploy". Pitfall 5 establishes that `discardDraft` must revert three things after this phase, not two, and that its flagship fallback becomes wrong for a non-flagship tenant. Pitfall 6 establishes that the tier gate must be an assert in the handler, not a filter in a `.tsx` — a picker that hides a card is a courtesy, not a control.
Output: one new Server Action and three amended ones, all in `src/server/theming/actions.ts`.
</objective>

Add `export const switchTemplate` to `src/server/theming/actions.ts`, built with `merchantAction<typeof switchTemplateSchema, SwitchTemplateData>({ mode: "write", … })` and the named generic (R appears only in the handler's return position, so TypeScript cannot infer it).

Schema — `switchTemplateSchema = z.object({ templateKey: z.string().refine(isTemplateKey, "Not a template.") })`. Exactly one field, and **NO TENANT IDENTIFIER** (T-04-04): this action is reachable by a direct POST that never rendered the picker, so the schema IS the trust boundary and the target is `ctx.tenantId` and nothing else. Narrow through the registry predicate rather than a `z.enum` restating 50 keys — the `isIndustrySegment` precedent, so the closed set lives in one place and the schema cannot drift from it.

Return type `SwitchTemplateData = { document: PageDocument; tokens: ThemeTokens; variants: SectionVariantMap; templateKey: string; draftUpdatedAt: string }` — the `discardDraft` precedent: the editor holds its state in the browser, so without this payload a switch would leave the open editor showing the design it just replaced until a full reload. `variants` is included so the editor can post the new map to its preview iframe.

Handler order is fixed and the first two statements come before any database call:

1. `assertCanEditStorefront(ctx, strings.editor.starterViewOnly)` — EDIT-03 / D-13 / D-15, unchanged behaviour.
2. `assertTemplateAccess(ctx, templateKey, strings.editor.templateTierLocked)` — D-06 / D-12. This is the control; the picker hiding a card is not. Both throw `EntitlementError` subclasses, which `merchantAction`'s existing catch arm converts to a form-level message with no change to that file.

Then compose the new draft state:

- `const document = templateDefaultDocument(templateKey);`
- Tokens preserve brand identity and reset template copy, per D-11: read the tenant's current `draftTokens`, keep `primaryAccent` and `secondaryAccent`, and take `announcementText` and `footerTagline` from `templateDefaultTokens(templateKey)`. `logoKey` lives on its own column and is simply not written, so it survives untouched. Use the same composition shape `saveBranding` already establishes at lines 583-593, and document why: D-09 discards the DOCUMENT, not the brand — resetting an identity the merchant chose at onboarding because they changed layout would read as data loss, not as a template change.
- Write inside one `scopedDb(ctx.tenantId).$transaction`: `storefrontPage.update` sets `draft` and `draftUpdatedAt` (explicitly, not left to `@updatedAt`); `storefrontTheme.update` sets `draftTokens` and `draftTemplateKey`. **`published`, `publishedTokens` and `publishedTemplateKey` are left byte-identical** — writing `publishedTemplateKey` here is a silent publish and is the single most important thing this action must not do. Put that sentence in the code as a comment above the `data` objects, in the register of lines 156-168.
- Throw `StorefrontNotSeededError(ctx.tenantId)` if either row is missing, matching `discardDraft`.
- `revalidatePath("/dashboard/storefront-editor")` after the transaction, then return `{ ok: true as const, … }` including `variantsForTemplate(templateKey)`.

Do NOT modify `ensureStorefrontSeeded` and do NOT give it a template parameter. Its `upsert` with `update: {}` on both halves exists so it NEVER CLOBBERS AN EXISTING MERCHANT'S WORK, and it is called on every editor visit; `switchTemplate` is the deliberate clobber. They are opposite intents and must remain separate exports.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client POST → `switchTemplate` | reachable without ever rendering the picker; the schema and the asserts are the whole control |
| client POST → `saveBranding` | reachable without ever rendering the onboarding form; runs outside the DAL by design |
| draft columns → published columns | the publish transaction is the only sanctioned promotion path |
