## Phase Goal

Merchants outside the fashion segment get their own structurally distinct storefront, and the template library reaches 50 visually distinct variations (10 Starter / 15 Business / 25 Professional) that a stranger would not mistake for one another.

> Planner note: the ROADMAP `**Goal:**` line for Phase 5 is not in `As a … I want to … so that …` form. It is reproduced verbatim above rather than invented. Run `/gsd mvp-phase 5` if the user-story framing is wanted.

<objective>
Define the rendering-variant vocabulary and the template-row contract that every other plan in this phase builds against, and lock the marker boundary that makes the whole design possible with a source-scanning test.

Purpose: this is the interface-first contract plan (Wave 0 in spirit). `05-RESEARCH.md` Finding 1 establishes that putting the variant vocabulary in `registry.ts` is "the single most likely wrong turn in this phase, and it fails at *build* time on the editor route" — this plan puts it in the right module and adds the test that catches the wrong turn in milliseconds instead of at build time.
Output: the variant type system, the extended `TemplateDefinition`, `variantsForTemplate()`, and a marker-boundary contract test.
</objective>

This is the FOURTH trust boundary (postMessage only) and is DELIBERATELY NOT part of `pageDocumentSchema` — variants are template-level and not merchant-editable (D-02), so a direct POST to `saveDraft` still cannot set one.

Do NOT add `import "server-only"` to this file. Do NOT widen `storageKeySchema`. Do NOT add a `variant` field to `sectionInstanceSchema` — `05-RESEARCH.md` § Anti-Patterns records that it makes the variant merchant-settable by direct POST and breaks `tests/unit/theming-registry.test.ts`'s "field descriptor for every schema key" assertion.

Each export carries a header doc comment in this file's established register: what it is, which decision ID it satisfies (D-02), the invariant it protects, and the explicit wrong fix. Extend the file's own three-doors paragraph (lines 15-33) to name the fourth door.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| editor iframe → preview canvas (postMessage) | `sectionVariantsSchema` becomes the fourth untrusted door into the preview client |
| stored `draftTemplateKey`/`publishedTemplateKey` column → renderer | a drifted or forged string reaches `variantsForTemplate()` on a public page |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-01 | Tampering | `sectionVariantsSchema` (postMessage payload) | mitigate | Zod `z.enum` per section type; the schema is deliberately NOT part of `pageDocumentSchema`, so no `saveDraft` POST can set a variant (D-02) |
| T-05-02 | Denial of Service | `variantsForTemplate(key)` on the public storefront | mitigate | Never throws; an unrecognised key degrades to the all-first flagship map, so a drifted column renders the Phase 4 design rather than crashing a live store |
| T-05-03 | Information Disclosure | `server-only` leakage into client bundles | mitigate | `tests/unit/theming-marker-boundary.test.ts` scans `src/app/s/[slug]/sections/**` and every `"use client"` file for registry/defaults imports |
| T-05-04 | Tampering | `storageKeySchema` widening pressure | accept | Explicitly out of scope; no stock imagery this phase (RESEARCH Finding 3). The regex is untouched by this plan |
| T-05-SC | Tampering | npm/pip/cargo installs | accept | Zero package installs this phase — `05-RESEARCH.md` § Package Legitimacy Audit records an empty table with an explicit "no installs this phase" disposition |
