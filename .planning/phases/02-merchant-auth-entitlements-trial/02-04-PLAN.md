## Phase Goal

**As a** merchant, **I want to** sign in to a dashboard that knows which store is mine from my session alone and shows my plan and trial state, **so that** I can run my store knowing my subscription limits are enforced on the server, not just displayed in the UI.

<objective>
Give a returning merchant a way back in: the `/login` surface, the sign-in and sign-out actions, and the distributed throttle that the login HTTP endpoint has been missing.

Purpose: TEN-04's session-derived tenancy is only reachable if a merchant can create a session after signup day. Phase 1 deliberately shipped `/signup` with no sign-in link; building it is this phase's job. Login is also a new abuse surface — Better Auth's built-in limiter is memory-backed and production-only by default, which is the "fictional limit" this repo's rate-limit module already refuses to ship.
Output: `/login`, `signInMerchant` / `signOutMerchant`, `rl:login`, and a Better Auth `rateLimit.customStorage` adapter on the existing Upstash client.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| anonymous browser → `signInMerchant` | Unauthenticated, credential-bearing input from anyone on the internet |
| anonymous browser → `POST /api/auth/sign-in/email` | The same credential check reachable without the Server Action, on the apex handler |
| app → Upstash Redis | Shared rate-limit state; a transport failure must degrade honestly |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-18 | Spoofing | Credential stuffing against `/api/auth/sign-in/email` | mitigate | `rateLimit: { enabled: true, customStorage: authRateLimitStorage }` backed by Upstash, with `consume` implemented atomically; proven behaviourally by the 429 on the fourth request in 10 seconds |
| T-02-19 | Denial of Service | scrypt CPU exhaustion via a login flood | mitigate | Same distributed limiter plus the action-level `rl:login` limiter, which runs before parsing and before any database read |
| T-02-20 | Information Disclosure | Account enumeration through login copy | mitigate | One `invalidCredentials` string for every authentication failure; Better Auth already equalises timing with a dummy hash for unknown users, and no second message is added |
| T-02-21 | Spoofing | Session not really revoked on sign-out | mitigate | `signOutMerchant` calls `auth.api.signOut`; the isolation test asserts `getSession` returns null afterwards, so a cleared-cookie-only implementation fails the gate |
| T-02-22 | Tampering | Configuring `secondaryStorage` to obtain distributed limits | mitigate | Explicitly forbidden and asserted absent: it flips `databaseStoresSessions` and would silently move sessions out of Postgres, breaking the `activeOrganizationId` back-fill |
| T-02-23 | Denial of Service | Upstash outage taking login offline | accept | Fail open with one loud warning naming the unprotected surface, matching the existing module contract; an in-process counter is rejected as dishonest rather than weak |
| T-02-24 | Elevation of Privilege | Hand-parsing the signed session cookie | mitigate | Session reads go through `auth.api.getSession({ headers })` only; Phase 1 already hit this bug and the correct tool is the library's own header handling |
| T-02-SC | Tampering | npm/pip/cargo installs | mitigate | Zero packages installed; any deviation requires a blocking human checkpoint |
</threat_model>
