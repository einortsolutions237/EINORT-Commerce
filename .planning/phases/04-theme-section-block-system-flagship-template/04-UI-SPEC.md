## ⚠️ READ THIS FIRST — THREE SURFACES, TWO DESIGN SYSTEMS, ONE HARD BOUNDARY

Phase 4 builds UI in three places. Two of them are the **merchant platform** design system; one is the **customer storefront** design system. Mixing them is the mistake that already cost this project one full retrofit (`260823-gu4`) and is guarded by `tests/unit/surface-token-isolation.test.ts`. **D-12 forbids weakening that test for the editor.**

| # | Surface | Route tree | Design system | Palette | Heading face | Radius |
|---|---|---|---|---|---|---|
| 1 | **Flagship storefront** (new sections + theme chrome) | `src/app/s/[slug]/**` | `01-UI-SPEC.md` § Color → restated in `03-UI-SPEC.md` § B, **extended here** | Zinc monochrome + `--brand-accent*` | Plus Jakarta Sans (`font-sans`) — Outfit is **banned** here | `0.25rem` |
| 2 | **Onboarding branding step** | `src/app/onboarding/branding/**` | `.planning/design-references/EINORT-COMMERCE-FRONT-END-MERCHANT-PLATFORM.md` | Blue / gold / slate | Outfit (`font-heading`) | `0.75rem` |
| 3 | **Storefront editor chrome** | `src/app/(dashboard)/dashboard/storefront-editor/**` | same as #2 | Blue / gold / slate | Outfit (`font-heading`) | `0.75rem` |

**The one rule: check which route tree you are in before you pick a token.** A reference is scoped to a surface, not to the product.

### The two-source storefront tension is now RESOLVED (record this)

`.planning/design-references/EINORT-COMMERCE-FRONT-END-MERCHANT-PLATFORM.md` § "A second tension" flagged that the storefront had two candidate design sources and demanded an explicit Phase 4–5 decision before template work starts. **This document is that decision:**

> **The customer storefront is governed by the zinc-monochrome DTC/editorial reference. The merchant-platform reference's own `src/pages/storefront/` blue/slate treatment is NOT adopted and must not be consulted for storefront work.**

Traceable to `04-CONTEXT.md` § Canonical References ("Design references — TWO distinct systems for TWO distinct surfaces"), D-09, and `globals.css`'s existing `[data-surface="storefront"]` scope. Do not reopen it.

### The D-12 boundary, stated as a rule an executor can apply

`--brand-accent*` is declared **only** inside the `[data-surface="storefront"]` block in `globals.css` and injected **only** from a file under `src/app/s/`. A dashboard component writing `bg-brand-accent` resolves to nothing. The only merchant accent visible on a dashboard screen is **inside the preview iframe**, which is a different document on a different origin. The separation is enforced by a document boundary, not by discipline.

One narrow, named exception, because a colour picker that cannot show a colour is not a colour picker:

> **The accent may be shown as a sample, never used as chrome.**
> **Allowed** on surfaces 2 and 3: a swatch tile, a hex text value, and a labelled colour chip, coloured via `style={{ backgroundColor: value }}` where `value` is Zod-validated state (never a literal — ban #1).
> **Forbidden** on surfaces 2 and 3: colouring any button fill, link, focus ring, border, badge, panel, active-state indicator, or hover state with a merchant accent. No `data-surface="storefront"` anywhere outside `src/app/s/` (ban #4). No mini "CTA preview" widget on the onboarding page — the editor's iframe is where a merchant sees their accent applied.

## Spacing Scale

Inherited verbatim from `01/02/03-UI-SPEC.md`. Spacing is not where surfaces differ — colour, radius and heading face are. **The scale is closed at seven steps, and Phase 4 adds none.**

The flagship does need deeper section bands than the scale's 64px top step — 96px, with a 128px ceiling. Those are **not** new scale steps and are **not** named tokens: they are band dimensions, the same category as the hero's `85svh` or the editor rail's 320px, and they live in the Exceptions table below, where exactly three named containers may reach them. The rationale is recorded there.

| Token | Value | Usage in Phase 4 |
|---|---|---|
| xs | 4px | Icon-to-text gap; section-heading → body gap in a trust item; hex-input → swatch gap |
| sm | 8px | Label → input gap; trust-item icon → heading gap; up/down button gap in the section list |
| md | 16px | Default gap between form fields; product-tile image → name; hero eyebrow → headline; grid gap <md |
| lg | 24px | Card inner padding ≥sm; grid gap ≥md; hero headline → body; section horizontal gutter at 360px (`px-6`) |
| xl | 32px | Section gutter ≥md (`px-8`); hero body → CTA; grid header → grid; trust-bar column gap |
| 2xl | 48px | Trust-bar band vertical padding <md; editorial-split column gap ≥md |
| 3xl | 64px | Storefront section vertical padding <md (`py-16`) |

**Exceptions (dimensions and layout constants, not spacing tokens):**

| Exception | Value | Why |
|---|---|---|
| Minimum touch target | **44px** (`min-h-11` / `size-11`) on every interactive element, all three surfaces | Inherited, non-negotiable: low-end Android market |
| Storefront primary CTA height | **48px** (`min-h-12`) | Inherited from 03-UI-SPEC; applies to every section CTA |
| **Flagship section band rhythm** | `py-16` (64px) <`md` → **`py-24` (96px)** ≥`md` | A band dimension, not a scale step — reachable by **exactly three containers** (`product-grid`, `editorial-split`, `contact`) and by nothing else: no card, no form, no component, no dashboard surface. Why not the scale's 64px top step: the zinc/editorial DTC reference this template is anchored on carries its sections on deep bands, and a storefront whose widest breathing room equals a login page's padding reads as a form, not as an editorial page. TMPL-01's bar is "genuinely polished, portfolio-quality," and check #1 of the § Design-Distinctiveness Gate is judged on exactly this. The <`md` value is the scale's `3xl`, unchanged. |
| **Flagship band padding ceiling** | **128px** (`py-32`) | The hard maximum vertical padding anywhere on the flagship. **Nothing uses it today.** It is recorded so that if the inverted `editorial-split` band needs one more step at `lg`+, the value is bounded and pre-approved rather than invented at build time — and so that nothing ever exceeds it. Any use outside that one band is a contract violation. |
| Hero height | `min-h-[85svh]`, `max-h-[900px]` | `svh` not `vh` — mobile browser chrome would otherwise crop the CTA |
| Editor rail width | **320px** (`w-80`), `lg`+ only | Fits a settings panel at 1024px without squeezing the preview below a usable width |
| Mobile preview viewport | **390px** iframe width | The reference device width for this market's mid-range Android |
| Product tile aspect | `aspect-[4/5]` | Editorial DTC proportion, from the reference. PDP gallery keeps `aspect-square` (03-UI-SPEC B2) — deliberate, see § Deviations |
| Editorial-split image aspect | `aspect-[4/3]` | From the reference |
| Logo render height | 28px <md / 32px ≥md, `object-contain`, `w-auto` | A logo is never cropped |
| Content columns | Sections `max-w-7xl` · hero copy `max-w-3xl` · contact `max-w-3xl` · prose `max-w-prose` · onboarding branding `max-w-2xl` | Layout constants |

Any value outside these two tables is a contract violation. **A value that appears only in the Exceptions table is never promotable to a spacing token** — the scale stays at seven steps (4 / 8 / 16 / 24 / 32 / 48 / 64), exactly as 01/02/03-UI-SPEC.md declare it.

## Typography

### Surface 1 — flagship storefront (`src/app/s/[slug]/**`)

**Exactly 4 roles, exactly 2 weights (400, 600). Every role uses `font-sans`.** `font-heading` (Outfit) fails ban #3 here.

| Role | Size | Weight | Line Height | Tracking |
|---|---|---|---|---|
| Body | 16px | 400 | **1.6** | normal |
| Label | 14px | 600 | 1.4 | `tracking-[0.08em]` + `uppercase` when used as an eyebrow |
| Heading | **24px → 32px at `md`** | 600 | 1.2 | `tracking-tight` |
| Display | **40px → 64px at `md`** | 600 | **1.05** | `tracking-tighter` |

**The responsive step-up is scoped to `src/app/s/[slug]/sections/**` and the theme chrome.** The fixed transactional pages (PDP, cart, checkout, tracking) keep `03-UI-SPEC.md` § B's non-responsive 24px Heading / 36px Display. A 64px product name on a PDP is wrong; a 36px hero headline on a 1440px display is anaemic. The split is by directory and is checkable.

**Weight 700 is deliberately NOT added — resolves Open Question 5.** The reference's hero is `font-bold` (700); `src/app/layout.tsx` loads Plus Jakarta Sans at 400/600 only, and three prior UI-SPECs lock "exactly 2 weights." Display presence comes from **size (64px) + `tracking-tighter` + a 1.05 line-height**, not from a third weight. Do **not** add `"700"` to the `next/font/google` declaration — that is a contract violation and an extra font file on the LCP path for a market on low-end Android. A synthesised bold is likewise forbidden: never write `font-bold` under `src/app/s/**`.

Role assignment on the flagship:

| Role | Where it appears |
|---|---|
| Display | Hero headline; editorial-split heading (at its 32→40px step, see below) |
| Heading | Product-grid section heading; contact-band heading; footer wordmark is Label, not Heading |
| Label | Announcement bar; store wordmark; section eyebrows; trust-item headings; "View all" link; product price; category chips; out-of-stock chip |
| Body | Hero body; trust-item body; product names; editorial body; contact body; footer tagline; in-section empty-state body |

**Editorial-split heading exception:** it sits on an inverted band beside an image, not full-bleed. It renders at **32px → 40px at `md`**, weight 600, line-height 1.1, `tracking-tight` — a fifth *size step* of the Display role, not a fifth role. Declared here so it is not invented at build time.

**Numerals:** every XAF amount renders `tabular-nums`.

### Surfaces 2 & 3 — onboarding branding + editor chrome

Inherited **verbatim** from `03-UI-SPEC.md` § A. Typography. Nothing changes.

| Role | Size | Weight | Line Height | Face |
|---|---|---|---|---|
| Body | 16px | 400 | 1.5 | `font-sans` |
| Label | 14px | 600 | 1.4 | `font-sans` |
| Heading | 24px | 600 | 1.2 | **`font-heading`** (Outfit) |
| Display | 36px | 600 | 1.1 | **`font-heading`** (Outfit) |

### Surface 1 — the flagship storefront

Zinc monochrome, editorial, **plus a strictly-bounded merchant accent**. The complete 20-token `[data-surface="storefront"]` set in `globals.css` is inherited unchanged from `03-UI-SPEC.md` § B. Color — copy nothing out of it, change nothing in it. This section declares only what Phase 4 **adds**.

#### The 60/30/10 split on the flagship home

| Role | Token | Where |
|---|---|---|
| **Dominant (60%)** | `--background` (white) | Page field; product-grid section; contact band; header; footer |
| **Secondary (30%)** | `--muted` / `--secondary` (zinc-100), `--brand-accent-secondary/8` wash, and `--foreground` as the inverted editorial band | Trust-bar band wash; image placeholders; the ink editorial-split band; the hero scrim |

#### The three new brand tokens (+ two derived)

Declared in `globals.css` under `@theme inline` and given fallbacks inside the storefront scope, exactly as `04-RESEARCH.md` Pattern 8 prescribes:

```css
@theme inline {
  --color-brand-accent: var(--brand-accent);
  --color-brand-accent-foreground: var(--brand-accent-foreground);
  --color-brand-accent-secondary: var(--brand-accent-secondary);
  --color-brand-accent-secondary-foreground: var(--brand-accent-secondary-foreground);
  --color-brand-accent-ring: var(--brand-accent-ring);
}

[data-surface="storefront"] {
  /* …the existing 20 zinc tokens, unchanged… */
  /* Fallbacks so a tenant with no theme row still renders correctly. */
  --brand-accent: var(--primary);
  --brand-accent-foreground: var(--primary-foreground);
  --brand-accent-secondary: var(--muted-foreground);
  --brand-accent-secondary-foreground: var(--primary-foreground);
  --brand-accent-ring: var(--ring);
}
```

The live values are injected by `src/app/s/[slug]/layout.tsx` (and by `preview-canvas.tsx` inside the iframe) as a `style` object whose **values are variables, never literals** — ban #1 passes because the line contains no colour.

| Token | Source | Default (merchant who skips the picker) |
|---|---|---|
| `--brand-accent` | `StorefrontTheme.publishedTokens.primaryAccent`, Zod `hexColorSchema` | `#18181B` (zinc-900 ink) |
| `--brand-accent-foreground` | **Derived server-side** — `accentForeground(accent, "#FFFFFF", "#18181B")` | `#FFFFFF` |
| `--brand-accent-secondary` | `…publishedTokens.secondaryAccent` | `#71717A` (zinc-500) |
| `--brand-accent-secondary-foreground` | **Derived server-side**, same function | `#FFFFFF` |
| `--brand-accent-ring` | **Derived server-side** — `contrastRatio(accent, "#FFFFFF") >= 3 ? accent : ZINC_400` | `#18181B` (ink clears 3:1 at 17.72:1) |

All five default constants live in `src/lib/theme-defaults.ts`. **Never in a `.tsx` under `src/app` or `src/components`** — ban #1's regex would fail the build (Pitfall 1).

#### Accent reserved for exactly four things

1. **The hero section's primary CTA fill** — `bg-brand-accent text-brand-accent-foreground`, `hover:bg-brand-accent/90`. The single 10% moment above the fold.
2. **The contact/WhatsApp band's primary CTA fill** — same treatment.
3. **The product-grid "View all" link** — `text-brand-accent underline underline-offset-4` plus an `arrow-right` icon. Colour is never the only signal: the underline and the arrow carry the affordance even at a bad contrast ratio.
4. **The selected state of a category filter chip** — `bg-brand-accent text-brand-accent-foreground` (D-09's "active states"). The unselected chip stays `border-border` on `--background`.

Plus one derived, non-discretionary use: **the focus ring** on every storefront interactive element resolves to `--brand-accent-ring`, which is the accent when it clears 3:1 against white and zinc-400 when it does not.

**Accent is NOT for:** any background, any body or heading text, card borders, hairlines, the header, the footer, icons, hover fills on secondary elements, the cart bubble, the out-of-stock chip, the PDP/cart/checkout/tracking pages, or "all interactive elements." A merchant can tint this storefront; they can never restructure it (D-09).

#### `--brand-accent-secondary` reserved for exactly two things

1. **The announcement bar fill** — `bg-brand-accent-secondary text-brand-accent-secondary-foreground`, Label/uppercase, one line, truncated. Always readable because the foreground is derived, never chosen.
2. **The trust-bar band wash** — `bg-brand-accent-secondary/8` (Tailwind v4 emits `color-mix(in oklab, …, transparent)`, valid for any CSS colour). An 8% wash of any hue on white stays light, so zinc-950 text on it always clears 4.5:1.

D-10 captures two colours; this is where the second one is visible. Both uses are **always present** (the default document ships non-empty announcement copy), so a merchant never picks a colour that shows up nowhere.

#### What each accent looks like, concretely

| Element | Default accent `#18181B` (ink) | Arbitrary accent, e.g. `#C2410C` (dark orange) | Arbitrary accent, e.g. `#FDE047` (pale yellow) |
|---|---|---|---|
| Hero CTA | Near-black pill, white label — reads exactly like the zinc reference | Orange pill, **white** label (derived: white wins 4.5:1) | Pale-yellow pill, **`#18181B`** label (derived: ink wins) — still legible, never a white-on-yellow break |
| "View all" link | Ink text, underlined | Orange text, underlined — clears 4.5:1, no warning | Pale-yellow text, underlined — **fails 4.5:1**, inline non-blocking warning shown at the picker (D-11), still shipped if the merchant insists; the underline + arrow keep it discoverable |
| Focus ring | Ink ring (clears 3:1 vs white at 17.72:1) | Orange ring (clears 3:1) | zinc-400 (accent fails 3:1 vs white → falls back). **The ring is never unusable.** |
| Selected category chip | Ink fill, white label | Orange fill, white label | Pale-yellow fill, ink label |
| Announcement bar | zinc-500 strip, white label | secondary colour strip, derived label | secondary colour strip, derived label |

**Why the ring is auto-fixed instead of warned about:** D-11's non-blocking warning is correct for a *taste* judgement (an accent link that is hard to read is the merchant's call). A focus ring is an accessibility mechanism under WCAG SC 1.4.11 / 2.4.11, on a route tree that includes **checkout**. It is not merchant-discretionary. The derivation is three lines beside `accentForeground()` and removes the failure mode entirely. The D-11 inline warning for the 3:1 non-text case is still shown — it is now informational rather than load-bearing.

**Contrast floors (unchanged, non-negotiable):** body 4.5:1, Heading/Display 3:1, focus ring 3:1 against the adjacent surface, non-text marks 3:1. Hero text over a photo relies on the scrim — see § S1.

## Motion Language (TMPL-02)

The reference's entire motion vocabulary is `opacity` + `translateY` + one easing curve + a stagger. All of it is CSS. **No motion library** (`04-RESEARCH.md` § Don't Hand-Roll).

### Tokens — declared once, inside the storefront scope

```css
[data-surface="storefront"] {
  /* …tokens above… */
  --motion-ease: cubic-bezier(0.16, 1, 0.3, 1);  /* expo-out, used EVERYWHERE */
  --motion-quick: 200ms;    /* colour/opacity transitions */
  --motion-reveal: 400ms;   /* section and grid reveals */
  --motion-hero: 700ms;     /* hero cascade */
  --motion-hover: 700ms;    /* image scale on hover */
  --motion-stagger: 50ms;   /* per child in a grid or a column set */
}

@media (prefers-reduced-motion: reduce) {
  [data-surface="storefront"] *,
  [data-surface="storefront"] *::before,
  [data-surface="storefront"] *::after {
    animation-duration: 1ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: 1ms !important;
    scroll-behavior: auto !important;
  }
}
```

The reduced-motion block is an **accessibility floor, not an optimisation**. It ships in the same task as the tokens.

### When to use which utility combination

| Purpose | Class string | Notes |
|---|---|---|
| Section reveal on scroll | `animate-in fade-in slide-in-from-bottom-4 fill-mode-both ease-[var(--motion-ease)] animation-duration-[var(--motion-reveal)]` | Applied by `<Reveal>` **only once the element enters the viewport** — `animate-in` fires on mount, not on scroll |
| Hero cascade (on mount, above the fold — **no `<Reveal>`**) | same combination at `animation-duration-[var(--motion-hero)]`, with `delay-0` / `delay-200` / `delay-[400ms]` / `delay-[600ms]` on eyebrow / headline / body / CTA | The hero is already in view; wrapping it in an observer costs a visible blank frame |
| Grid / column stagger | the reveal combination + `style={{ animationDelay: \`calc(var(--motion-stagger) * ${Math.min(index, 7)})\` }}` | Index capped at 7 (350ms) so a 40-product grid does not animate for two seconds. An inline numeric/`calc` style is not a colour — ban #1 is unaffected |
| Product image hover | `transition-transform duration-[var(--motion-hover)] ease-[var(--motion-ease)] group-hover:scale-105` on the `<Image>`, with `overflow-hidden` on the tile | Reference value: 1.05 |
| Icon hover (trust items, CTAs) | `transition-transform duration-[var(--motion-reveal)] ease-[var(--motion-ease)] group-hover:scale-110` | Reference value: 1.1 |
| Colour / opacity transitions (links, buttons, chips) | `transition-colors duration-[var(--motion-quick)] ease-[var(--motion-ease)]` | The easing is the same curve as everything else — that consistency is the "language" |
| Sticky header translucency | `bg-background/80 backdrop-blur-sm border-b border-border` | Static, no animation |

### `<Reveal>` — the one client component this needs

`src/app/s/[slug]/sections/reveal.tsx`, `"use client"`, ~25 lines.

| Rule | Value |
|---|---|
| Mechanism | `IntersectionObserver`, `threshold: 0.1`, `rootMargin: "0px 0px -10% 0px"` |
| One-shot | `unobserve()` on first intersection. A section that re-animates on scroll-up is a distraction, not a delight. |
| Reduced motion | If `window.matchMedia("(prefers-reduced-motion: reduce)").matches`, render **visible with no animation classes** from the first frame |
| No-JS / no-IO | Render **visible**. The default state is visible-and-unanimated; the observer *adds* the animation. A reveal that hides content when JS fails is a blank page. |
| Wrapper | `<div>` with no styling of its own — it must not introduce a layout box that changes the section's spacing |

**Descope path (documented, not the default):** if `<Reveal>` slips, drop the observer and let every section animate on mount. Acceptable on a slow connection where the page arrives at once. Do **not** descope to "no motion at all" — the motion language is a TMPL-02 deliverable.

## Interaction & State Contract

### As-you-type (D-07) — the differentiator, spelled out

| Rule | Value |
|---|---|
| Dispatch | Every keystroke, every colour change, every select change dispatches to the reducer **immediately — no debounce.** |
| Push to preview | Every reducer action re-posts the whole document + tokens over `postMessage` with an **exact** `targetOrigin`. There is **no network in the loop.** |
| First paint | The iframe server-renders the **published** document so the pane is never blank while the handshake completes. |
| Persistence | **Explicit `Save`, not autosave.** D-07's "instant" promise is about the preview, not about persistence; autosaving experimental edits on a flaky mobile connection creates more support questions than it prevents. |
| Leave guard | `beforeunload` when dirty. |
| Reorder | Instant in the rail **and** in the preview. `move-up` at index 0 and `move-down` at the last index are silent no-ops, never errors. |

### The four states, on every new surface

| State | Requirement |
|---|---|
| Loading | Server-rendered routes get a `loading.tsx` `skeleton` matching the final shape. The preview gets the flagship-shaped silhouette above. Buttons swap to a `…` label, disabled, width retained. **No full-page spinners anywhere.** |
| Empty | `product-grid` with zero products → the in-section dashed block. The section list is never empty (the template is fixed). The preview is never empty (published, or registry defaults). |
| Error | Blocking errors are a destructive `alert` **plus** `aria-invalid` on the offending field. Never a toast alone. The preview-handshake failure is non-destructive (the draft is safe) and is styled as a plain `alert`. |
| Success | A navigation is the success signal (branding submit → storefront). A stay-on-page action gets a toast (publish). A storefront state change is a page re-render, not a toast. |

### Optimistic updates

| Action | Optimistic? | Why |
|---|---|---|
| Reorder / edit a field in the editor | **Yes**, entirely client-side | It is draft state in the browser; nothing has been asked of a server yet |
| Save draft | **No** | The server may refuse on the entitlement gate |
| Publish | **No** | It changes what customers see; the strict parse may refuse it |
| Logo upload | **No** (per-tile progress states instead) | R2 + Sharp can fail |

### Accessibility floor (inherited, non-negotiable)

- Every input has a visible `<label>`.
- Visible focus ring on every interactive element: `--ring` on surfaces 2/3, `--brand-accent-ring` on surface 1, ≥2px, ≥3:1.
- 44px minimum touch target everywhere; 48px on storefront section CTAs.
- Reorder announcements, save/publish status, copy confirmations and the preview-loading state are `role="status" aria-live="polite"`.
- Full keyboard path through the branding form, the section list (including reorder), and the settings panel. Tab order matches visual order.
- Colour is never the only signal: the "View all" link carries an underline and an arrow; the selected section row carries `aria-current` and a left rule, not just a fill; the selected category chip carries a fill **and** `aria-pressed`.
- `prefers-reduced-motion: reduce` disables every animation and transition on the storefront (§ Motion) and switches preview scrolling to `auto`.
- Hero background images are decorative (`alt=""`); product images carry the product name; the logo carries the store name.
- Every new route sets a meaningful `<title>` through the root layout's `%s · EINORT` template.

### Responsive strategy

Mobile-first, **designed at 360px first**. The editor is the one surface that genuinely cannot show its two panes on a phone — it uses an explicit `Edit`/`Preview` toggle rather than a squeezed side-by-side. No modals on the storefront. No drawers, no carousels, no parallax, anywhere.

## Copywriting Contract

**Voice:** direct, second person, no exclamation marks, no "Oops"/"Whoops", no emoji, no ALL-CAPS shouting. Errors say what happened and what to do next. Storefront copy addresses the **shopper**; dashboard and onboarding copy address the **merchant** — never mix.

**All copy lives in `src/lib/strings.ts`.** New namespaces: `strings.branding`, `strings.editor`, `strings.flagship`; plus `strings.dashboard.nav.storefrontEditor`. **Zero user-facing literals in JSX** — the source-scanning contract tests fail the build otherwise.

**Never write:** a promise the product cannot keep (no newsletter, no delivery guarantee, no "Verified"), an industry-specific claim before Phase 5 ships one, an internal name (`/s/`, `scopedDb`, `PAYMENT_CLAIMED`, "section registry"), or fashion-flavoured default copy (D-04).

## Design-Distinctiveness Gate (closes STATE.md's named Phase 4 risk)

> *"design-distinctiveness has no objective completion signal — the side-by-side 'would a stranger think these are the same product' check must be built into this phase's definition of done explicitly."* — `.planning/STATE.md` § Blockers/Concerns

It is now built in. The planner must schedule this as an explicit **`checkpoint:human-verify`** task in the phase's final wave. Seven checks, five of them objectively decidable.

| # | Check | Objective? | Pass condition |
|---|---|---|---|
| 1 | **The stranger test.** Two seeded demo stores, different logos, different accents, different copy, screenshotted side by side at 360px and 1440px. Show them to someone who has not seen the project and ask, verbatim: *"Are these two different shops, or the same shop twice?"* | No — the one genuinely human check | The answer is "different shops," unprompted, and they can name **three** differences without help |
| 2 | **Surface separation.** The flagship home beside the merchant dashboard, same screenshot | Yes | Zero shared palette, zero shared radius, zero shared heading face. A stranger asked *"are these the same product?"* should say "related, but clearly different parts" |
| 3 | **Five rhythms at 360px.** Scroll the home page on a 360px viewport | Yes | Photo hero → washed band → white grid → ink band → white contact. **No two adjacent sections share a background treatment.** At least four product tiles visible. |
| 4 | **Type hierarchy.** Measure the rendered hero headline and the body | Yes | 64px at ≥768px, 40px at 360px, line-height 1.05, `tracking-tighter`, weight **600 not 700**, and a ≥2.5× size ratio to the 16px body |
| 5 | **Motion.** Load the page; then toggle `prefers-reduced-motion: reduce` in devtools and reload | Yes | First load: the hero cascade is visible and sections reveal on scroll. Reduced motion: **nothing animates, nothing transitions, no layout shift, no hidden content** |
| 6 | **Token hygiene.** `npm run test:unit && npm run lint && npm run typecheck` | Yes | Green. Specifically: zero literal colours, zero palette utilities, no `font-heading` or `gold-accent` or `--success` under `src/app/s/**`, no `data-surface="storefront"` outside it, and no `brand-accent` utility under `(dashboard)` |
| 7 | **Accent extremes.** Re-render the home page with three accents — `#18181B`, `#C2410C`, `#FDE047` | Yes | Every CTA label is legible at all three; the focus ring is visible at all three; no section's structure changes; the page never stops reading as zinc-monochrome-with-a-tint |

A phase gate that passes 6/7 with #1 failing is **not** a pass. The stranger test is the requirement (TMPL-01 says "genuinely polished, portfolio-quality"); the other six exist so that failing it is diagnosable.

## Decisions Made Under "Claude's Discretion"

`04-CONTEXT.md` § Claude's Discretion and `04-RESEARCH.md` § Open Questions left these open. They are settled here so no one settles them at build time.

| Item | Decision | Rationale |
|---|---|---|
| WCAG threshold and calculation (D-11) | 4.5:1 for accent-as-link text vs white (**warn**); 3:1 for non-text marks (**warn**); button foreground **auto-derived**, never warned; focus ring **auto-derived with a zinc-400 fallback**, never warned | Taste is warnable; accessibility mechanisms on a route tree containing checkout are not |
| Discard-draft control | **Ship it.** `Discard` (ghost) in the publish bar + a destructive `alert-dialog` | Four lines of server code (`draft = published`); without it a merchant who experiments has no way back |
| Onboarding step ordering | `/onboarding/plan` → `/onboarding/branding` → storefront, gated on `industry === null` | Extends the existing DAL redirect ladder by one rung instead of inventing a second mechanism; nobody uploads a logo before completing signup |
| Segment labels and icons | The six rows in § Onboarding | lucide names verified: `shirt`, `smartphone`, `sparkles`, `shopping-basket`, `sofa`, `store` |
| Block types | Exactly one repeatable block type — `trust-item`, 1–4 per `trust-bar`, modelled as a typed array **inside** that section's settings | Pattern 9; inventing more block types to look thorough is padding |
| Plus Jakarta Sans 700 (Open Q5) | **Not added.** Display presence comes from 64px + `tracking-tighter` + 1.05 line-height | Three prior UI-SPECs lock two weights; a third font file on the LCP path for a low-end-Android market is a real cost |
| Scroll reveal (Pattern 10 a-vs-c) | **(a)** — a ~25-line `<Reveal>` with IntersectionObserver. Documented descope to (c) | Verified support; degrades to visible-and-unanimated with no JS |
| Section CTA radius | **Pill** (`rounded-full`) for the three section CTAs; transactional CTAs (Add to cart, Checkout, I've paid) keep `rounded` (0.25rem) | The reference's own language, and marketing CTAs vs money buttons are deliberately different affordances. Do not "make them consistent." |
| Editorial-band CTA colour | `bg-background text-foreground`, **never the accent** | The default accent is ink; ink-on-ink is invisible and no derivation fixes a fill-vs-fill collision |
| Secondary accent's role | Announcement bar fill + trust-bar 8% wash. Both always present. | D-10 captures two colours; a colour with no visible role is a pointless question at onboarding |
| Footer link columns | **Removed** from the reference's footer (deviation 3) | V1 has no About/Help/Policy pages; dead links on a real customer's storefront are worse than a clean footer |
| Product tile aspect | `aspect-[4/5]` on the grid section; PDP gallery stays `aspect-square` | The reference's grid proportion; a PDP gallery benefits from square (zoom/thumbnail parity), and 03-UI-SPEC already shipped it |
| Preview click-to-select | **Not this phase.** The rail is the only selection surface; preview anchors are intercepted and inert | D-05/D-06 keep the editor surface small; a half-built click-to-select reads as a bug |
