Write the header naming this as the ONE place a section type maps to a component. State why it
is a `switch` and not a `Record<string, { schema, Component }>` registry: a `Record`-keyed
registry cannot be mapped over without a cast, because TypeScript cannot prove
`REGISTRY[section.type].Component` accepts `section.settings`. The `switch` proves it. Cite
`state-machine.ts` lines 62-70 as the codebase's existing statement of the same drift-detection
intent, and state the consequence explicitly: adding a sixth section type to the union is a
compile error HERE, which is exactly what makes a half-added section impossible to ship.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Merchant-authored settings -> rendered links and images | `viewAllHref`, `ctaHref` and image keys all originate in the editor |
| Server-authoritative catalogue -> section props | Prices, stock and product identity must never come from a section's settings |
| Public storefront render path | Anonymous, unauthenticated, unlimited traffic |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-07 | Tampering | A storefront link carrying the internal `/s/` prefix | mitigate | Every href in these components is origin-relative (`/`, `/?category=`, `/p/{slug}`), matching `store-header.tsx`'s canonical statement for the route tree. `tests/unit/storefront-link-prefix.test.ts` fails the build if the prefix returns, and the fix is always to make the link relative — never to relax the `/s/` check in `src/proxy.ts`, which is what makes a direct `/s/*` request a hard 404. |
| T-04-25 | Tampering | Price, stock or product identity arriving through section settings | mitigate | `product-grid` settings carry only `heading`, `viewAllLabel`, `viewAllHref` and `itemCount` — no price, no product id, no stock. Products come from `data`, which plan 04-10 populates server-side from `scopedDb` through the existing storefront queries. `itemCount` is a closed `4 \| 8 \| 12` union used only as a slice bound. |
| T-04-15 | Tampering | `product.imageKey` rendered as an image `src` | mitigate | Product image keys come from `ProductImage.storageKey` written by the Phase 3 pipeline, never from editor settings; `next.config.ts` `remotePatterns` restricts the host `next/image` will fetch, and `publicUrlFor` (server-side) already refuses an `/original` key. |
| T-04-26 | Tampering | An outbound `target="_blank"` link on the contact CTA | mitigate | `rel="noopener noreferrer"` on the WhatsApp anchor, asserted by an acceptance criterion. The href itself is built server-side in plan 04-10 from the merchant's stored payment settings, not concatenated in the browser. |
| T-04-12 | Denial of service | A sixth section type reaching production half-wired | mitigate | The renderer's `switch` has no `default` arm, so an added union member fails `npm run typecheck` at this file. Verified by a temporary-addition acceptance criterion. No try/catch swallows the failure. |
| T-04-11 | Denial of service | A write on the public storefront render path | mitigate | Nothing in this directory performs I/O of any kind — no `scopedDb`, no `fetch`, no cache write. The zero-products branch renders an in-section dashed block from existing copy rather than triggering a lazy seed. Pitfall 11 verbatim. |
| T-04-SC | Tampering | npm installs | accept | This plan installs nothing. `lucide-react` supplies every icon and deliberately has no WhatsApp glyph — `MessageCircle` plus the word is the answer, not a brand-icon package. |
</threat_model>
