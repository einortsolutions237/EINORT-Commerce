<objective>
Ship ONB-02, ONB-03 and ONB-04 as one screen: the branding step that turns a merchant who has just picked a plan into a merchant with a live, published, branded storefront.

Purpose: this is the phase's payoff moment and the product's core promise — "a merchant picks an industry, adds a logo and a few products, and within minutes has a storefront that looks like it cost them money to build." The step extends the existing DAL redirect ladder by exactly one rung rather than inventing a second gating mechanism, and its submit is a single `saveBranding` call that writes `published` directly, so the store is live the instant the action returns.

Output: the ladder rung, the plan-step redirect fix, and the `/onboarding/branding` route.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser -> `saveBranding` Server Action | Untrusted body, reachable by direct POST with no page load |
| Browser -> `requestLogoUpload` + R2 PUT + finalize | A three-hop upload where each hop is independently reachable |
| Onboarding surface -> storefront design system | Surface 2 must never take a storefront token, and must never colour its own chrome with the merchant's accent |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-04 | Elevation of privilege | A forged `tenantId` in the branding payload | mitigate | `saveBranding`'s schema (plan 04-09) has exactly five fields and none is a tenant id; the target is `session.session.activeOrganizationId`, and `scopedDb` stamps `tenantId` last into both halves of both upserts. The form has no field to send. |
| T-04-13 | Elevation of privilege | `Organization.industry` set by a request body | mitigate | `industry` is `input: false` in the Better Auth organization `additionalFields` (plan 04-01), so `/organization/update` cannot set it. The form's value is validated through `isIndustrySegment` server-side before `platformDb.organization.update` runs. |
| T-04-01 | Information disclosure / Tampering | The logo upload's three hops | mitigate | `requestLogoUpload` (plan 04-05) recomputes the key from `ctx.tenantId` and a server-generated uuid; the client names neither a namespace nor a key nor a path. The finalize route re-checks `ctx.canWrite` and picks its Sharp preset from the server-side `KIND_PRESET` map. The client-side content-type allowlist here is a courtesy mirror and is never the authority. |
| T-04-10 | Tampering | The logo key landing on `Organization.logo` | mitigate | The form submits `logoKey`, and `saveBranding` writes it to `StorefrontTheme.logoKey`. `Organization.logo` is a Better Auth CORE field that `input: false` cannot protect and is left unwritten by this phase. |
| T-04-09 | Tampering / XSS-adjacent | The two accents reaching a `style` attribute in the sample chips | mitigate | The form schema reuses `hexColorSchema` from `@/server/theming/schema`, the same regex the server enforces, so an invalid value never reaches `style={{ backgroundColor: value }}`. The server re-validates independently and the storefront layout validates AGAIN on read (plan 04-10) — three passes, because React's `setProperty` does not sanitise. |
| T-04-02 | Tampering | The merchant's accent colouring surface-2 chrome | mitigate | The only permitted use on this page is the sample chip, per 04-UI-SPEC's named exception. No button fill, link, focus ring, border, badge or active state takes a merchant value; ban #5 (plan 04-04) fails the build on a `brand-accent` utility here, and an acceptance criterion greps for `data-surface` and `brand-accent` returning 0. |
| T-04-27 | Denial of service (self-inflicted) | The branding page or action looping against its own ladder rung | mitigate | Neither `page.tsx` nor `saveBranding` calls `requireMerchantContext`. Both resolve the session directly, mirroring `/onboarding/plan` and `selectPlan` — the precedent `context.ts`'s own comment already documents. Asserted by a `grep -c "requireMerchantContext"` acceptance criterion returning 0. |
| T-04-03 | Information disclosure (accessibility) | A merchant choosing an unreadable accent | mitigate | Split deliberately: the accent-as-LINK case gets D-11's non-blocking `role="status"` warning (a taste judgement the merchant may make badly), while the button foreground and the focus ring are DERIVED server-side and never warned about. The secondary accent gets no warning because its foreground is always derived — warning about an impossible problem trains merchants to ignore warnings. |
| T-04-SC | Tampering | npm installs | accept | This plan installs nothing. `react-hook-form`, `@hookform/resolvers`, `lucide-react` and the shadcn primitives are all already installed. |
