<objective>
Build the theming domain's server side: the one read that a public storefront makes, and the five writes that are the only way instance data ever changes.

Purpose: this is where D-08's draft/publish split becomes atomic and where EDIT-03's gate becomes real. The document-per-page model exists precisely so publish is `update({ data: { published: draft } })` on one row — `$executeRaw` is banned repo-wide and Prisma cannot express column-to-column assignment, so any other shape would be an N-row loop whose correctness depends on the loop being right. It is also where two traps live: the public read path must never write and must never throw, and `saveBranding` must NOT be built with `merchantAction`.

Output: `errors.ts`, `queries.ts`, `actions.ts` under `src/server/theming/`.
</objective>

`assertCanEditStorefront(ctx, strings.editor.starterViewOnly)` FIRST, before any DB call.
Then, in one `scopedDb(ctx.tenantId).$transaction`: update `storefrontPage.draft` and

**Leave `published` and `publishedTokens` byte-identical** — that is the whole point of D-08 and

is missing.

**`publishStorefront`** — schema `z.object({})`. Gate, then one `$transaction`:
read both rows; `pageDocumentSchema.parse(page.draft)` and `themeTokensSchema.parse(theme.draftTokens)`
— **strict `parse`, NOT `safeParse`** — then two single-row updates setting
`published` / `publishedTokens` and `publishedAt`.

PARSE BEFORE PROMOTING is the one gate that stops a draft written under an older registry from
becoming the live storefront. Write that reasoning into the file: a parse failure HERE is a
refused publish the merchant can act on; a parse failure on the public read path is a customer
looking at nothing. This asymmetry (strict on write, lenient on read) is deliberate and must not
be "made consistent."

Two rows, one statement each, one transaction — no half-published state is representable and no
raw SQL is required, which matters because `$queryRaw`/`$executeRaw` are banned repo-wide by
`no-restricted-syntax`. Record that constraint in the header as the reason the document model
was chosen. Then `revalidatePath("/dashboard/storefront-editor")` so the publish-bar status line
does not stay stale (the `payments/actions.ts` precedent).

**`discardDraft`** — schema `z.object({})`. Gate, then
`update({ data: { draft: page.published ?? flagshipDefaultDocument(), draftUpdatedAt: new Date() } })`
and the equivalent for `draftTokens`. It **OVERWRITES**, never deletes — D-08's no-hard-delete
convention applies to merchant-owned data, and the isolation suite asserts the row survives.

**`ensureStorefrontSeeded`** — schema `z.object({})`. **No editor gate** (a Starter merchant must
be able to open a working editor; the gate is on saving and publishing, not on existing).
Idempotent `upsert` PAIR in one transaction:
- `storefrontTheme.upsert({ where: { tenantId: ctx.tenantId },
  create: scopedCreateData<…>({ templateKey: "flagship-fashion", logoKey: null,
  draftTokens: tokens, publishedTokens: tokens, publishedAt: now }), update: {} })`
- `storefrontPage.upsert({ where: { tenantId_pageType: { tenantId: ctx.tenantId, pageType: "home" } },
  create: scopedCreateData<…>({ pageType: "home", draft: document, published: document,
  publishedAt: now }), update: {} })`

`update: {}` on BOTH — never clobber an existing merchant's work. `upsert` rather than `create` is
what makes this safe against a double submit and against a legacy organization self-healing on
first editor visit. `scopedCreateData<T>()` is REQUIRED on both `create` halves because
tenant-scoped models declare `tenantId` required with no default, and `scopedDb` stamps `tenantId`
into both the `where` and the `create` halves of an upsert.

Reproduce, adapted, the `payments/actions.ts` header block: NO TRIAL CHECK AND NO TENANT ID LIVE
IN THESE HANDLERS. `mode: "write"` IS the read-only gate; re-checking it here would create a
second place for D-08 to drift. And no schema in this file contains a `tenantId`, a price, a
product id or a storage URL — the target is always `ctx.tenantId`, resolved from the session
before the handler runs.

Also put Pattern 12's rule in the header: **a route that can take money or change order state is
never section-rendered.** These actions only ever touch `pageType: "home"`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser -> theming Server Action | Untrusted body; reachable by direct POST with no page load |
| Better Auth `/organization/update` -> Organization row | Any signed-in merchant can POST an organization update body |
| `scopedDb` -> the two new tenant-scoped tables | The only sanctioned door; an unregistered model would run unscoped |
| Public storefront render -> database | Anonymous, unauthenticated, unlimited traffic |
