## Phase Goal

ROADMAP goal (verbatim): *A merchant can list a product and a customer can complete a full purchase through to a merchant-confirmed order, with stock, order state, and payment-claim integrity guaranteed server-side.*

Derived user story (same derivation 03-01 through 03-05 committed):
**As a** Cameroonian merchant and their customer, **I want to** list products and complete a purchase through WhatsApp, Mobile Money claim, or cash on delivery, **so that** the sale is recorded, the stock is correct, and the payment status is auditable.

**This plan's slice:** a shopper finishes buying. They review a basket with a real total, type their name and phone, pick one of the three ways this market actually pays, and get an order — with a link they can come back to. After this plan a WhatsApp order and a cash-on-delivery order are complete round trips from browse to merchant confirmation.

<objective>
Build the B3 cart review page and the B4 checkout page with its three-path selector, plus the `submitCheckout` action that rate-limits, deduplicates, reads the cart from Redis, calls `placeOrder`, and hands back the tracking link and (on the WhatsApp path) the `wa.me` deep link.

Purpose: CHK-02 is the requirement this phase exists to satisfy in a Cameroonian market — three payment paths, none of them a PSP. D-01 makes the WhatsApp path a real order record before the deep link opens, which is what keeps the merchant's order list and the ORD-05 audit trail complete regardless of channel.
Output: `/s/[slug]/cart`, `/s/[slug]/checkout`, `src/server/checkout/actions.ts`, two loading skeletons and one isolation test.
</objective>

    Create `src/server/checkout/actions.ts` (`"use server"`) exporting one function, `submitCheckout`. It is NOT a `merchantAction` — the caller is an anonymous shopper. Validate with a Zod schema carrying `slug`, `customerName`, `customerPhone`, `deliveryAddress` (nullable), `customerNote` (nullable), `channel`, `operator` (nullable, only meaningful on `MANUAL_TRANSFER`) and `idempotencyKey`. **There is no `items` field and no money field of any kind**: the line items come from Redis and every amount comes from the database.     Handler order:
    1. `orderPlacementLimiter` keyed on `callerIp(await headers())`. On a limit hit, return the rate-limited failure copy. The limiter fails open on an Upstash outage, so a blip degrades throttling rather than checkout.
    2. `resolveTenantBySlug(slug)`; a null tenant returns a not-found failure.
    3. `recallOrderForKey(idempotencyKey)` — when it returns an order id, look that order up, and return its existing tracking outcome instead of placing again. This is what makes a double tap on a slow network produce one order rather than two and one stock decrement rather than two.
    4. Read the cart cookie, `readStoredCart`, and refuse an empty or tenant-mismatched cart with the appropriate failure. The stored `items` become `PlaceOrderInput.items` unchanged — ids and quantities only.
    5. `getPaymentSettings(tenant.id)` and `resolvePaymentPaths(...)`. **Refuse a channel the merchant has not configured**, with a failure that tells the shopper to choose another method. This is the server half of the rule that unconfigured paths are not rendered: the markup hiding a card is a courtesy, and this check is the authority. On `MANUAL_TRANSFER`, also refuse an operator the merchant has not configured (D-16).
    6. Normalize `customerPhone` with `normalizeCameroonMsisdn`; refuse a null result with the field error. Require `deliveryAddress` only when the channel is `CASH_ON_DELIVERY` — B4 is explicit that the requirement appears with the selection rather than sitting there greyed out.
    7. `placeOrder(tenant.id, input)`. On `OutOfStockError`, return the approved out-of-stock copy (*Someone just bought the last one. We've updated your cart — check it and try again.*) and leave the cart intact so the shopper can adjust it; on `UnavailableItemError`, return the removed-item copy.
    8. `rememberOrderForKey(idempotencyKey, orderId)`, then `clearStoredCart(cartId)`.
    9. Build the outcome. On every channel return `{ orderId, orderNumber, trackingPath: "/s/{slug}/order/{token}" }` — the plaintext token is used here and never persisted. On `WHATSAPP` additionally build the deep link with `buildOrderMessage` and `buildWhatsAppOrderLink(settings.whatsappNumber, message)`, with the tracking URL near the top of the message because some clients truncate a long `text`. D-01 is satisfied by construction: the order and its token already exist by the time this link is returned, so the sale is recorded regardless of whether the shopper ever opens WhatsApp.

    Create `tests/isolation/checkout-paths.test.ts`:

    - Submitting `MANUAL_TRANSFER` for a tenant whose `MerchantPaymentSettings` has neither an MTN nor an Orange number is refused and writes no order.
    - Submitting `MANUAL_TRANSFER` with `operator: "ORANGE_MONEY"` when only MTN is configured is refused (D-16).
    - The same `idempotencyKey` submitted twice produces one `Order` row, one stock decrement and the same tracking outcome both times.
    - A cart whose stored `tenantId` belongs to tenant B is refused under tenant A and writes no order.
