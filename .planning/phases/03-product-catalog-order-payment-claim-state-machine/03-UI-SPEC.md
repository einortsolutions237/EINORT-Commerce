## ⚠️ READ THIS FIRST — THIS PHASE HAS TWO DESIGN SYSTEMS, NOT ONE

Phase 3 is the first phase that builds real UI on **both** product surfaces at once. They are governed by **two different, already-established design references**. Mixing them is the exact mistake that already cost this project one retrofit (`260823-gu4`, where Phase 1's zinc storefront palette leaked onto the entire merchant platform). It must not happen again.

| Surface | Route tree | Governing reference | Palette | Heading face | Radius |
|---|---|---|---|---|---|
| **A — Merchant platform** | `src/app/(dashboard)/dashboard/**` | `.planning/design-references/EINORT-COMMERCE-FRONT-END-MERCHANT-PLATFORM.md` | Blue brand / gold accent / slate surface | **Outfit** (`font-heading`) | `0.75rem` |
| **B — Customer storefront** | `src/app/s/[slug]/**` | `.planning/phases/01-multi-tenant-foundations-domain-resolution/01-UI-SPEC.md` § Color (zinc-monochrome DTC/editorial) | Zinc monochrome, ink-as-accent | **Plus Jakarta Sans** (`font-sans`) — Outfit is deliberately NOT used | `0.25rem` |

**The single rule:** *check which route tree you are in before you pick a token.* A reference is scoped to a surface, not to the product.

### Enforcement mechanism (build this before any storefront page)

`src/app/globals.css`'s `:root` currently resolves every semantic token to the **merchant** (slate/blue/gold) values. Storefront pages that write `bg-background text-foreground` today therefore silently render in merchant colours. Fix this once, structurally, rather than by discipline:

1. Add a scoped token block to `globals.css` (below `:root`, above `.dark`) that re-declares the **complete** zinc set under an attribute selector:
   ```css
   /* Surface B — customer storefront (src/app/s/[slug]/**) ONLY.
      Zinc-monochrome DTC/editorial, per 01-UI-SPEC.md § Color.
      Deliberately NOT the merchant platform's blue/gold/slate. */
   [data-surface="storefront"] {
     --background: oklch(1 0 0);
     --foreground: oklch(0.141 0.005 285.823);
     /* …and every remaining row of § B. Color — all 20 tokens, verbatim, omit none. */
   }
   ```
   **Completeness is the entire mechanism.** A semantic token that is *not* re-declared inside this selector inherits the merchant `:root` value, so one omitted `--card`, `--input` or `--primary-foreground` silently puts slate and blue back on the storefront — the exact leak this section exists to prevent. § B. Color below enumerates the full set, **one token per row, one value per row**; copy it whole rather than picking from it.
2. `src/app/s/[slug]/layout.tsx` wraps `{children}` in `<div data-surface="storefront" className="flex min-h-full flex-1 flex-col">`.
3. Every storefront page then uses the **same semantic utilities** (`bg-background`, `text-foreground`, `bg-primary`, `border-border`) and gets zinc for free.

### Four bans that make the split checkable, not aspirational

| # | Ban | Scope | Guard |
|---|---|---|---|
| 1 | No literal colour value (hex, `oklch(`, `rgb(`) in any component | both | grep `src/app` + `src/components` |
| 2 | No Tailwind palette utility (`zinc-*`, `slate-*`, `blue-*`, `amber-*`, `emerald-*`, `red-*`) | both | grep — semantic tokens only |
| 3 | No `font-heading`, no `gold-accent`, no `--success` under `src/app/s/**` | Surface B | grep `src/app/s` |
| 4 | No `data-surface="storefront"` outside `src/app/s/**` | Surface A | grep `src/app/(dashboard)` |

Add these four as a single `tests/unit/surface-token-isolation.test.ts`, in the spirit of the existing `tests/unit/no-tenant-id-param.test.ts`. A grep test is the only thing that survives a future contributor who has not read this file.

### Scope note on the open storefront-source question

The merchant-platform reference flags that the storefront has **two** candidate design sources and that the choice is a deliberate Phase 4–5 decision. That decision stays open. This contract does **not** settle it — it settles only that *Phase 3's storefront pages ship in the zinc/editorial direction as a plain, on-brand placeholder*, per `03-CONTEXT.md` § Canonical References. They are not a fully art-directed storefront; Phase 4's Theme→Section→Block system is what produces that. Build them so Phase 4 can replace them without regret.

## Spacing Scale (shared — one scale governs both surfaces)

The 4-point scale is inherited verbatim from `01-UI-SPEC.md` / `02-UI-SPEC.md`. Spacing is **not** where the two surfaces differ; colour, radius and heading face are.

| Token | Value | Usage in Phase 3 |
|---|---|---|
| xs | 4px | Icon-to-text gap; chip inner gap; thumbnail strip gap |
| sm | 8px | Label → input gap; variant-matrix cell padding; badge-to-text gap |
| md | 16px | Default gap between form fields; card inner padding on mobile; product-grid gap on mobile; table row vertical padding |
| lg | 24px | Card inner padding ≥sm; gap between form-section cards; product-grid gap ≥md; claim-card inner padding |
| xl | 32px | Page gutter; page header → content gap |
| 2xl | 48px | Vertical rhythm between major page blocks (e.g. PDP details → description) |
| 3xl | 64px | Top/bottom page padding on the tracking page and the empty-cart page |

**Exceptions (dimensions, not spacing tokens):**

| Exception | Value | Why |
|---|---|---|
| Minimum touch target | **44px** (`min-h-11`) on every interactive element, both surfaces | Inherited, non-negotiable: mobile-first, low-end Android market |
| Storefront primary CTA height | **48px** (`min-h-12`) full-width — Add to cart, Checkout, place-order, "I've paid" | These are the money buttons on a phone held one-handed |
| Image tiles | 40px (list row thumb) · 56px (PDP thumbnail strip) · 64px (cart line item) · 96px (claim screenshot thumb) | Fixed dimensions |
| Content column widths | Surface A list/table pages `max-w-5xl`; Surface A forms & settings `max-w-3xl`; Surface B checkout/cart/tracking `max-w-lg`; PDP `max-w-6xl`; catalog `max-w-7xl` | Layout constants |
| Sidebar rail width | 256px expanded / 0 (off-canvas sheet) below `lg` | See § Navigation Shell |
| Body paragraph cap | `max-w-prose` wherever body copy runs as a paragraph | Inherited |

Any value outside this table is a contract violation.

## A. Typography

Inherited verbatim from `02-UI-SPEC.md`. **Exactly 4 sizes, exactly 2 weights (400, 600).** No 300, no 500, no 700, no italics.

| Role | Size | Weight | Line Height | Face |
|---|---|---|---|---|
| Body | 16px | 400 | 1.5 | `font-sans` (Plus Jakarta Sans) |
| Label | 14px | 600 | 1.4 | `font-sans` |
| Heading | 24px | 600 | 1.2 | **`font-heading`** (Outfit) |
| Display | 36px | 600 | 1.1 | **`font-heading`** (Outfit) |

Role assignment for this phase:

| Role | Where it appears |
|---|---|
| Display | **Unused.** Reserved for the wordmark. A product price or an order total is not a Display. |
| Heading | Page headings (`Products`, `Orders`, `Payment claims`, `Payment settings`); `CardTitle` on every form-section card; the claimed amount on a claim card; the order total on the order-detail page |
| Label | Table column headers; form field labels; every status badge; nav items; the product-count meter; timestamps; the reference string; helper text that names a constraint ("6 digits") |
| Body | Everything else — descriptions, helper text, empty-state bodies, error text, audit-trail entries |

**Numerals:** every XAF amount and every stock count renders with `tabular-nums`, so a column of prices aligns. Transaction references render `font-mono` (`--font-mono` is already declared).

## A. Color

Blue brand / gold accent / slate surface. Values already live in `globals.css` `:root` — **read them from there, do not re-derive.**

| Role | Token | Value | Usage |
|---|---|---|---|
| Dominant (60%) | `--background` | `oklch(0.984 0.003 247.9)` slate-50 | Page field |
| Secondary (30%) | `--card` / `--secondary` / `--muted` | `oklch(1 0 0)` white / `oklch(0.968 0.007 247.9)` slate-100 | Cards, sidebar, table header row, input fill, chips |
| Accent (10%) | `--primary` | `oklch(0.546 0.215 262.9)` brand-600 | See reserved-for list |
| Second accent | `--gold-accent` | `oklch(0.767 0.139 91.1)` gold-500 | **Needs-your-attention only** — see below |
| Destructive | `--destructive` | `oklch(0.577 0.245 27.325)` | Reject action, Disputed state, field errors, cap-exceeded alert. Nothing else. |
| Success | `--success` | `oklch(0.596 0.145 163.225)` emerald-600 | Confirmed / Fulfilled state chips only |
| Hairlines | `--border` | `oklch(0.929 0.013 255.5)` slate-200 | All rules, table dividers, card borders |
| Helper text | `--muted-foreground` | `oklch(0.554 0.041 257.4)` slate-500 | Helper and secondary metadata only, never body copy that carries meaning |

**Accent (`--primary`, blue) reserved for exactly:**
1. The single primary CTA fill per page (`Add product`, `Save product`, `Save payment settings`, `Confirm payment`, `Confirm order`) — **one per page, never two**
2. The active nav item indicator in the sidebar
3. Focus ring (`--ring` = brand-500, one step lighter — do not "tidy" it to brand-600)
4. Inline text links

**Accent is NOT for:** status badges, table headers, icons, hover fills, card borders, or "all interactive elements."

**`--gold-accent` reserved for exactly two things in this phase — this is the tightest budget in the contract:**
1. The pending-claims count badge on the `Payment claims` nav item
2. The `Payment claimed` status chip

Gold means *a human needs to look at this now*. It appears nowhere else. Never a hover, never a border, never a generic highlight. (This is why the retrofit created a separate `--gold-accent` pair instead of repointing shadcn's `--accent`, which is the neutral-hover slot.)

**Colour is never the only signal.** Every status chip carries an icon **and** a text label (WCAG 1.4.1). Contrast floors: body 4.5:1, Heading/Display 3:1, focus ring 3:1.

## A. Navigation Shell (resolves the `260823-gu4` deferred item)

Phase 2's dashboard layout says, in a code comment: *"No sidebar: there is nothing to navigate to yet, and a placeholder nav rail would be Phase 3's decision made early and badly."* Phase 3 is that phase. It adds four destinations. **Nav is now mandatory** — without it `/dashboard/products` is unreachable.

**Decision: adopt the reference's `AppShell` silhouette using the shadcn official `sidebar` block.** Rationale: it ships the off-canvas mobile sheet, keyboard handling and collapse state that a hand-rolled rail would get wrong, and the reference's own layout is a sidebar + header shell.

| Property | Value |
|---|---|
| Component | shadcn official `sidebar` (pulls `sheet`, `tooltip`, `skeleton`, `separator`, `use-mobile`) |
| Breakpoint | Rail visible ≥`lg` (1024px). Below that: off-canvas sheet, trigger is a `panel-left` icon-button at the left of the header. |
| Rail fill | `--sidebar` (white) with a `--sidebar-border` hairline. Not slate-100 — the page field is already slate-50. |
| Items | Overview (`layout-dashboard` → `/dashboard`) · Products (`package`) · Orders (`shopping-bag`) · Payment claims (`banknote`) · Plan (`credit-card` → `/dashboard/plan`) · Payment settings (`settings`) |
| Active item | `--sidebar-accent` fill + `--sidebar-primary` text + `aria-current="page"`. **No blue fill bar** — the accent budget does not cover it. |
| Badge | Only on `Payment claims`, only when pending > 0, `--gold-accent` |
| Header band | Retained from Phase 2: store name (Label) left, `SignOutButton` right, `--border` bottom hairline. Add the sidebar trigger to its left below `lg`. |
| Trial banner | Retained, unchanged, above content on every dashboard route |

Existing pages (`/dashboard`, `/dashboard/plan`) move inside the shell. Their `max-w-3xl` content column is retained; list pages use `max-w-5xl`.

## A. Order-State Display Contract (ORD-01 / D-01 / D-02 / D-03)

**One map, six states, used by both the Orders list and the Order detail page.** Define it once (`src/lib/strings.ts` for the copy + a component-local `Record<OrderState, …>` for the chip config) and never inline a state label.

| `OrderState` | Merchant chip label | Badge variant | Token | Icon (lucide) |
|---|---|---|---|---|
| `ORDER_PLACED` | `New order` | `outline` | `--border` / `--foreground` | `receipt-text` |
| `PAYMENT_PENDING` | `Awaiting payment` | `secondary` | `--secondary` slate-100 | `clock` |
| `PAYMENT_CLAIMED` | `Payment claimed` | **`gold`** (new variant) | `--gold-accent` @ 15% fill, `--gold-accent-foreground` text | `bell-ring` |
| `CONFIRMED` | `Confirmed` | **`success`** (new variant) | `--success` @ 10% fill, `--success` text | `circle-check` |
| `DISPUTED` | `Disputed` | `destructive` | `--destructive` | `triangle-alert` |
| `FULFILLED` | `Fulfilled` | `outline-success` | transparent fill, `--success` border + text | `package-check` |

Emerald appears twice by design: filled = "confirmed", outlined = "done and settled". Same family, further along.

**Two new `badge` variants (`gold`, `success`, `outline-success`) must be added in place to `src/components/ui/badge.tsx`,** following the discipline that file's own header documents for its existing two overrides. Note the diff so a future `shadcn add badge` can re-apply it.

**Per-channel display rule (D-02, load-bearing):**

| `OrderChannel` | Channel chip | Icon | States that can EVER appear |
|---|---|---|---|
| `WHATSAPP` | `WhatsApp` | `message-circle` | `New order` → `Confirmed` → `Fulfilled` |
| `CASH_ON_DELIVERY` | `Cash on delivery` | `truck` | `New order` → `Confirmed` → `Fulfilled` |
| `MANUAL_TRANSFER` | `Mobile Money` (+ operator sub-label `MTN` / `Orange`) | `banknote` | all six |

`Awaiting payment`, `Payment claimed` and `Disputed` **cannot render on a WhatsApp or COD row.** Encode this as a typed map (`Record<OrderChannel, readonly OrderState[]>`) so a WhatsApp row showing "Awaiting payment" is a type error, not a review catch. The channel chip is always rendered next to the status chip — the pair is what makes a two-state WhatsApp order legible beside a six-state transfer order.

**lucide has no WhatsApp glyph.** Use `message-circle` plus the literal text `WhatsApp`. Do **not** install a brand-icon package.

## Interaction & State Contract (both surfaces)

### Every surface declares four states

| State | Requirement |
|---|---|
| Loading | Server-rendered pages: a `skeleton` matching the final layout's shape (grid tiles, table rows, claim cards) via `loading.tsx`. Buttons: label swaps to a `…` variant, `disabled`, width retained (no layout shift). **No full-page spinners anywhere.** |
| Empty | Every list surface has an authored empty state (heading + body + CTA-or-not) — specified per page above. A blank region is a contract violation. |
| Error | Blocking errors render as a destructive `alert` above the form **and** mark the offending field `aria-invalid`. **Never a toast alone for a blocking error.** Non-blocking success/confirmation may be a `sonner` toast. |
| Success | A navigation is the success signal (no success toast on a redirect). A stay-on-page save gets a toast. A state change on the tracking page is a page re-render, not a toast. |

### Optimistic updates — where they are allowed

| Action | Optimistic? | Why |
|---|---|---|
| Cart add / quantity / remove | Yes | Cheap, reversible, Redis-backed |
| Confirm order (merchant, D-02) | Yes | One-tap by design; failure re-renders the row with an alert |
| Confirm / reject claim | Yes (card leaves the queue) | Same |
| Place order | **No** | It decrements stock and mints a token. Show the submitting state and wait. |
| Save product / payment settings | **No** | The server may reject on the entitlement cap or validation |

### Accessibility floor (inherited, non-negotiable)

- Every input has a visible `<label>`. Placeholder-as-label is a contract violation.
- Visible focus ring on every interactive element (`--ring`, ≥2px, 3:1).
- 44px minimum touch target everywhere; 48px on storefront primary CTAs.
- Status regions that change without navigation (cart count, copy confirmation, slug-style inline checks, claim submission result) are `aria-live="polite"` with `role="status"`.
- Full keyboard path through the product form, the variant matrix, the checkout radio cards and the reject dialog. Dialog focus is trapped and returns to the trigger on close.
- Colour is never the only signal — every status carries an icon and a text label.
- Every route sets a meaningful `<title>` through the root layout's `%s · EINORT` template.
- Images: product images get real `alt` (the product name); decorative placeholders get `alt=""`.

### Responsive strategy

Mobile-first, **designed at 360px width first** — this market is low-end Android. Tables collapse to stacked cards below `md`, never to horizontal scroll. The sidebar collapses to an off-canvas sheet below `lg`. Storefront primary CTAs stick to the viewport bottom below `md` on the cart and checkout. **No modals on the storefront except the screenshot lightbox** (which is merchant-side anyway); no drawers, no carousels.

## Copywriting Contract

**Voice:** direct, second person, no exclamation marks, no "Oops"/"Whoops", no emoji, no ALL-CAPS shouting. Errors state what happened and what to do next. Storefront copy addresses the shopper; dashboard copy addresses the merchant — never mix ("your store" on the dashboard, "the seller" on the storefront).

**Never write:** "Delete" for a product (D-08), "Verified" for a payment number (D-17), "Payment received" before a merchant confirms (ORD-02), a plan/phase/internal name (`scopedDb`, `/s/`, `PAYMENT_CLAIMED`), or any promise of a payment guarantee the platform does not make.

## Registry Safety

| Registry | Blocks Used | Safety Gate |
|---|---|---|
| shadcn official | `form`, `table`, `select`, `textarea`, `checkbox`, `switch`, `radio-group`, `dialog`, `alert-dialog`, `dropdown-menu`, `sonner`, `skeleton`, `sidebar`, `sheet`, `tooltip` (+ existing `button`, `card`, `input`, `label`, `badge`, `alert`, `separator`) | not required |
| *(third-party)* | **none declared** | not applicable |

`components.json` currently declares `"registries": {}`. **No third-party registry is authorized for this phase.** Adding one during execution invalidates this contract and requires a re-run of the vetting gate (`npx shadcn view <block> --registry <url>`, scan for `fetch(`, `process.env`, `eval(`, external dynamic imports, obfuscated identifiers) before the block may be used.

**Post-`add` review requirement:** because `components.json` still carries `"baseColor": "zinc"` (vestigial under `cssVariables: true`), every newly added component must be scanned for hardcoded `zinc-*` utilities and converted to semantic tokens before it is used on **either** surface. This is ban #2 and the grep test catches it.
