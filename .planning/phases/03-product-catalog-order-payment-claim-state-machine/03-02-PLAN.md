## Phase Goal

ROADMAP goal (verbatim): *A merchant can list a product and a customer can complete a full purchase through to a merchant-confirmed order, with stock, order state, and payment-claim integrity guaranteed server-side.*

Derived user story: **As a** Cameroonian merchant and their customer, **I want to** list products and complete a purchase through WhatsApp, Mobile Money claim, or cash on delivery, **so that** the sale is recorded, the stock is correct, and the payment status is auditable.

<objective>
Make the two-surface design split structural rather than aspirational, install every dependency and shadcn component the phase needs, and validate the R2/Resend environment at boot.

Purpose: `src/app/globals.css`'s `:root` currently resolves every semantic token to the merchant blue/gold/slate values, so a storefront page written today silently ships in merchant colours — the exact leak that already cost this project one retrofit (`260823-gu4`). Fixing it once, with a grep test as the guard, is cheaper than fixing it at fourteen pages.
Output: a scoped `[data-surface="storefront"]` token block, a wrapped storefront layout, three new badge variants, fourteen shadcn components, five npm packages, a validated env surface, and a build-failing surface-isolation test.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Deploy environment → application boot | Missing or blank secrets can silently disable a control instead of failing loudly |
| npm registry → build | Newly installed packages execute in the build and in production |
| Merchant surface ↔ customer surface | Shared CSS variables; a token leak crosses a brand boundary, and the merchant tokens carry status semantics (gold = needs attention) that must not appear on a shopper's page |
