## Decisions Made

- Deferred the `../src/server/images/r2` import to inside `main()`, placed immediately before it is first needed (right before scratch-product seeding), rather than at the top of `main()` — so the cheapest, most specific guards (missing/unsafe `TEMPLATE_PREVIEW_STORE_SLUG`, nonexistent store) never require R2 credentials to be configured just to fail correctly.
- Used a `typeof import("../src/server/images/r2")` type query (erased at compile time) to keep the dynamically-imported module fully typed, rather than casting to `any` or hand-writing duplicate signatures.
- Threaded the resolved r2 functions through `seedScratchProducts` as an explicit parameter (`r2: Pick<R2Module, ...>`) rather than reaching for a module-scope mutable variable, keeping the function's dependencies visible in its signature.
- Used `node:http`'s `request()` instead of `fetch()` for the dev-server reachability probe specifically when the target host is `localhost` or `*.localhost`, connecting to `127.0.0.1` directly with an explicit `Host` header, rather than trying to work around `fetch()`'s forbidden-header restriction.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] ESM static-import evaluation order broke the script's own env-loading loop**

- **Found during:** Re-verification of the plan's own acceptance criterion — "With `TEMPLATE_PREVIEW_STORE_SLUG` unset, `npm run templates:previews` exits non-zero and its output matches `/TEMPLATE_PREVIEW_STORE_SLUG/`."
- **Issue:** The script statically imported `putObject`, `objectKeyFor`, `derivativePrefixFor`, and `templatePreviewPrefixFor` from `../src/server/images/r2` at the top of the file. `r2.ts` itself imports `@/env`, whose `createEnv()` call throws synchronously — at module-evaluation time — the instant it runs with any required var undefined. Per the ES module spec, every static import is fully evaluated, recursively and depth-first, before the importing module's own top-level statements run, regardless of where the import sits textually in the file. So `@/env`'s validation always ran before this script's own `.env.local`/`.env` loading loop (which sits later in the file, but that's irrelevant to evaluation order) ever got a chance to populate `process.env`. Running the script produced a generic `@t3-oss/env-nextjs` "Invalid environment variables" crash naming `DATABASE_URL`, `R2_ACCOUNT_ID`, etc. as undefined, instead of this script's own actionable guard message — and this was real breakage, not a test artifact, since `.env.local` genuinely never got loaded before `r2.ts` needed it.
- **Fix:** Converted the static import of `../src/server/images/r2` into a dynamic `await import(...)` performed inside `main()`, placed after all cheaper guards (configured-slug check, `DATABASE_URL` check, org-exists check, order-count safety check) so a run refused for one of those reasons never even needs R2 credentials. Added a type-only `type R2Module = typeof import("../src/server/images/r2")` so the dynamically-resolved module keeps full type safety. Threaded the resolved functions through `seedScratchProducts` as an explicit parameter and through the capture loop as `r2.putObject(...)` / `r2.templatePreviewPrefixFor(...)`. Verified `../src/server/images/pipeline` does NOT need the same treatment — it imports only `server-only` and `sharp`, no `@/env` — so `processImage` remains a static import.
- **Files modified:** `scripts/generate-template-previews.ts`
- **Verification:** Re-ran the plan's guard-refusal acceptance criterion with `TEMPLATE_PREVIEW_STORE_SLUG` removed from `.env.local` — now exits non-zero with `[generate-template-previews] Refusing to run: TEMPLATE_PREVIEW_STORE_SLUG is not set.` (previously crashed with the generic env-validation error). Also re-ran with the slug pointed at a nonexistent store — exits non-zero naming `signup` as the remediation. `npm run typecheck` and `npm run lint` both pass.
- **Committed in:** `f8f422f` (part of the single combined commit)

**2. [Rule 1 - Bug] Node's `fetch()` cannot resolve `*.localhost` subdomains on this Windows/Node combination, producing a false "server is down" reading**

- **Found during:** Manual verification of the `--dry-run` behavioral acceptance criterion, after fixing deviation #1 above. With the guard-order fix in place and a real scratch store configured, the dev-server probe still failed with `cannot reach http://einort-preview.localhost:3001/ ... (fetch failed)` even though `curl` and a direct Playwright/Chromium navigation to the same URL both returned `200`.
- **Issue:** Node's built-in DNS resolver (`getaddrinfo`, used internally by `fetch`/undici) does not implement RFC 6761's requirement that any `*.localhost` name resolve to loopback without a DNS query — confirmed empirically (`dns.lookup("sub.localhost", ...)` → `ENOTFOUND`), unlike Chromium (used by Playwright's browser, which resolved the same URL correctly) and unlike curl or any real browser, all of which special-case `.localhost` client-side. This meant the dev-server probe would always report "server unreachable" on this machine even when the server was up and correctly serving the tenant — an actively misleading failure, directly undermining RESEARCH Pitfall 4's goal of one actionable failure rather than a wrong one. A first attempted fix — rewriting the request URL's hostname to `127.0.0.1` while passing the original hostname via a `Host` header to `fetch()` — was itself blocked by the WHATWG fetch spec, which makes `Host` a forbidden request header; `fetch` silently discards any attempt to set it, and the request then 404s because `classifyHost()` sees `127.0.0.1:3001` instead of the tenant subdomain (verified empirically).
- **Fix:** Added a `probeReachable(url)` helper that behaves like `fetch` (returns `{ ok, status }`, never throws on a non-2xx) but, for `localhost`/`*.localhost` targets only, uses `node:http`'s `request()` directly — connecting to `127.0.0.1` with the original hostname preserved in an explicit `Host` header, which `node:http` (unlike `fetch`) permits. Non-localhost (real production) hostnames still go through a plain `fetch`, so this change has no effect outside local dev.
- **Files modified:** `scripts/generate-template-previews.ts`
- **Verification:** Re-ran `npm run templates:previews -- --only=flagship-fashion,retail-general --dry-run` against the real scratch store with `npm run dev` running — the probe now succeeds, both templates are captured (`flagship-fashion: 7148 bytes (800x500)`, `retail-general: 13560 bytes (800x482)`), the dry-run correctly skips the R2 upload and manifest rewrite, and `git diff --quiet -- src/server/theming/preview-manifest.ts` confirms the manifest is untouched. `npm run typecheck` and `npm run lint` both still pass.
- **Committed in:** `f8f422f` (part of the single combined commit)
