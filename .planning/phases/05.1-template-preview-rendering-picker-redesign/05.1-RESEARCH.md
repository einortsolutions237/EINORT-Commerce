## User Constraints (from CONTEXT.md)

### Locked Decisions

**Screenshot framing**
- **D-01:** Each preview image is a cropped shot capturing the hero section plus roughly the next section (e.g. trust bar or first product row) — not hero-only, and not a full scrollable homepage compressed into one tall image. This matches a picker card's aspect ratio while still showing enough structure/accent per template to tell them apart at a glance.

**Rendering & regeneration strategy**
- **D-02:** Screenshots are generated by a one-time build/seed script, not rendered on-demand at request time. The script renders all 50 templates' `TEMPLATE_DEFAULTS` (default document + tokens, deterministic) and uploads the resulting images to R2 once. No runtime rendering cost, no request-time latency risk. Re-running the script is a manual step whenever a template's default design changes — this phase's plan should make that re-run path an explicit, documented command, not an ad-hoc script only the original author knows how to invoke.
- **D-03 (implied by D-02):** The script needs a headless-browser dependency (e.g. Playwright or Puppeteer) that is not currently in the project's dependency tree. Per this project's established pattern (`next-themes` in quick task 260906-egn), a new dependency of this kind is `[ASSUMED]` until package-legitimacy-checked and gets a blocking `checkpoint:human-verify` gate before install — the plan must include this gate, not skip it.

**Grid layout per surface**
- **D-04:** One shared card design (same image aspect ratio, same typography treatment) is used in both surfaces. Onboarding's full-width page renders more columns; the editor's narrower "Change template" side panel renders fewer columns (down to 1-2 if needed) — column count is responsive to available width, not a second card variant. No duplicate component to maintain.

**Fallback behavior**
- **D-05:** If a template's screenshot isn't available (mid-generation, or generation failed for that one template), the tile falls back to 05-09's existing CSS-wireframe `TemplateThumbnail` component rather than a broken-image icon, blank tile, or generic skeleton. Since generation is a one-time build script (D-02), this fallback should rarely if ever be seen in production — it exists as a safety net for partial-script-completion, not as an expected steady-state UI.

## Summary

This phase has three separable technical problems and one environment blocker.

**(1) How to render 50 templates for screenshotting.** The obvious approach — a new "render this template key" route — is blocked three ways in this codebase: `src/proxy.ts` returns an unconditional bare 404 for every path starting with `/s/` [VERIFIED: `src/proxy.ts:65`], the storefront layout at `src/app/s/[slug]/layout.tsx` is a hard tenant gate that `notFound()`s without a live `Organization` row, and `tests/unit/surface-token-isolation.test.ts` ban #4 fails the build if `data-surface="storefront"` appears in any `.tsx` outside `src/app/s/` — so the storefront's zinc token scope cannot be re-created anywhere else. The clean resolution is to add **no route at all**: a `tsx` script writes each template's `TEMPLATE_DEFAULTS` into a dedicated scratch tenant's `StorefrontTheme`/`StorefrontPage` published columns, then drives headless Chromium at `http://{scratch-slug}.{ROOT_DOMAIN}/` — the merchant's real, published storefront home — and screenshots it. Fifty write-navigate-shoot iterations. This is not a workaround: it produces pixel-identical output to what a merchant actually gets, because it *is* what a merchant gets.

**(2) Which headless browser.** Playwright, decisively. `playwright@1.63.0` has **zero install/postinstall scripts** and exactly one dependency (`playwright-core`, itself dependency-free) [VERIFIED: registry.npmjs.org packument]. `puppeteer@25.10.0` ships `postinstall: node install.mjs` — a network-fetching install hook that downloads a Chrome binary — plus six direct dependencies [VERIFIED: npm view]. Since Vercel installs devDependencies during `next build`, Puppeteer's postinstall would download ~150 MB of Chrome on every production build for a script that never runs there. Playwright's browsers are fetched by a separate explicit `npx playwright install chromium`, which Vercel never invokes. Playwright also has ~8x Puppeteer's weekly downloads and `engines: node >=20` (satisfied by the local Node v24.16.0).

**(3) Where the preview lives.** No Prisma migration is needed — a template preview is platform-wide code-adjacent data, not tenant data, and touches zero DB rows. Recommend a **generated, committed manifest** (`src/server/theming/preview-manifest.ts`) keyed by `TemplateKey`, plus a pure `templatePreviewPrefixFor(key)` helper beside `objectKeyFor` in `src/server/images/r2.ts`, rather than a hand-maintained `previewImageKey` field on 50 `TEMPLATES` rows. The registry records *design decisions*; the manifest records *generation state* — including which templates succeeded, which is exactly the fact D-05's fallback branches on and the fact a hand-authored registry field structurally cannot know.

## Architectural Responsibility Map

| Capability | Primary Tier | Secondary Tier | Rationale |
|------------|-------------|----------------|-----------|
| Rendering a template's default document to pixels | **Build-time script (Node CLI)** | Frontend Server (SSR) | D-02 locks one-time generation. The script *drives* a browser; the Next server does the actual React/CSS rendering. Neither tier alone can do it: the script has no CSS engine, the server has no screenshot capability. |
| Deciding the crop region (D-01) | **Build-time script** | — | `page.screenshot({ clip })` is a script-side argument. Putting crop logic in a CSS class on the page would mean shipping preview-only markup into the merchant-facing storefront. |
| Re-encoding PNG → WebP, downscaling | **API/Backend (`src/server/images/pipeline.ts`)** | — | Existing `IMAGE_PRESETS` registry (D-07). A bespoke Sharp call in the script is exactly the `processLogoImage()` duplication that file's header rejects. |
| Storing the preview bytes | **Object storage (R2)** | — | D-02 locks R2. `putObject()` already exists and is server-side-only by design. |
| Knowing *which* templates have a preview | **Generated manifest (build artifact, committed)** | — | Generation state is script output, not a hand-authored design decision. Keeping it out of `registry.ts` prevents a script from rewriting a human-edited file. |
| Resolving a preview key → public URL | **Frontend Server (RSC)** | — | `publicUrlFor()` lives in `server-only` `r2.ts`. `tests/unit/theming-marker-boundary.test.ts` forbids any `"use client"` file importing a value from the server-only registry/defaults; the RSC flattens to `TemplateTile[]` exactly as it already does. |
| Choosing image vs. wireframe fallback (D-05) | **Browser/Client (`TemplatePicker`)** | Frontend Server | The RSC decides `previewUrl: string \| null`; the client component branches on it. No network call, no `onError` race. |
| Column count per surface (D-04) | **Browser/Client (CSS container queries)** | — | The editor rail's width (`lg:w-80`) is *decoupled* from the viewport width. Only a container query can express "columns follow my own box." |

### Pattern 1: Reseed-a-scratch-tenant, screenshot the real storefront home

**What:** Rather than adding a route that renders an arbitrary template, the script mutates one designated scratch tenant's *published* theme to each template in turn and screenshots `/` on that tenant's subdomain.

**Why this and not a dedicated route** — three independently-verified blockers make the route approach expensive and the reseed approach nearly free:

1. `src/proxy.ts:65` — `if (pathname === "/s" || pathname.startsWith("/s/")) return new NextResponse(null, { status: 404 })`, unconditional, on every host. A headless browser cannot address any `/s/*` path directly; it must go through a real store hostname. [VERIFIED: codebase read]
2. `tests/unit/surface-token-isolation.test.ts` ban #4 fails the build if `data-surface="storefront"` appears in any `.tsx` outside `src/app/s/`, and Phase 4's D-12 forbids weakening it. The storefront's zinc token scope + 0.25rem radius therefore cannot be recreated on a dashboard-side route. [VERIFIED: codebase read]
3. `src/app/s/[slug]/layout.tsx` `notFound()`s on an unresolved tenant *and* injects **that tenant's** `--brand-accent*` values via `deriveThemeCssVars`. A per-template route nested under it would need a second, nested token scope to override the accent — and the layout's own header explicitly states "There is no second wrapper div." The chrome (announcement bar, header) would still carry the wrong accent. [VERIFIED: codebase read]

Reseeding sidesteps all three: the layout reads the scratch tenant's published tokens, which the script has *already set to the template's own tokens*. Header, announcement bar, footer and sections are all correct simultaneously. Zero new public surface, zero new env gate, zero token-override hack.

**When to use:** Any time you need pixel-accurate output of an existing server-rendered route with substituted data.

**The safety obligation.** The script performs destructive writes. Mirror `tests/setup/seed-two-tenants.ts`'s posture exactly — that module defines `UnsafeSeedTargetError extends Error` with `override readonly name`, and `assertSafeSeedTarget()` refuses to run against the wrong Neon endpoint. The preview script needs the inverse guard: refuse unless the target slug is the explicitly-configured scratch store, and refuse if that store has any `Order` rows (a store with orders is somebody's real business). Fail closed, throw, do not sanitise — the `objectKeyFor` posture.

**Where the script's Prisma client comes from.** `eslint.config.mjs:44` scopes the `no-restricted-imports` ban on `**/server/db/base` and `**/generated/prisma*` to `files: ["src/**/*.{ts,tsx}"]` only. A script under `scripts/` is outside that zone, exactly as `tests/setup/seed-two-tenants.ts` is — and that file's own header records the reason it builds its client explicitly rather than importing from `src/server/db/*`: "it keeps this module importable from a plain `tsx` script (the `src/server/db/*` modules open with `import "server-only"`, which throws outside a `react-server` resolution)." [VERIFIED: codebase read]

**Consequence:** the script needs `--conditions=react-server` anyway (it imports `server-only`-marked `defaults.ts`, `pipeline.ts`, `r2.ts`), so it *can* import `server-only` modules — but building its own client is still the safer, precedented shape.

**Import style:** use **relative** imports (`../src/server/theming/defaults`), not the `@/` alias. `prisma/seed.ts` uses `../tests/setup/seed-two-tenants`. `vitest.config.ts` has to re-declare the alias because Vitest does not read `tsconfig.json` paths; do not assume `tsx` resolves it either. Relative removes the question. [VERIFIED: codebase read of `prisma/seed.ts`, `vitest.config.ts` alias comment in CLAUDE.md conventions]

### Pattern 2: A `templatePreview` row in `IMAGE_PRESETS` — plus one honest schema fix

**What:** Playwright emits PNG or JPEG only (`type: "png" | "jpeg"` — there is no WebP option) [CITED: playwright.dev/docs/api/class-page#page-screenshot]. So the pipeline is always **Playwright → PNG buffer → Sharp → WebP**, which is precisely what `processImage()` already does for every other surface.

Per `pipeline.ts`'s own header — "Written as a registry, Phase 4 is a row" — the correct move is a row, not a bespoke Sharp call in the script.

**The complication, stated honestly.** The existing `enhance` flag conflates two independent axes. From the file's own comment: `enhance` "says whether the photographic finishing chain (`.normalise()`, `.modulate()`, `.sharpen()`) runs, and **it also selects the WebP mode**: lossy at `WEBP_QUALITY` when true, lossless when false."

A UI screenshot needs the `logo` row's treatment on axis one (no `.normalise()` — it would stretch the luminance histogram and shift the template's deliberately-chosen brand accent, the exact argument the `logo` row's header makes) but the `product` row's treatment on axis two (lossy — a 2x-DPR screenshot full of antialiased text encodes very badly as lossless WebP; expect several hundred KB per image, times 50).

**Recommendation:** add an explicit `lossless: boolean` field to every preset row and have `processImage` read it instead of reusing `enhance`. This is a 3-line change that decouples two things that were only ever coincidentally aligned, and it is fully in the spirit of the file's stated rule: *"the row is the whole specification, so `processImage` reads this flag and NEVER branches on the preset's name."* Set `product: { enhance: true, lossless: false }`, `claim: { enhance: true, lossless: false }`, `logo: { enhance: false, lossless: true }` — no behaviour change to any existing row — and `templatePreview: { enhance: false, lossless: false }`.

**Proposed row:**

```ts
/**
 * TMPL-06 / 05.1 D-01. A rendered template preview for the picker grid.
 *
 * `enhance: false` for the same reason the `logo` row sets it: the input is
 * already correctly exposed, flat UI output whose colours ARE the template's
 * own declared accent. `.normalise()` would shift them and `.sharpen()` would
 * halo the type.
 *
 * `lossless: false` is NOT inconsistent with that. A 2x-DPR screenshot is
 * dense antialiased text, which lossless WebP encodes badly — this is the one
 * place the two axes genuinely diverge, which is why they are two fields.
 *
 * `fit: "inside"` + `ratio: null` means 800 is the LONG edge and the 16:10
 * aspect the Playwright `clip` produced is preserved: 800x500. The crop
 * decision (D-01) lives in the script's `clip`, never here — Sharp only
 * downscales and re-encodes.
 */
templatePreview: {
  sizes: [800],
  labels: ["card"],
  fit: "inside",
  ratio: null,
  format: "webp",
  enhance: false,
  lossless: false,
},
```

**Why 800px and not 1280.** The card renders at roughly 280–400 CSS px wide in both surfaces (see Pattern 4's column math). At 2x DPR that is 560–800 device px. 800 is the ceiling with no waste. `next/image` downscales further per the `sizes` attribute. Expect ~25–50 KB per preview; 50 previews ≈ 1.3–2.5 MB **worst case if every tile loads**, which lazy-loading prevents. This matters: `template-thumbnail.tsx`'s own header rejected stored images partly because of "real image bytes on the low-end Android this market runs on." TMPL-06 overrides that decision, but the constraint is unchanged and the size budget is the mitigation.

**`limitInputPixels`** is 50 MP; a 2560x1600 PNG is 4.1 MP. No conflict.
**`.rotate()`** runs unconditionally on every preset. A Playwright PNG carries no EXIF orientation tag, so it is a harmless no-op — do **not** add a branch to skip it.

### Pattern 3: Generated manifest, not a registry field — with the derived key as a pure function

**Recommendation: a generated, committed `src/server/theming/preview-manifest.ts`, plus `templatePreviewPrefixFor(key)` in `r2.ts`. Do not add `previewImageKey` to `TemplateDefinition`.**

| | `previewImageKey` on 50 `TEMPLATES` rows | Generated manifest |
|---|---|---|
| Maintenance | 50 hand-written strings that are 100% derivable from `key` | 0 hand-written lines |
| What it can express | "this template *should* have a preview" | "this template *does* have a preview, at these dimensions, generated at this time" — the fact D-05 actually branches on |
| Merge risk | A script rewrites a 1262-line file humans actively edit | Script owns the file exclusively; nobody edits it (same posture as `src/generated/prisma/**`, which is "never hand-edited") |
| Type safety | `Readonly<Record<TemplateKey, …>>` exhaustive by construction | `Readonly<Partial<Record<TemplateKey, …>>>` + a drift test asserting every key is a `TemplateKey` and (when complete) all 50 present |
| Partial state (D-05's whole reason for existing) | Inexpressible — the field is non-optional or it lies | Native — a missing key *is* the fallback signal |

The registry's rows encode **design decisions** (`segment`, `minTier`, `sections`) — things a human chose. A storage path is not a design decision; it is a naming convention plus generation state. The registry header's own framing ("SECTION AND BLOCK **TYPES** ARE BUILD-TIME CODE") is about hand-authored code, and a script-rewritten field would violate that spirit even while technically living in the right file.

**Note for the planner:** ROADMAP.md's Success Criterion 1 for this phase reads "…and referenced from the `TEMPLATES` registry." The manifest satisfies the intent — it is keyed by `TemplateKey`, typechecked against `TEMPLATE_KEYS`, and the registry remains the sole source of truth for which templates exist — but the wording should be reconciled in the plan so the verifier does not read it as a literal requirement for a registry column. CONTEXT.md (2026-09-07, later) explicitly hands this choice to research.

**The key convention.** Follow `r2.ts`'s existing derivative layout exactly: a prefix plus a label basename. `IMAGE_PRESETS`'s labels "end up in object keys like `{prefix}/card.webp`, so renaming one orphans stored objects rather than moving them." Therefore:

```
templates/{templateKey}/card.webp
```

`templates/` is a sibling namespace to `tenants/`. There is no collision risk: `objectKeyFor()` guarantees every tenant key begins `tenants/`, and `templateKey` is validated against the closed `TEMPLATE_KEYS` tuple, never client input.

**`templatePreviewPrefixFor` must throw, not sanitise** — the `objectKeyFor` posture, "because the whole point is that there is no such thing as close enough to a tenant boundary." Validate with the existing `isTemplateKey()` narrower from `registry.ts` (both modules are `server-only`; `registry.ts` does not import `r2.ts`, so there is no cycle). Add coverage to `tests/unit/r2-key.test.ts` or a sibling, matching the existing exhaustive treatment of `objectKeyFor`.

**`publicUrlFor()` works unchanged** — it only refuses keys ending in `/original`, and `…/card.webp` does not.

**No Prisma migration.** A template preview is platform-wide, code-adjacent data. It touches no tenant row, no `StorefrontTheme` column, no `Organization` field. [VERIFIED: `prisma/schema.prisma` read — `StorefrontTheme` carries `draftTemplateKey`/`publishedTemplateKey`/`logoKey`, all per-tenant; nothing here is per-tenant.] The five existing migrations stay untouched.

### Pattern 4: Tailwind v4 container queries — and the column bug this fixes

**This is not merely a nicety. The current picker is measurably wrong in the editor.**

`template-picker.tsx:136` sets `className="grid grid-cols-2 gap-4 sm:grid-cols-3"`. Those are **viewport** breakpoints. The editor rail is `lg:w-80` — a fixed **320px** column [VERIFIED: `editor-shell.tsx:682`] with `px-4` padding, leaving ~288px of content width. Because `sm:` fires at a 640px *viewport*, any desktop user opening "Change template" gets **three columns inside 288px** — roughly 85px per card. D-04's "down to 1-2 if needed" is not achievable with viewport breakpoints at all, because the rail's width is decoupled from the window's.

Tailwind CSS v4 ships container queries in core, no plugin. [CITED: tailwindcss.com/docs/responsive-design] Container breakpoints: `@sm` = 24rem/384px, `@md` = 28rem/448px, `@lg` = 32rem/512px, `@xl` = 36rem/576px, `@2xl` = 42rem/672px, `@3xl` = 48rem/768px.

**Recommended grid:**

```tsx
<div className="@container">
  <RadioGroup className="grid grid-cols-1 gap-5 @sm:grid-cols-2 @2xl:grid-cols-3">
```

Resulting column counts:

| Surface | Container width | Fires | Columns | Card width |
|---|---|---|---|---|
| Editor "Change template" rail | ~288px | none | **1** | ~288px |
| Onboarding, current `max-w-2xl` | 672px | `@sm`, `@2xl` | **3** | ~205px |
| Onboarding, widened to `max-w-5xl` | 1024px | `@sm`, `@2xl` | **3** | ~325px |
| Onboarding at `< sm` viewport | ~350px | none | **1** | full |

**Recommendation for the UI-SPEC step:** widen the onboarding container from `max-w-2xl` (672px, currently sized for the 6-tile industry grid) to `max-w-5xl` so a 3-up grid gives ~325px cards — genuinely comparable to the Shopify reference. At `max-w-2xl` a 3-up grid gives 205px cards, which is barely larger than today's wireframe tiles and would not close the gap TMPL-06 names. This is a layout change to `src/app/onboarding/branding/page.tsx`, not to the shared component, so D-04's "no second card variant" is preserved.

**Anti-Patterns to Avoid**

- **Viewport breakpoints on the picker grid.** The bug described above. `sm:`/`md:`/`lg:` must not appear on the grid container. A source-contract test should pin this (see § Validation Architecture).
- **`priority` on any tile `<Image>`.** 50 preview images with `priority` would cancel lazy loading entirely and blow ~2 MB onto a Douala mobile connection on first paint. `next/image` lazy-loads by default; leave it.
- **`onError`-based fallback instead of the `previewUrl === null` branch.** D-05's fallback must be decided *before* render from manifest state. An `onError` fallback flashes a broken image, produces console noise, and — critically — will **not** save you from the un-allowlisted-host case, which `next/image` treats as a thrown error, not an image load failure.
- **A hex colour or Tailwind palette utility anywhere in the redesigned card.** `tests/unit/surface-token-isolation.test.ts` bans #1 and #2 scan every `.tsx` under `src/app` and `src/components` and fail the build. Use semantic tokens (`bg-card`, `border-border`, `text-muted-foreground`). The one exception already in `template-thumbnail.tsx` is `AccentBlock`'s single `style={{ backgroundColor: primaryAccent }}`, which stays.
- **Inline user-facing prose in the picker.** All copy goes in `src/lib/strings/index.ts` (`strings.branding.*`, `strings.editor.*`). `tests/unit/dashboard-nav.test.ts` scans `.tsx` for prose-shaped literals.
- **Importing `TEMPLATES` / `TEMPLATE_DEFAULTS` / `preview-manifest` from the picker.** `tests/unit/theming-marker-boundary.test.ts` fails the build if any `"use client"` file in `src/` imports a *value* from a `server-only` module. The RSC flattens to `TemplateTile[]`; that contract is unchanged.
- **Putting `playwright` in `dependencies`.** It must be a devDependency. It is never imported by anything under `src/`.
- **Adding the browser download to `postinstall`.** `package.json` already has `postinstall: node scripts/prisma-generate.mjs`. Appending `playwright install` there would fire on every Vercel build. Keep it a documented one-time manual command.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Rendering a template's default document to pixels | A `renderToStaticMarkup` + hand-assembled Tailwind CSS harness | Playwright against the real `next start` server | Six section components import `next/image`; `next/font/google` injects `--font-sans`/`--font-heading`; `globals.css` scopes zinc tokens under `[data-surface="storefront"]`. A second render path drifts silently from the real one. |
| Cropping to hero + next section | CSS classes or a wrapper element on the storefront page | `page.screenshot({ clip: {x,y,width,height} })` | Keeps preview-only concerns entirely out of merchant-facing markup. |
| Stopping the hero's entrance animation mid-capture | A `sleep(2000)` before the shot | `screenshot({ animations: "disabled" })` + `newContext({ reducedMotion: "reduce" })` | Deterministic, not timing-dependent. See § Common Pitfalls → Pitfall 1. |
| PNG → WebP, downscale | A bespoke `sharp()` chain inside the script | A new `IMAGE_PRESETS` row + `processImage()` | `pipeline.ts`'s header rejects exactly this: "Written as `processProductImage()` today, that becomes `processLogoImage()` in four weeks, and the second copy is where the EXIF rotation quietly does not get applied." |
| Uploading to R2 | A new S3 client in the script | `putObject()` from `src/server/images/r2.ts` | The client is already configured with the mandatory `region: "auto"` R2 quirk and the correct endpoint. |
| Building the preview's public URL | String concatenation in a component | `publicUrlFor(templatePreviewPrefixFor(key) + "/card.webp")` in the RSC | `publicUrlFor` carries the "never serve an `/original`" refusal, and `R2_PUBLIC_BASE_URL` is not `NEXT_PUBLIC_`, so a client component cannot read it. |
| Column count per surface | A `variant`/`columns` prop on `TemplatePicker`, or a second component | Tailwind v4 `@container` + `@sm:`/`@2xl:` | D-04 forbids a second variant. A prop would also require both call sites to know the rail's pixel width — a number in two places. |
| Guarding the destructive reseed | An ad-hoc `if (slug !== "preview") return` | The `assertSafeSeedTarget` / `UnsafeSeedTargetError` shape from `tests/setup/seed-two-tenants.ts` | Named error class with `override readonly name`, throws rather than warns, unit-testable (`tests/unit/seed-guard.test.ts` already exists as the precedent). |
| Verifying package legitimacy | Trusting `npm view` alone | The `checkpoint:human-verify` gate (D-03) with the evidence packet above | Registry existence does not confer legitimacy; a slopsquatted package also passes `npm view`. slopcheck is unavailable here. |

**Key insight:** every capability this phase needs already exists in the codebase in some form (`processImage`, `putObject`, `publicUrlFor`, `SectionRenderer`, `TemplateThumbnail`, `assertSafeSeedTarget`, the `sortedBySegment` + tier-lock + inert-current-card logic in `TemplatePicker`). The genuinely new surface area is exactly three things: one npm devDependency, one script, one generated file. Everything else is a row, a field, or a class change. Any plan whose task list is materially larger than that is rebuilding something that exists.

## Common Pitfalls

### Pitfall 1: The hero's entrance animation captured mid-fade

**What goes wrong:** Every hero variant applies `CASCADE` = `"animate-in fade-in slide-in-from-bottom-4 fill-mode-both ease-[var(--motion-ease)] animation-duration-[var(--motion-hero)]"` on mount, with children staggered through `delay-0 / delay-200 / delay-[400ms] / delay-[600ms]` [VERIFIED: `hero-section.tsx:106`]. A screenshot taken immediately after load captures a half-transparent, half-offset headline. Across 50 templates, some will land at different animation phases, so the previews will look inconsistent for reasons nobody can diagnose from the images.

**Why it happens:** `page.goto()` resolving does not mean animations have finished.

**How to avoid:** Two independent, complementary controls. Use both.
1. `browser.newContext({ reducedMotion: "reduce" })` — `src/app/globals.css:283` declares `@media (prefers-reduced-motion: reduce) { [data-surface="storefront"] *, …::before, …::after { animation-duration: 1ms !important; animation-iteration-count: 1 !important; transition-duration: 1ms !important; } }`. This collapses the entire cascade to its end state at the CSS level. [VERIFIED: codebase read]
2. `page.screenshot({ animations: "disabled" })` — Playwright fast-forwards finite CSS animations to completion before capturing. [CITED: playwright.dev/docs/api/class-page#page-screenshot]

**Warning signs:** Two consecutive runs of the script produce visually different bytes for the same template.

**Non-pitfall, worth stating so nobody "fixes" it:** `<Reveal>` (`sections/reveal.tsx`) defaults to **visible and unanimated** — its header states explicitly "THE DEFAULT STATE IS VISIBLE AND UNANIMATED. DO NOT 'FIX' THIS BY SEEDING A ZERO-OPACITY OR HIDDEN INITIAL CLASS." So a screenshot taken before `IntersectionObserver` fires shows content, not a blank band. This codebase got that right; the pitfall is only the hero's mount-time cascade.

---

### Pitfall 2: `next/image` hard-errors instead of falling back when `R2_PUBLIC_BASE_URL` is unset

**What goes wrong:** `next.config.ts` builds `images.remotePatterns` from `process.env.R2_PUBLIC_BASE_URL`, and "a missing or malformed value degrades to 'no remote pattern'" — an empty array. `next/image` then throws `Invalid src prop … hostname is not configured under images` for every preview. This is **not** an image-load failure, so D-05's fallback does not catch it and neither would an `onError` handler.

**Why it happens:** `.env.local` currently has **no `R2_*` variables at all**, while `src/env.ts` declares all five as required. [VERIFIED: filesystem]

**How to avoid:** Treat R2 credentials as a `user_setup` prerequisite for this phase, not a runtime concern. The plan should open with an explicit setup item. If they cannot be provisioned, the documented fallback is committing the 50 WebP files to `public/templates/` — which needs no `remotePatterns` entry, no credentials, and no network — but that contradicts D-02 and must be raised with the user rather than chosen unilaterally.

**Warning signs:** The picker renders in dev but every card throws; or `npm run dev` fails at `@/env` import time with a Zod error naming `R2_ACCOUNT_ID`.

---

### Pitfall 3: The script cannot import `server-only` modules under a plain `tsx` invocation

**What goes wrong:** `templateDefaultDocument()` / `templateDefaultTokens()` live in `src/server/theming/defaults.ts`, which opens with `import "server-only"`. So do `pipeline.ts` and `r2.ts`. Running `tsx scripts/generate-template-previews.ts` throws immediately.

**How to avoid:** `tsx --conditions=react-server`. The precedent is already in the repo: `prisma.config.ts:66` — `seed: "tsx --conditions=react-server prisma/seed.ts"`, whose comment states this is so "`server-only`-marked modules resolve correctly during seeding." [VERIFIED: codebase read] Add the npm script with the flag baked in, e.g. `"templates:previews": "tsx --conditions=react-server scripts/generate-template-previews.ts"`.

**Related:** use relative imports, not `@/`. `prisma/seed.ts` does. Do not assume `tsx` reads `tsconfig.json` paths — Vitest famously does not, which is why `vitest.config.ts` re-declares the alias.

---

### Pitfall 4: Screenshotting the wrong host, or the right host on the wrong port

**What goes wrong:** `npm run dev` binds **port 3001** (`next dev --port 3001`), while `.env.example` and most docs say `localhost:3000`. Hitting the wrong port yields connection-refused; hitting `http://localhost:3001/s/whatever` yields the proxy's bare 404.

**Mitigating fact, verified:** `classifyHost()` **ignores the port on both sides** — `rawHost.toLowerCase().trim().split(":")[0]` and the same for `rootDomain` [VERIFIED: `src/server/tenant/host.ts:75-76`]. And this machine's `.env.local` already sets `NEXT_PUBLIC_ROOT_DOMAIN="localhost:3001"`. So the *classification* is robust; only the *connection* port matters.

**How to avoid:** Derive the base URL the same way `src/app/s/[slug]/preview/page.tsx` derives `editorOrigin` — `const protocol = rootDomain.startsWith("localhost") ? "http" : "https"` — and build `${protocol}://${slug}.${rootDomain}`. That reuses the configured value verbatim. Then probe it once before the loop and fail with an actionable message ("start the server with `npm run dev`") rather than 50 confusing timeouts.

`*.localhost` resolves to 127.0.0.1 in Chromium with zero configuration, including on Windows — CLAUDE.md's Platform Requirements states this explicitly. [VERIFIED: CLAUDE.md]

---

### Pitfall 5: An empty product grid makes half the previews look broken

**What goes wrong:** Every template's default document sets `backgroundImageKey: null` on heroes and `imageKey: null` on editorial-splits — and this is a **hard invariant**, not an oversight: `fashion-apparel.ts`'s header states "`storageKeySchema`'s tenant-prefixed regex makes a shared stock asset structurally unreferenceable, and there is no stock photograph to fall back to." [VERIFIED: codebase read] So heroes render as typographic bands on `bg-secondary`.

That is fine — the templates differ by accent, type scale, section order and variant, all of which a screenshot captures. **But** the product grid is a different story: with zero products the section renders a dashed empty-state block (`strings.storefront.emptyHeading/emptyBody`), and with products but no images each tile renders an `ImageOff` glyph on `bg-muted` [VERIFIED: `product-grid-section.tsx:293-325`].

This matters unevenly. Templates whose second section is `trust-bar` (e.g. `flagship-fashion`, `fashion-classic`) crop fine. Templates whose second section is `product-grid` (e.g. `fashion-edit`: `hero/stack` → `product-grid/showcase`) would put a row of grey placeholder glyphs directly in the preview frame.

**How to avoid — a decision the plan must make explicitly, not by default:**
- **Recommended:** seed the scratch tenant with ~8 products carrying real `imageKey`s, by pushing a handful of neutral placeholder photos once through the existing presign→PUT→finalize path. Cost: one setup task. Benefit: all 50 previews show product imagery, which is the single largest visual gap against the Shopify reference.
- **Acceptable minimum:** seed 8 products with `imageKey: null` — the grid gets real names, prices (`Intl.NumberFormat("fr-CM", …XAF`) and structure, with the deliberate `ImageOff` glyph. `product-grid-section.tsx`'s own comment defends this as "a placeholder that looks chosen rather than a failure."
- **Not acceptable:** zero products. The dashed empty-state block in a template preview reads as a broken template.

**Warning signs:** Reviewing the 50 generated previews side by side and finding a visually distinct cluster that all happen to be product-grid-second templates.

---

### Pitfall 6: The crop rectangle is assumed rather than measured

**What goes wrong:** Every hero variant is `min-h-[85svh] max-h-[900px]` [VERIFIED: `hero-section.tsx`]. At a 1280x800 viewport, 85svh = 680px, so the hero occupies roughly y=0…680 *below* the layout's announcement bar and `StoreHeader`, whose combined height is not a constant (the announcement bar renders only when `tokens.announcementText.trim() !== ""`). A hardcoded `clip: {y: 0, height: 800}` will land differently depending on whether the scratch tenant's tokens carry announcement text — and each template's tokens differ.

**How to avoid:** Do **not** hardcode the clip from arithmetic. Measure once per page with a locator bounding box — e.g. take the second section element's `boundingBox().y` and clip from 0 to `secondSectionTop + K`, where K is a fixed overlap (~120px) that realises D-01's "hero plus roughly the next section." Then letterbox/pad to the target 16:10 in Sharp, or accept a small per-template aspect variance and let `fit: "inside"` normalise the long edge. A first draft should generate 3–5 templates, eyeball them, and only then run all 50.

**Warning signs:** Some previews show a sliver of the second section and others show half of it.

---

### Pitfall 7: Adding a public route "just for the script"

**What goes wrong:** The instinct is `src/app/s/[slug]/preview/template/[key]/page.tsx`. It compiles, it works locally — and it ships a permanently public, unauthenticated route that renders arbitrary platform template content on **every merchant's own domain**. `merchant-shop.einort.com/preview/template/beauty-luxe` is a page on a merchant's brand-bearing hostname whose content the merchant never chose. Combined with the fact that the storefront tree deliberately has no `X-Frame-Options`/`frame-ancestors` header (documented at length in `preview/page.tsx`'s header, because the editor iframe depends on its absence), that is a small but real brand-confusion surface added for a build-time convenience.

**How to avoid:** Pattern 1 — reseed, don't route. If a route is nonetheless chosen, it must be gated by a server-side env check that 404s when the flag is absent (fail closed, the codebase's stated posture), and carry `robots: { index: false, follow: false }` like `/preview` does.

const context = await browser.newContext({

await page.goto(url, { waitUntil: "networkidle" });

const buffer = await page.screenshot({

  animations: "disabled",      // The other half: fast-forward finite animations.
  caret: "hide",
  scale: "device",             // Honour deviceScaleFactor (this is the default).

### The preview key helper (beside `objectKeyFor`, same throw-don't-sanitise posture)

```ts
// Source: pattern copied from src/server/images/r2.ts objectKeyFor()
import { isTemplateKey } from "@/server/theming/registry";

/**
 * The prefix a template's rendered preview derivatives live under (TMPL-06).
 *
 * `templates/` is a SIBLING namespace to `tenants/`, never nested inside one:
 * a preview is platform content, identical for every merchant, and putting it
 * under a tenant prefix would imply an ownership that does not exist.
 *
 * Throws rather than sanitising, exactly like `objectKeyFor`. The input is
 * always a member of the closed `TEMPLATE_KEYS` tuple and never client data,
 * so this is defence in depth — but it costs one call and it means a future
 * caller passing something else gets an exception rather than a stray object.
 *
 * The derivative basename comes from the preset's own `labels` entry, so the
 * full key is `templates/{key}/card.webp`. Renaming that label orphans stored
 * objects rather than moving them — see IMAGE_PRESETS' header.
 */
export function templatePreviewPrefixFor(templateKey: string): string {
  if (!isTemplateKey(templateKey)) {
    throw new Error("Invalid template key for preview object key");
  }
  return `templates/${templateKey}`;
}
```
