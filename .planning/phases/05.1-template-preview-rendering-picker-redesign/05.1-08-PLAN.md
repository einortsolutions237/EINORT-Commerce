## Phase Goal

> **ROADMAP `**Goal:**` verbatim (NOT in `As a ... I want to ... so that ...` user-story form — flagged to the orchestrator; run `/gsd mvp-phase 05.1` to convert):**
>
> The template picker (onboarding and the storefront editor's "Change template" action) shows a real rendered screenshot per template in a large, polished grid — not the placeholder CSS-wireframe thumbnails Phase 5 shipped — closing the gap against the owner-supplied Shopify Discover-Themes reference before Phase 5's Wave 6 builds its 50-template contact sheet on top of it.

**MVP-mode note:** this is the thinnest possible end-to-end proof of the second slice. Four templates travel the entire path — scratch store, Chromium, Sharp, R2, manifest, picker — before anyone commits to fifty. It also exercises D-05's partial-manifest state in the real UI for free, which no unit test can do.

<objective>
Run the generator against a small, deliberately-varied subset of templates, calibrate the crop against what actually came out, and get human sign-off on the framing before committing to all fifty.

Purpose: `05.1-RESEARCH.md` Pitfall 6 and assumption A3 both flag the crop rectangle as arithmetic that has never been measured against a running server — "a first draft should generate 3-5 templates, eyeball them, and only then run all 50". Pitfall 1 (heroes captured mid-fade) and Pitfall 5 (product grids full of `ImageOff` glyphs) are also only detectable by looking at output. Fifty wrong images cost fifty regenerations; four wrong images cost one adjustment.
Output: four committed preview entries, a calibrated crop constant, and an approved framing decision.
</objective>

<interfaces>
Everything this plan needs already exists:

- `npm run templates:previews -- --only=<comma-separated keys>` (plan 05.1-07) — regenerates just those templates and MERGES into the existing manifest rather than clobbering it.
- `npm run templates:previews -- --dry-run` — full loop with no R2 write and no manifest write.

- The redesigned picker (plan 05.1-06) renders `next/image` for a tile whose key is present in the manifest and `<TemplateThumbnail>` for one that is absent.

Template variety for the subset — pick FOUR keys spanning these distinct shapes, reading `src/server/theming/registry.ts`'s `TEMPLATES` to confirm each one's actual `sections` array before choosing:
1. `flagship-fashion` — the flagship, the baseline every other template is compared against.
2. A template whose SECOND section is `trust-bar` (crops cleanly; RESEARCH names `fashion-classic` as an example).
3. A template whose SECOND section is `product-grid` (the hard case — RESEARCH names `fashion-edit`: `hero/stack` then `product-grid/showcase`). This is where seeded product imagery either works or shows grey glyphs.
4. A template from a different segment entirely (electronics, beauty, grocery, furniture or general retail) with a different hero variant, so accent and type-scale differences are visible side by side.
