## Phase Goal

> **ROADMAP `**Goal:**` verbatim (NOT in `As a ... I want to ... so that ...` user-story form — flagged to the orchestrator; run `/gsd mvp-phase 05.1` to convert):**
>
> The template picker (onboarding and the storefront editor's "Change template" action) shows a real rendered screenshot per template in a large, polished grid — not the placeholder CSS-wireframe thumbnails Phase 5 shipped — closing the gap against the owner-supplied Shopify Discover-Themes reference before Phase 5's Wave 6 builds its 50-template contact sheet on top of it.

**MVP-mode note:** this plan is a genuine input to the user-visible slice rather than an interface. Without it, roughly a third of the 50 previews (every template whose second section is a product grid) would show a row of grey `ImageOff` glyphs inside D-01's crop, which reads as a broken template (`05.1-RESEARCH.md` Pitfall 5). It ships ahead of the slice because the generation run consumes it.

<objective>
Assemble the small set of generic, commercial-use-safe placeholder photographs D-06 authorises, expose them through a single `scripts/`-only module, and build the automated containment test that proves they can never reach `TEMPLATE_DEFAULTS` or any file a real merchant request can reach.

Purpose: D-06 is explicit — this imagery exists strictly inside the screenshot-generation script and "must never reach `TEMPLATE_DEFAULTS` or any real merchant's live storefront", and the plan must include "an explicit, testable enforcement mechanism ... not just a code comment promising it". Templates ship zero stock imagery by hard invariant (Phase 5 D-04: `backgroundImageKey`/`imageKey` are null for all 50 rows because `storageKeySchema`'s tenant-prefixed regex makes a shared stock asset structurally unreferenceable). This plan does not weaken that invariant — it builds a wall beside it.
Output: six photographs plus a licence ledger, one path-resolving module, and a source-scanning boundary test.
</objective>
