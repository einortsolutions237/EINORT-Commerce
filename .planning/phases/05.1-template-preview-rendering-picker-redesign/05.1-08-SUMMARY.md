## Accomplishments

- Confirmed prerequisites: `TEMPLATE_PREVIEW_STORE_SLUG="einort-preview"` scratch store already existed (created during 05.1-07), zero orders, `R2_*` vars present, dev server started and reachable on port 3001.
- Ran the dry-run guard exercise first (`--dry-run --only=flagship-fashion`), confirmed exit 0 and zero manifest diff.
- Discovered and fixed a real bug: `measureAndCapture()`'s `page.screenshot({ clip })` call was missing `fullPage: true`, so Chromium silently clamped any `clip.height` taller than the browser viewport (800px) down to the viewport bound — this is what produced Pitfall 6's "sliver of the second section" symptom for `full-bleed`/`band`-variant templates (flagship-fashion, fashion-classic), verified with an isolated Playwright reproduction before touching the real script.
- Discovered a second, independent real bug while investigating why `fashion-edit`'s product tiles rendered as broken images (not the `ImageOff` glyph `product-grid-section.tsx` uses for a genuinely-missing image): `seedScratchProducts()`'s three Prisma upserts ran unconditionally regardless of `options.dryRun`, while only the R2 `putObject` call was gated on it. An earlier (05.1-07) dry-run session had left 8 `ProductImage` rows in the DB whose `storageKey` pointed at R2 objects that were never actually uploaded (confirmed via direct DB query and a raw R2 HTTP 404). Fixed by gating all three upserts on `!dryRun`, then forced one real reseed pass to repair the existing scratch tenant's data.
- Discovered that the redesigned picker's card frame (`05.1-06`, already merged) is a hard `aspect-[16/10]` box with `object-cover object-top` — meaning any stored preview image taller than a true 16:10 slice has its excess silently cropped away by the browser, invisible in the deployed picker even though fully visible when opening the raw WebP directly. An early calibration attempt (margin=450, producing 800×763 images) looked great as a raw file but would have shown almost nothing extra in the real UI — this was caught by working through the object-cover math, not by visual inspection alone.
- Recalibrated using two constants together rather than the margin alone: reduced `VIEWPORT_HEIGHT` (800→640, since every hero variant sizes off `svh` and a taller viewport makes the hero taller too — proportionally eating any margin gained) and raised `SECOND_SECTION_CLIP_MARGIN_PX` (120→300), plus added an explicit `TARGET_CLIP_HEIGHT_PX` cap (auto-derived as `1280 * 500/800 = 800`) so the captured/stored asset always matches the picker's real 16:10 budget — no wasted bytes, no raw-file/rendered-UI mismatch.
- Generated final real previews for all four keys; all four land natively at exactly 800×500 (perfect 16:10, no front-end crop mismatch).
- Ran a two-run determinism check on `flagship-fashion`: byte-for-byte SHA-256-identical across two independent invocations.
- Updated `tests/unit/template-preview-manifest.test.ts`'s sequencing assertion (which the test's own comment stated "05.1-08 is the plan that replaces this assertion") to check for the four calibration entries actually present, in `TEMPLATE_KEYS` order, rather than the prior "ships empty" check.
- All of `npx vitest run tests/unit/template-preview-manifest.test.ts`, `npm run test:unit` (650 tests), `npm run lint`, `npm run typecheck`, and `npm run build` pass.

## Crop Calibration: Before and After

| Constant | Before | After | Reasoning |
|---|---|---|---|
| `VIEWPORT_HEIGHT` | 800 | **640** | Every hero variant sizes off `svh` (`min-h-[85svh]` full-bleed/split, `min-h-[70svh]` stack) — a taller capture viewport makes the hero proportionally taller too, which eats any margin gained by raising the margin constant alone. Solved `chrome(~91px) + 0.85·VH + margin(~150px) <= 800px` (the 16:10 budget) for the worst case (85svh), giving `VH <= ~657`; chose 640. |
| `SECOND_SECTION_CLIP_MARGIN_PX` | 120 | **300** | 120 was only ever enough for the smallest `trust-bar` `strip` variant (86px tall); `band` (210-236px) and `product-grid` `showcase` (~930px, heading + tile rows) both needed meaningfully more before any of their own actual content (not just top padding) became visible. |
| `TARGET_CLIP_HEIGHT_PX` (new) | — (none) | `Math.round(1280 * 500/800) = 800` | The picker's card frame (05.1-06, already shipped) is a hard `aspect-[16/10]` box with `object-cover object-top` — any stored image taller than a true 16:10 slice has its excess silently cropped away by the browser. This cap makes the generated asset's aspect match what the picker will actually render, so the raw-file review Task 2 relies on is trustworthy evidence of the real UI. |

**Critical intermediate finding, recorded so it isn't re-litigated:** an interim calibration attempt (margin=450 with the original 800px viewport, producing 800×763 images) visually looked excellent when the raw WebP file was opened directly — full legible trust-bar content plus a peek at the third section. But because the picker's frame is `object-cover object-top` against a fixed 16:10 box, only the top ~500px-equivalent of a taller image is ever rendered in the real UI; the extra ~263px of "improvement" in that raw file would have been silently cropped away and never seen by a merchant. This is why the final fix targets the CSS frame's own budget (`TARGET_CLIP_HEIGHT_PX`) rather than just eyeballing an isolated raw-file preview at increasing margins — a raw-file review alone can look better while the deployed result stays unchanged.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `measureAndCapture()` missing `fullPage: true`, silently truncating the crop at the viewport**
- **Found during:** Task 1(d), inspecting `flagship-fashion`/`fashion-classic`'s initial output (a bare sliver of the trust-bar band, no legible content)
- **Issue:** `page.screenshot({ clip })` without `fullPage: true` clamps `clip.height` to the current browser viewport height. The function's own `scrollHeight` clamp implies the intent was always to allow capturing beyond the viewport.
- **Fix:** Added `fullPage: true` to the screenshot call, with a comment recording the empirically-verified root cause.
- **Verification:** Isolated Playwright reproduction confirmed the clamp before the fix and its removal after; re-ran the four keys and confirmed non-clamped raw PNG dimensions.
- **Files modified:** `scripts/generate-template-previews.ts`
- **Committed in:** `5dc232e`

**2. [Rule 1 - Bug] `seedScratchProducts()` performed persistent DB writes during `--dry-run`, leaving dangling R2 references**
- **Found during:** Task 1(d), inspecting `fashion-edit`'s product-grid tiles (rendered as broken images with visible alt text, not the deliberate `ImageOff` glyph)
- **Issue:** The three Prisma upserts (`Product`, `ProductVariant`, `ProductImage`) ran unconditionally regardless of `options.dryRun`, while only the R2 `putObject` call was gated on it — an earlier (05.1-07) dry-run session left `ProductImage.storageKey` rows referencing R2 objects that were never uploaded, and every later `--only` run's `skipIfPresent` check (product count >= 8) silently hid the gap forever.
- **Fix:** Gated all three upserts on `!dryRun`, matching the R2 write's gate; forced one real reseed pass (bypassing `skipIfPresent`) to repair the existing scratch tenant's 8 products.
- **Verification:** Direct DB query confirmed `storageKey` matched the expected `objectKeyFor`/`derivativePrefixFor` layout; a raw R2 HTTP HEAD went from 404 to 200 after the reseed; the regenerated `fashion-edit` preview shows real, recognizable product photography.
- **Files modified:** `scripts/generate-template-previews.ts`
- **Committed in:** `5dc232e`
