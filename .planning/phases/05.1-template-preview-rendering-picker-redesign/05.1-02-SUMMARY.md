## Decisions Made
- **Test fixture for the lossy-vs-lossless byte-size comparison (Task 1):** the plan's own action text anticipated "dense antialiased text" as the reason `templatePreview` needs `lossless: false`. An initial fixture built from sparse SVG text lines on a large flat background produced the *opposite* result in the test — lossless WebP compresses flat regions extremely well (the same property the `logo` row's own header cites as a reason to prefer lossless there), so the sparse-text fixture's lossless encode came out smaller than its lossy encode. Switched to dense per-pixel random noise, which reliably reproduces the "lots of independent, non-repeating detail" property that makes lossless WebP perform worse than lossy — the same underlying property real antialiased screenshot text has, just expressed in a way that is deterministic and immune to a background-ratio accident. No production code was affected; this was purely a test-fixture correction caught while running the test the plan specified.
- **Placement of `templatePreviewPrefixFor`:** directly beneath `derivativePrefixFor` in `r2.ts`, per the plan's instruction and the file's own stated convention that adjacent functions keep "the two halves of the layout" (now three) from drifting apart across files.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Test fixture inverted the lossy/lossless size comparison it was meant to prove**
- **Found during:** Task 1 (templatePreview preset test coverage)
- **Issue:** The plan's behavior spec (Test 5) called for "materially smaller than the same input encoded losslessly at the same size," with the fixture recipe implied to be text-like content. A first implementation using sparse SVG text on a large flat background produced a lossless encode *smaller* than the lossy encode, failing the assertion (`expected 62256 to be less than 11282.4`) — because a mostly-flat image is exactly the case lossless WebP is good at, not bad at.
- **Fix:** Replaced the fixture generator with dense per-pixel random noise (`crypto.randomBytes` rasterized via Sharp), which reliably makes lossless WebP compress worse than lossy WebP at the same target size, matching the property the row's own header comment attributes to "dense antialiased text" — expressed more robustly for a deterministic unit test.
- **Files modified:** `tests/unit/image-pipeline.test.ts`
- **Verification:** `npx vitest run tests/unit/image-pipeline.test.ts` — all 26 tests pass, including the lossy-vs-lossless comparison.
- **Committed in:** `7469502` (Task 1 commit)
