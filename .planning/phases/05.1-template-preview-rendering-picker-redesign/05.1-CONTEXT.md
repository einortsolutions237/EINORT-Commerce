# Phase 05.1: Template Preview Rendering & Picker Redesign - Context

**Gathered:** 2026-09-07
**Status:** Ready for planning

<domain>
## Phase Boundary

Replace the 50 templates' zero-byte CSS-wireframe thumbnails with real rendered screenshot previews, and redesign the shared `TemplatePicker`/`TemplateTile` grid used by both the onboarding flow (`src/app/onboarding/branding/**`) and the storefront editor's "Change template" panel (`src/app/(dashboard)/dashboard/storefront-editor/change-template-panel.tsx`) toward Shopify Discover-Themes-quality: real preview images, larger cards, clearer typography/hierarchy, hover states, category grouping.

This phase does not change which 50 templates exist, their tier gating, their default document/token content, or the switching/publishing mechanics built in Phase 5 Waves 1-5 — it changes only how each template is *previewed* before a merchant picks it.

Inserted as an urgent decimal phase after Phase 5's Wave 5 and before Wave 6, because Wave 6's plan (05-22) builds a 50-thumbnail "contact sheet" for the design-distinctiveness stranger test using this same thumbnail component — it should exercise the redesigned, real-screenshot version.

</domain>

<decisions>
## Implementation Decisions

### Screenshot framing
- **D-01:** Each preview image is a cropped shot capturing the hero section plus roughly the next section (e.g. trust bar or first product row) — not hero-only, and not a full scrollable homepage compressed into one tall image. This matches a picker card's aspect ratio while still showing enough structure/accent per template to tell them apart at a glance.

### Rendering & regeneration strategy
- **D-02:** Screenshots are generated by a one-time build/seed script, not rendered on-demand at request time. The script renders all 50 templates' `TEMPLATE_DEFAULTS` (default document + tokens, deterministic) and uploads the resulting images to R2 once. No runtime rendering cost, no request-time latency risk. Re-running the script is a manual step whenever a template's default design changes — this phase's plan should make that re-run path an explicit, documented command, not an ad-hoc script only the original author knows how to invoke.
- **D-03 (implied by D-02):** The script needs a headless-browser dependency (e.g. Playwright or Puppeteer) that is not currently in the project's dependency tree. Per this project's established pattern (`next-themes` in quick task 260906-egn), a new dependency of this kind is `[ASSUMED]` until package-legitimacy-checked and gets a blocking `checkpoint:human-verify` gate before install — the plan must include this gate, not skip it.

### Grid layout per surface
- **D-04:** One shared card design (same image aspect ratio, same typography treatment) is used in both surfaces. Onboarding's full-width page renders more columns; the editor's narrower "Change template" side panel renders fewer columns (down to 1-2 if needed) — column count is responsive to available width, not a second card variant. No duplicate component to maintain.

### Fallback behavior
- **D-05:** If a template's screenshot isn't available (mid-generation, or generation failed for that one template), the tile falls back to 05-09's existing CSS-wireframe `TemplateThumbnail` component rather than a broken-image icon, blank tile, or generic skeleton. Since generation is a one-time build script (D-02), this fallback should rarely if ever be seen in production — it exists as a safety net for partial-script-completion, not as an expected steady-state UI.

### Preview imagery
- **D-06 (added after research, before planning):** Templates ship with zero stock imagery by design (`backgroundImageKey`/`imageKey` null for all 50 rows, per Phase 5's D-04 — a real merchant supplies their own photos). A raw screenshot of that default state would show empty image slots, unlike Shopify's photo-filled cards. Decision: add a small set of generic, royalty-free, per-segment placeholder photography (fashion/electronics/beauty/grocery/furniture/general-retail) used **strictly inside the screenshot-generation script** to produce richer preview images — this imagery must **never** reach `TEMPLATE_DEFAULTS` or any real merchant's live storefront. The plan must include an explicit, testable enforcement mechanism (e.g. a source-scanning contract test, mirroring this codebase's other boundary tests like `surface-token-isolation.test.ts`) proving the placeholder-photo asset set is referenced only from the screenshot script's own module, never from `src/server/theming/defaults.ts` or any file reachable by a real request.
- Exact placeholder-photo source (Unsplash/Pexels-style royalty-free catalog, or a small hand-picked set) is left to research/planning — commercial-use-safe licensing is the only hard constraint.

### Claude's Discretion
- Exact storage mechanism: a new `previewImageKey`-style field on the `TEMPLATES` registry row vs. a separate manifest/lookup table — research should evaluate both against the existing `IMAGE_PRESETS`/R2 pattern in `src/server/images/pipeline.ts` and `src/server/images/r2.ts` and recommend one.
- Exact image dimensions/aspect ratio, compression/format (the existing Sharp pipeline's conventions should inform this).
- Exact headless-browser library choice (Playwright vs. Puppeteer) — research should compare against this project's constraints (Node 24 runtime, Vercel deployment target, solo-builder maintenance burden) and recommend one for the human-verify gate to evaluate.
- Whether the build script renders against a real running dev/preview server or an isolated render context — a technical implementation detail for research/planning to resolve.
- Exact grid card visual details (typography scale, spacing, hover treatment) beyond the aspect-ratio/column-count decisions above — informed by the UI-SPEC step, using the Shopify Discover-Themes reference screenshot the user supplied as the visual target.

</decisions>

## Existing Code Insights

### Reusable Assets
- `TemplateThumbnail` (`src/components/theming/template-thumbnail.tsx`) — becomes the fallback component per D-05, not deleted.
- `IMAGE_PRESETS` / `processImage()` pattern (`src/server/images/pipeline.ts`) — the established one-object-literal-per-surface pattern for image handling; a new `templatePreview` preset likely follows this shape.
- R2 presigned-upload/finalize pattern (`src/server/images/r2.ts`) — may not directly apply (this is server-generated, not a merchant browser upload), but the R2 client/bucket configuration is reusable.

### Established Patterns
- `Readonly<Record<TemplateKey, ...>>` registry pattern — any new per-template data (like a preview image key) should extend `TemplateDefinition`/`TEMPLATES` following this same exhaustive-by-construction style, not a separate loosely-typed lookup.
- Package-legitimacy human-verify gate — every new npm dependency in this project's recent history (`next-themes`) gets a blocking checkpoint before install when `slopcheck`/equivalent tooling can't verify it automatically.

### Integration Points
- `TemplatePicker`/`TemplateTile` is the single shared component consumed by `src/app/onboarding/branding/branding-form.tsx` (05-18) and `src/app/(dashboard)/dashboard/storefront-editor/change-template-panel.tsx` (05-19) — changes here propagate to both call sites for free, per D-04.
- Phase 5 Wave 6's `05-22-PLAN.md` (not yet executed) will consume this phase's redesigned thumbnails for its 50-template contact sheet — confirm before Wave 6 executes that its plan references the new preview-image mechanism, not the old wireframe one.
