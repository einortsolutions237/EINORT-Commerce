## Phase Goal

**As a** prospective Cameroonian merchant, **I want to** sign up with an email, a password and a store address I choose myself, **so that** I immediately have a working, tenant-isolated storefront at `{my-store}.einort.com` that no other merchant's data can ever leak into.

<objective>
Build the server side of the merchant journey: authentication, tenant provisioning, and the live store-address availability check that D-02 requires. After this plan the whole loop closes on the server — a signup call produces a user, a tenant, a membership, a slug-history row, an active session, and a subdomain that plan 05's resolver answers for on the very next request.

Purpose: ONB-01, DOM-01 and the authoritative write-layer half of TEN-06 land here. This is also where the three Better Auth behaviours that no public tutorial gets right must be implemented exactly: system-action organization creation, the `beforeCreateOrganization` body re-spread trap, and the fact that the built-in slug checker cannot serve an anonymous signup form.
Output: `auth.ts`, the auth route handler, `checkStoreSlug`, `signUpMerchant`, and a green signup isolation test.
</objective>

Order of operations inside `checkStoreSlug`, and the order matters: rate-limit FIRST, because this endpoint is unauthenticated and enumerable — it is a direct read of which merchants exist. Read the IP from `await headers()` (async in Next 16) and consult the `rl:slugcheck` limiter; on rejection return `{ status: "rate-limited", ... }`, which plan 07's form maps to the "check unavailable" UI state (the CTA stays ENABLED in that state — the server is the authority, the client is UX only). Then `storeSlugSchema.safeParse`; on failure inspect the first issue's message and return `reserved` when it carries the reserved wording, `invalid` otherwise. Then check uniqueness with `platformDb.organization.findUnique({ where: { slug }, select: { id: true } })` and, separately, check `StoreSlugHistory` for the same slug through the unscoped registry path so a previously-claimed-and-released slug also reports `taken`. Return `available` only when both are clear.

Do NOT wire `authClient.organization.checkSlug()` to this. It sits behind `requestOnlySessionMiddleware`, which throws `UNAUTHORIZED` whenever the call carries request headers and no session — which is precisely an anonymous signup form, so it 401s on every keystroke. It also only tests uniqueness (it would report `admin` as available, since it knows nothing about the reserved list) and it signals collision by throwing rather than returning a value.

Create `src/server/auth/signup.ts` with `"use server"`, exporting `signUpMerchant`. Validate the whole payload with a Zod 4 object: `email` (use the v4 top-level email form), `password` string min 8 max 128, `storeName` trimmed 2-80, and `slug: storeSlugSchema`. Rate-limit with the `rl:signup` limiter before doing any work. Then:

  1. `auth.api.signUpEmail({ body: { email, password, name: storeName }, headers })` — creates the user and the session; `nextCookies()` persists the cookie.
  2. `auth.api.createOrganization({ body: { name: storeName, slug, userId: signUp.user.id } })` with **NO `headers`**. Passing `userId` and omitting headers is what makes this a system action (`isSystemAction = !session && ctx.body.userId`), which is verified to bypass `allowUserToCreateOrganization: false` while `organizationLimit: 1` still applies. GitHub issue #6791 claims the opposite; that claim does not hold for 1.6.29. Catch the failure: Better Auth re-checks slug uniqueness inside the endpoint and returns `BAD_REQUEST ORGANIZATION_ALREADY_EXISTS`, which is exactly the race between the live availability check and submit — surface it as a slug-scoped error using `01-UI-SPEC.md`'s "slug race-lost" copy.
  3. Write the initial slug claim: `scopedDb(org.id).storeSlugHistory.create({ data: { slug } })`. Do not pass `tenantId` — the extension stamps it, which is the point. This row is D-03's rename-safe record and is what makes a released slug un-reissuable.
  4. `auth.api.setActiveOrganization({ headers, body: { organizationId: org.id } })`.
