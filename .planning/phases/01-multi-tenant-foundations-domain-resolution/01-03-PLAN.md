## Phase Goal

**As a** prospective Cameroonian merchant, **I want to** sign up with an email, a password and a store address I choose myself, **so that** I immediately have a working, tenant-isolated storefront at `{my-store}.einort.com` that no other merchant's data can ever leak into.

Create `proxy.ts` at the repository root (same level as `src/`). The filename is `proxy.ts`, NOT `middleware.ts` — Next 16 renamed the convention, `middleware.ts` is deprecated and slated for removal, and every hostname snippet in `.planning/research/ARCHITECTURE.md` is written against the old convention and must be treated as pseudocode. Export a named function `proxy` (or a default export; do not export both). Do NOT set `export const runtime` in this file — Proxy is always Node.js runtime in Next 16 and setting the runtime option throws.

Body, in this exact order:

1. **First statement, before anything else:** if `pathname === "/s"` or `pathname.startsWith("/s/")`, return `new NextResponse(null, { status: 404 })`. The `/s/[slug]` route tree is a real filesystem route; nothing otherwise stops `https://einort.com/s/some-other-store` from serving a tenant storefront on the apex. That is not a data leak (storefronts are public) but it breaks DOM-02's exact-resolution guarantee, creates duplicate content across hosts, and renders merchant-controlled content inside the apex cookie scope — which is exactly what makes the D-07 cookie separation safe. This is safe to do unconditionally because legitimate traffic reaches `/s/...` only after a rewrite, and rewrites do not re-enter the Proxy.

2. Copy `request.headers` into a new `Headers` instance and unconditionally `delete("x-tenant-id")` and `delete("x-store-slug")` on it — on EVERY branch, including root and reserved, not only the storefront branch. A client can send these headers itself; the Proxy feels like a trusted boundary but nothing enforces that downstream. Forward the sanitised headers with `NextResponse.next({ request: { headers } })` — note the nested `request` key; `NextResponse.next({ headers })` exposes them to the client instead.

3. Call `classifyHost(request.headers.get("host"), ROOT_DOMAIN)` where `ROOT_DOMAIN` is read once at module scope from the literal expression `process.env.NEXT_PUBLIC_ROOT_DOMAIN` (a literal reference, so Next inlines it), throwing at module load if it is missing — a blank root domain silently classifies every host as root and takes every storefront offline.

4. Switch exhaustively on `result.kind`: `root` and `reserved` both return the sanitised passthrough (root serves D-06's placeholder, D-07's signup/login/dashboard and `/api/auth/*`; reserved hostnames are platform-owned and are never a tenant lookup). `unknown` returns `NextResponse.rewrite(new URL("/store-not-found", request.url))` — fail closed, DOM-02. `store` clones `request.nextUrl`, sets `url.pathname` to `/s/${result.slug}${pathname}` and returns `NextResponse.rewrite(url, { request: { headers } })` with the sanitised headers.

Do not put Prisma, Redis or any `src/server/db/**` import behind this file. The Next 16 Proxy docs state it "should not attempt relying on shared modules or globals", and bundling the ORM here pays cold-start on every matched request including prefetches. Resolution against the database is plan 05's job, in the storefront layout.

Export `config.matcher` as `["/((?!_next/static|_next/image|favicon.ico|robots.txt|sitemap.xml).*)"]`. Deliberately do NOT exclude `/api`: a storefront subdomain hitting `/api/auth/*` must be rewritten into `/s/{slug}/api/auth/*` so it 404s, keeping auth apex-only per D-07. Note that without a matcher the Proxy runs on every request including static assets, and that `_next/data` runs even when a negative matcher excludes it.

Do not copy `vercel/platforms`'s `extractSubdomain` verbatim — it only rewrites when `pathname === "/"`, has no reserved handling, no fail-closed branch and no `/s/` guard. It is a demo, not a security boundary.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| internet -> Proxy | Every inbound request, including scanner traffic across the whole wildcard space. All request headers and the full URL are attacker-controlled. |
| Proxy -> application routes | The only sanctioned channel for tenant identity is the rewritten path. Headers crossing this boundary must be sanitised. |
| apex host -> storefront route tree | Must be impassable: a tenant storefront must never render in the apex cookie scope. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
