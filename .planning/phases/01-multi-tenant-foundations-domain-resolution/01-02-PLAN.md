## Phase Goal

**As a** prospective Cameroonian merchant, **I want to** sign up with an email, a password and a store address I choose myself, **so that** I immediately have a working, tenant-isolated storefront at `{my-store}.einort.com` that no other merchant's data can ever leak into.

<objective>
Create the tenant data model and the single sanctioned path to it. This plan delivers the load-bearing guarantee of the whole product: `scopedDb(tenantId)` injects `tenantId` into every operation on every registered model and throws for anything unregistered, while `platformDb` and `adminDb` cover the two categories that legitimately are not tenant-scoped.

Purpose: TEN-01, TEN-02, TEN-05 and the `tenantId` half of TEN-08 are satisfied structurally here, not by convention in later feature code. Plan 04 proves it with a two-tenant suite; plans 05-07 consume it.
Output: an applied first migration on Neon and four data-access clients behind the lint boundary that plan 01 already installed.
</objective>

Create all four modules with `import "server-only";` as the first line, so an accidental client import is a build failure rather than a runtime credential leak.

`src/server/db/base.ts`: import `PrismaClient` from `@/generated/prisma/client` and `PrismaPg` from `@prisma/adapter-pg`. Construct `const adapter = new PrismaPg({ connectionString: env.DATABASE_URL })` — the pooled Neon URL (C-5), because an unpooled URL exhausts Postgres connection limits under serverless concurrency. Export `prismaBase` as a `globalThis`-cached singleton, assigning to the global only when `process.env.NODE_ENV !== "production"`, to survive dev hot-reload. Never instantiate `new PrismaClient()` per request or per tenant; `$extends` returns a cheap wrapper that shares the pool.

`src/server/db/tenant-scoped.ts`: export `TENANT_SCOPED_MODELS` as a `Set<string>` initialized to exactly `["StoreSlugHistory"]`. Export `scopedDb(tenantId: string)` which throws `"scopedDb: tenantId is required"` on a falsy `tenantId`, then returns `prismaBase.$extends({ name: "tenant-scope", query: { $allModels: { $allOperations({ model, operation, args, query }) { ... } } } })`.

Inside the handler, first check membership: if `model` is not in `TENANT_SCOPED_MODELS`, throw an error naming the model and directing the caller to `platformDb` (registry) or `adminDb` (platform admin, `src/server/admin/**` only). Failing loudly here is the entire point — a model that nobody registered must never silently run unscoped.

Then branch on `operation`, matching the verified `args` shapes:
  - `create` -> set `args.data = { ...args.data, tenantId }`. Spread order matters: `tenantId` goes LAST so a caller-supplied `tenantId` is overwritten, never merged. This is TEN-08 and CLAUDE.md C-2 in one line.
  - `createMany` and `createManyAndReturn` -> `args.data` arrives as an ARRAY; normalize with `Array.isArray` and map each element to `{ ...d, tenantId }`.
  - `upsert` -> inject into BOTH `args.where` and `args.create`, so an upsert can never resurrect or hijack another tenant's row.
  - default (covering `findUnique`, `findUniqueOrThrow`, `findFirst`, `findFirstOrThrow`, `findMany`, `count`, `aggregate`, `groupBy`, `update`, `updateMany`, `delete`, `deleteMany`) -> `args.where = { ...args.where, tenantId }`. Note that `aggregate` and `groupBy` may arrive with no `where` key at all; spreading `undefined` is safe.
Then `return query(args)`.

Do NOT rewrite `findUnique` into `findFirst`. That workaround is still the top public search result for Prisma tenant scoping and it is stale: `extendedWhereUnique` has been GA since Prisma 5, and this session verified against the generated 7.9.1 client that `ProductWhereUniqueInput` is `Prisma.AtLeast<{...all scalars...}, "id" | ...>` — non-unique scalars such as `tenantId` are accepted alongside the unique selector and pass runtime validation. Rewriting fragments the extension and reopens escape hatches. Do NOT use `prisma.$use()` either — it was removed in Prisma 7; extensions are the only mechanism.

`$allOperations` hands `args` in loosely-typed form, so a small amount of `any` is unavoidable. Contain it entirely in this file and keep the file short. Export `type ScopedDb = ReturnType<typeof scopedDb>`.

`src/server/db/platform.ts`: export `platformDb`. This is the third client category and it is necessary — slug availability and hostname resolution must read the `organization` table, which is NOT tenant-scoped and therefore cannot go through `scopedDb`. Without naming this category, that code would be forced to reach for `prismaBase` (weakening the boundary) or `adminDb` (polluting the TEN-05 admin isolation). Implement it as a narrow façade over `prismaBase` exposing only the non-tenant-scoped registry models this project needs: `organization`, `user`, `member`, `session`. Do not re-export the whole client.

`src/server/db/admin.ts`: export `adminDb` as a deliberately unscoped client over `prismaBase`, with a file-header comment stating that it is intentionally cross-tenant, that it exists to satisfy TEN-05's architectural-isolation requirement, that it is importable only from `src/server/admin/**` (enforced by the ESLint zone from plan 01), and that no admin routes exist until Phase 6. TEN-05 is satisfied by this client existing, being unscoped, and being lint-fenced — not by building admin UI now.

Do not add Postgres Row-Level Security in this phase. CLAUDE.md C-7 defers it past V1 deliberately; record it in the SUMMARY as intentional debt, not an oversight.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| application code -> database | Every tenant-scoped read/write crosses here. `scopedDb` is the sole sanctioned crossing; anything else is a bug by construction. |
| caller-supplied payload -> `scopedDb` args | A `tenantId` present in `data` or `where` is attacker-influenced input and must never win. |
| platform-admin surface -> tenant data | Deliberately unscoped. Isolation is architectural (separate module + lint zone), not conditional. |
