## Phase Goal

**As a** prospective Cameroonian merchant, **I want to** sign up with an email, a password and a store address I choose myself, **so that** I immediately have a working, tenant-isolated storefront at `{my-store}.einort.com` that no other merchant's data can ever leak into.

<objective>
Close the hostname loop: the slug that plan 03's Proxy put into the URL becomes a real tenant, read from Postgres through a Redis-cached, fail-closed resolver, and rendered as either a live storefront or the branded EINORT failure page.

Purpose: this is the plan that makes the Walking Skeleton walk. After it, a real visitor typing a real subdomain gets a real page backed by a real database read — and every wrong hostname converges on one indistinguishable failure surface, which is both D-04/D-05 and an anti-enumeration control.
Output: `resolveTenantBySlug`, the `tenant:host:*` cache, the `/s/[slug]` storefront route tree, and the shared branded 404 body.
</objective>

Create `src/server/tenant/cache.ts` with `import "server-only"` at the top. It owns the `tenant:host:{slug}` key namespace and nothing else — C-11 keeps `tenant:host:*`, `session:*` and `jobs:*` separate, and Phase 3's cart/idempotency keys must not land here.

Export `getCachedTenant(slug)`, `setCachedTenant(slug, tenant)`, `setCachedMiss(slug)` and `invalidateTenantHost(...slugs)`. Cache the full `{ id, slug, status }` object, not just the id — the resolver must be able to enforce D-05 (suspended renders the same not-found page) without a second lookup. Use a distinct sentinel value for a negative entry.

Two TTLs, both required: 300 seconds for a hit and 60 seconds for a miss. The shorter negative TTL exists because with a wildcard domain every `<anything>.einort.com` reaches the app, so a scanner walking random subdomains produces a stream of cache misses that each fall through to a database lookup returning nothing and caching nothing — an unauthenticated path to saturating the Neon connection pool. Caching the miss is the fix; a shorter TTL keeps a newly-claimed slug from being shadowed for long.

When `UPSTASH_REDIS_REST_URL` or `UPSTASH_REDIS_REST_TOKEN` is absent, the module must degrade to a no-op cache (every read a miss, every write discarded) AND emit a single `console.warn` naming the missing variables. The degradation is for local dev without Upstash credentials; making it loud is what stops it silently shipping to production. Do not throw — a missing cache must not take the storefront down.

Create `src/server/tenant/resolve.ts` with `import "server-only"`. Export `ResolvedTenant` and `resolveTenantBySlug`, wrapping the function in React's `cache()` so repeated calls within one render pass dedupe to a single lookup. Logic: read the cache; a negative sentinel returns `null` immediately; a positive hit returns the tenant only when `status === "active"`, otherwise `null`. On a miss, read `platformDb.organization.findUnique({ where: { slug }, select: { id: true, slug: true, status: true } })`. If nothing is found, write the negative entry and return `null`. If found, write the positive entry with the full record and then return it only when `status === "active"`. Note the ordering: cache what the database said, then apply the suspension rule at return time — that way a later un-suspend only needs an invalidation, not a different cache shape.

Fail closed everywhere. Any unexpected error from the cache layer must fall through to the database read; any unexpected error from the database read must propagate rather than resolve to a tenant.

Do not import this module from `proxy.ts`. Resolution needs the database and the cache; the Proxy is documented to avoid shared modules and runs on every matched request including prefetches. The split is deliberate.

Write `tests/isolation/resolve.test.ts` (isolation project — it needs the seeded database). Assert: an active seeded slug resolves to that tenant's id; an unknown slug resolves to `null`; a slug whose organization has `status` set to something other than `"active"` resolves to `null`; a second call for the same slug within the TTL issues no second database query (spy on the `platformDb.organization.findUnique` call count); an unknown slug queried twice issues only one database query (proving the negative cache); and `invalidateTenantHost(slug)` causes the next call to hit the database again. Give the suspension test a name containing "suspended" so it is greppable.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| rewritten `/s/{slug}` path -> tenant record | The slug arrives from the Proxy, derived from the Host header. The resolver must treat "no match" and "not active" identically and must never fall through to a default tenant. |
| anonymous visitor -> store existence signal | Whether a hostname is suspended versus never claimed is information the platform deliberately withholds. |
| wildcard hostname space -> Neon connection pool | Every `*.einort.com` reaches the app. Unbounded cache misses are an availability risk. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-29 | Information disclosure | Distinguishing a suspended store from a never-claimed hostname (enumeration of the merchant base) | mitigate | Both paths call `notFound()` and render the identical `src/app/not-found.tsx` with identical props and a 404 status; asserted by a byte-identical `curl` body diff (D-05) |
| T-01-30 | Elevation of privilege | A suspended or unresolved tenant's storefront still rendering child routes | mitigate | `resolveTenantBySlug` returns `null` for any non-`active` status and the `/s/[slug]` layout calls `notFound()` before rendering children; no `try`/`catch` may swallow a resolver error |
| T-01-31 | Denial of service | Wildcard-subdomain scan producing one uncached database miss per request until the Neon pool is exhausted | mitigate | Negative caching of misses at a 60s TTL plus zero-I/O rejection of malformed labels in `classifyHost` (plan 03); most scanner traffic dies before touching Redis |
| T-01-32 | Tampering | A suspended store continuing to serve for up to the cache TTL after a platform admin suspends it | mitigate | `invalidateTenantHost` is exported and must be called on every `slug` or `status` mutation; the 300s TTL is a backstop, not the mechanism. Phase 6's suspend action and plan 06's provisioning both call it. |
| T-01-33 | Information disclosure | Search engines indexing thousands of wildcard hostnames as 200-status pages | mitigate | Failure renders through `notFound()` for a genuine 404 status rather than a rewritten 200 |
| T-01-34 | Information disclosure | Cross-tenant leakage through a cached storefront shell | mitigate | `cacheComponents` stays off in Phase 1; Next 16 is dynamic by default, which is the tenant-safe posture |
| T-01-35 | Denial of service | Upstash outage or missing credentials taking every storefront offline | accept | The cache degrades to a no-op with a loud `console.warn` and the resolver falls through to Postgres. Accepted because the failure mode is added database load, not incorrect tenant resolution, and V1 pilot traffic is small. |
</threat_model>
