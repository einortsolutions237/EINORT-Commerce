## Phase Goal

**As a** prospective Cameroonian merchant, **I want to** sign up with an email, a password and a store address I choose myself, **so that** I immediately have a working, tenant-isolated storefront at `{my-store}.einort.com` that no other merchant's data can ever leak into.

Purpose: TEN-07 is a hard gate on the phase ("automated tenant-isolation tests exist and run before any milestone is considered done"), and the suite is what converts plan 02's structural claims about TEN-02, TEN-05 and TEN-08 into observed behaviour against a real Postgres. </objective>

Create `tests/isolation/tenant-isolation.test.ts`. Do NOT write per-model tests. Iterate `TENANT_SCOPED_MODELS`, derive the delegate key by lowercasing the model name's first character, and generate a `describe(model)` block per registered model, so a model added in Phase 3 is covered the moment it is registered. Inside each block, acting as tenant B against a database seeded with one row per tenant:

  - "findMany returns only tenant B rows" — result length is 1 and its `tenantId` equals `TENANT_B.id`
  - "findUnique on a tenant-A id returns null" — exercises the `extendedWhereUnique` path that the stale `findFirst`-rewrite advice would have broken
  - "findFirst on a tenant-A id returns null"
  - "update on a tenant-A id affects 0 rows / throws" — assert the tenant-A row is byte-unchanged afterwards, not merely that the call rejected
  - "delete on a tenant-A id throws or affects 0 rows" — and the tenant-A row still exists afterwards
  - "updateMany and deleteMany never touch tenant A" — after an unfiltered `updateMany`/`deleteMany` as tenant B, tenant A's row count read through `adminDb` is unchanged
  - "count, aggregate and groupBy exclude tenant A" — note `aggregate` and `groupBy` may arrive with no `where` at all, which is exactly the case that would leak if the extension only handled `where`-bearing operations
  - a test whose name contains "ignores client-supplied tenantId": `create` with `data: { ..., tenantId: TENANT_A.id }` issued through `scopedDb(TENANT_B.id)` stores the row under B (TEN-08 / CLAUDE.md C-2 — the extension overwrites, it does not merge)
  - "upsert cannot resurrect a tenant-A row" — an upsert keyed on a tenant-A unique selector must create a new B-owned row or fail, never mutate A's

Also include these three suite-level tests, outside the per-model loop:

Add one negative-control test asserting `scopedDb(TENANT_B.id)` throws when addressed at a model that is NOT in `TENANT_SCOPED_MODELS` (use a registry model such as `organization`), with an error message naming `platformDb` and `adminDb`. ## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| tenant B's request context -> tenant A's rows | The boundary this entire plan exists to test. Both tenants' data lives in one shared schema. |
| future schema changes -> the tenant-scoping registry | An unregistered model with a `tenantId` column is an unguarded table. The drift guard is the control. |
| test fixture -> production database | The seed truncates every table; pointing it at the wrong connection string is destructive. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-21 | Information disclosure | Cross-tenant read through any of the 14 intercepted Prisma operations | mitigate | Model-generic suite asserts read isolation for `findMany`, `findUnique`, `findFirst`, `count`, `aggregate` and `groupBy` per registered model |
| T-01-22 | Tampering | Cross-tenant write or delete via `update`, `updateMany`, `delete`, `deleteMany` or `upsert` | mitigate | Each is asserted to leave tenant A's row byte-unchanged, verified by re-reading through `adminDb` after the attempted mutation |
| T-01-23 | Tampering | Client-supplied `tenantId` honoured on create | mitigate | Dedicated behavioural test "ignores client-supplied tenantId" (TEN-08) |
| T-01-24 | Elevation of privilege | `scopedDb` silently running unscoped against a model nobody registered | mitigate | Negative-control test asserting a throw whose message names `platformDb` and `adminDb` |
| T-01-25 | Information disclosure | Transactional writes escaping the extension (assumption A1, unverified before this plan) | mitigate | Explicit "$transaction inside scopedDb stays scoped" test; a failure is a declared blocking finding that forces a `$transaction` wrapper before any Phase 3 transactional code |
| T-01-26 | Tampering | Isolation guarantee decaying as Phases 3-6 add models | mitigate | Drift guard over `Prisma.ModelName` + `Prisma.<Model>ScalarFieldEnum`, with its failure path itself verified by temporarily de-registering a model |
