## Phase Goal

**As a** prospective Cameroonian merchant, **I want to** sign up with an email, a password and a store address I choose myself, **so that** I immediately have a working, tenant-isolated storefront at `{my-store}.einort.com` that no other merchant's data can ever leak into.

<objective>
Ship the one user-facing form in Phase 1 and close the Walking Skeleton loop: a real person on a real browser fills in three fields, watches their store address get checked live, submits, and arrives at their own storefront on their own subdomain.

Purpose: this is the plan where the phase becomes demonstrable rather than merely tested. It also carries the two verification steps that no unit test can cover — the Windows-specific `next start` proxy smoke check, and human confirmation that the surfaces match `01-UI-SPEC.md`.

</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser form -> server actions | Every field is attacker-controlled. Client-side validation and client-side submit gating are UX, never enforcement. |
| authenticated session -> recovery route | The recovery route must derive identity from the session only, never from a query parameter or form field. |
| local production build -> real deployment | The Windows `next start` behaviour is the closest available proxy for production routing on this machine. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-48 | Elevation of privilege | Bypassing the client form to submit a reserved or malformed slug | mitigate | Client gating is presentational only; the authoritative gates are `storeSlugSchema` inside the server action and `beforeCreateOrganization` in plan 06, both already proven by `tests/isolation/signup.test.ts` |
| T-01-49 | Spoofing | The recovery route accepting a user id or organization id from the URL or form | mitigate | `/onboarding/create-store` reads identity only from `auth.api.getSession({ headers })` and counts organizations server-side; no identifier is accepted from the request |
| T-01-50 | Information disclosure | Slug enumeration accelerated by the form's debounced live check | mitigate | Server-side `rl:slugcheck` limiter from plan 06 is the control; the 400ms debounce and the 3-character minimum reduce incidental volume but are not relied upon |
| T-01-51 | Tampering | A stale in-flight availability response overwriting the current one, showing "available" for a taken address | mitigate | `AbortController` or request sequence number so only the latest response may update state; asserted as a source criterion and as human-verify step 6 |
